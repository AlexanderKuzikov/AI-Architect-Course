# GLOSSARY — Очереди задач и фоновая обработка

Термины из модуля по алфавиту. Латиница — первой, затем кириллица.

---

## A

**ACK (Acknowledgement)**  
Подтверждение успешной обработки задачи воркером. В BullMQ — неявный ACK: возврат из processor без исключения = успех, Redis структуры обновляются автоматически. Без ACK задача остаётся active до истечения lock.

**at-least-once**  
Гарантия доставки: задача будет выполнена минимум один раз. При падении воркера до завершения — задача возвращается в очередь и обрабатывается повторно. Требует идемпотентного processor. BullMQ работает в режиме at-least-once.

**at-most-once**  
Гарантия доставки: задача выполнится не более одного раза, но может быть потеряна. Подходит для некритичных операций (аналитика, метрики). В Node.js — `EventEmitter` или прямой вызов без персистентности.

**attempts**  
Максимальное число попыток выполнения задачи включая первую. `attempts: 3` = первая попытка + 2 retry. При исчерпании — задача переходит в `failed`. Устанавливается в `defaultJobOptions` или на уровне отдельной задачи.

---

## B

**backoff**  
Стратегия задержки между повторными попытками. Типы в BullMQ: `exponential` — задержка удваивается с каждой попыткой (`delay * 2^attemptsMade`); `fixed` — фиксированная задержка. Предотвращает шторм retry при массовом сбое.

**backpressure**  
Механизм сдерживания producer когда consumer не успевает обрабатывать. В контексте очередей: проверять `queue.getWaitingCount()` перед добавлением задач, ждать если очередь превышает порог. Без backpressure — Redis заполняется быстрее чем воркеры обрабатывают.

**batch processing**  
Обработка группы задач за одну операцию. В pg-boss: `batchSize: N` — воркер получает до N задач одновременно. В BullMQ: нет встроенного batch, но можно группировать через flow или вручную.

**BLPOP**  
Блокирующая Redis команда: ждёт появления элемента в LIST. BullMQ использует для получения задач из `waiting` списка без polling. Требует `maxRetriesPerRequest: null` в ioredis — иначе команда прерывается по таймауту retry.

**BullMQ**  
Node.js библиотека очередей задач на основе Redis. Версия 5.71.0 (март 2026). Поддерживает: приоритеты, delay, cron, FlowProducer (DAG), rate limiting, OpenTelemetry. Работает в режиме at-least-once.

**Bull Board**  
Web UI для мониторинга BullMQ очередей. npm: `@bull-board/express` (6.x). Отображает состояния задач, прогресс, ошибки, возможность retry/удаления. Обязательно защищать от публичного доступа.

---

## C

**concurrency**  
Число параллельно выполняемых задач в одном Worker экземпляре. Для CPU-bound задач: `os.cpus().length`. Для IO-bound задач: 20–50. Для внешних API с rate limit: 1–2. Независим от числа запущенных Worker процессов.

**completed**  
Состояние задачи BullMQ: processor вернул результат без исключения. Хранится в ZSET `bull:{name}:completed`. Автоматически очищается по `removeOnComplete: { count: N }` или `{ age: seconds }`.

---

## D

**DAG (Directed Acyclic Graph)**  
Направленный ациклический граф зависимостей задач. В BullMQ реализуется через FlowProducer: дочерние задачи выполняются параллельно, родительская ждёт завершения всех. Без циклов — задача не может зависеть от своего потомка.

**dead letter queue (DLQ)**  
Очередь для задач исчерпавших все попытки retry. BullMQ не имеет встроенного DLQ — реализуется через `worker.on('failed')` с проверкой `attemptsMade >= attempts`. Используется для анализа системных сбоев и ручного replay.

**delayed**  
Состояние задачи BullMQ: задача добавлена с `delay` или `cron` и ждёт наступления времени обработки. Хранится в ZSET sorted by `processAt` timestamp. Переходит в `waiting` когда время наступило.

---

## E

**enableReadyCheck**  
Опция ioredis: `false` — не ждать команды `READY` от Redis при соединении. Рекомендовано для BullMQ: ускоряет reconnect при временной недоступности Redis.

**exactly-once**  
Гарантия доставки: задача выполнится ровно один раз. Требует транзакционной атомарности между созданием задачи и бизнес-операцией. Реализуется через pg-boss с `{ tx: client }`. Redis-based очереди не поддерживают exactly-once нативно.

**expireInSeconds**  
Параметр pg-boss: через сколько секунд активная задача считается stalled (воркер не отвечает). По истечении задача возвращается в очередь для повторной попытки. Аналог `lockDuration` в BullMQ.

**extendLock**  
Метод `job.extendLock(duration)` в BullMQ: продлевает lock активной задачи. Обязателен для задач выполняющихся дольше `lockDuration`. Вызывать с периодичностью `lockDuration / 2` или после каждого значимого шага.

---

## F

**failed**  
Состояние задачи BullMQ: processor выбросил исключение и `attemptsMade >= attempts`. Хранится в ZSET `bull:{name}:failed`. Можно вручную retry через Bull Board или API. Очищается по `removeOnFail`.

**FlowProducer**  
BullMQ класс для создания DAG-пайплайнов. `flowProducer.add()` принимает дерево задач: родительская задача переходит в `waiting` только когда все `children` завершены. Children могут быть в разных очередях.

---

## G

**graceful shutdown**  
Корректное завершение процесса: дать воркерам закончить текущие задачи, затем закрыть соединения. В BullMQ: `worker.close()` ждёт завершения активных задач. Без graceful shutdown — активные задачи становятся stalled и перезапускаются.

---

## I

**idempotent processor**  
Processor который можно выполнить несколько раз с одними данными без побочных эффектов. Обязателен при at-least-once семантике: при retry одна и та же задача выполняется повторно. Техника: проверять `documentId` в БД перед обработкой, использовать `jobId` как идемпотентный ключ.

**ioredis**  
Node.js Redis клиент. Версия 5.x (март 2026). Используется BullMQ как транспорт. Критичные опции для BullMQ: `maxRetriesPerRequest: null`, `enableReadyCheck: false`.

---

## J

**jobId**  
Уникальный идентификатор задачи в BullMQ. Автогенерируется как UUID если не указан явно. При явном `jobId: 'my-id'` — повторный `queue.add()` с тем же `jobId` игнорируется (дедупликация). Использовать `documentId` как `jobId` для предотвращения дублей.

---

## L

**limiter**  
Параметр BullMQ Worker: глобальный rate limit через Redis. `{ max: 60, duration: 60000 }` = не более 60 задач в минуту. Применяется ко всем Worker экземплярам суммарно — Redis-координированный.

**lockDuration**  
Время жизни lock активной задачи в BullMQ (мс). Если Worker не продлевает lock в течение этого времени — задача помечается как stalled. Должен быть больше максимального ожидаемого времени выполнения задачи.

**lockRenewTime**  
Частота автоматического продления lock в BullMQ. Рекомендуется `lockDuration / 2`. При `lockDuration: 30000` → `lockRenewTime: 15000` — lock продляется каждые 15s.

---

## M

**maxRetriesPerRequest**  
Опция ioredis: максимальное число retry для одной Redis команды. Дефолт: 20. Для BullMQ — обязательно `null` (без лимита). BullMQ использует блокирующие команды которые могут ждать долго — ioredis retry должен быть отключён.

---

## P

**pg-boss**  
Node.js библиотека очередей задач на основе PostgreSQL. Версия 12.8.0 (март 2026). Использует `SKIP LOCKED` для конкурентного получения задач. Поддерживает transactional enqueue через `{ tx: client }`. Не требует отдельной инфраструктуры если PostgreSQL уже используется.

**pollingIntervalSeconds**  
Параметр pg-boss Worker: как часто опрашивать таблицу задач. Дефолт: 2 секунды. PostgreSQL не имеет push-нотификаций для задач как Redis → pg-boss использует polling.

**priority**  
Числовой приоритет задачи в BullMQ. Меньшее число = выше приоритет. `priority: 1` обрабатывается раньше `priority: 10`. Хранится через ZSET score в `waiting` структуре. Задачи без приоритета обрабатываются FIFO.

---

## Q

**Queue**  
BullMQ класс для добавления задач. Создаёт соединение к Redis. Методы: `add()`, `addBulk()`, `getWaitingCount()`, `getActiveCount()`, `pause()`, `resume()`, `close()`. Один экземпляр Queue — одно Redis соединение для публикации.

**QueueEvents**  
BullMQ класс для подписки на события очереди (completed, failed, progress). Создаёт отдельное Redis соединение для pub/sub. Используется в `job.waitUntilFinished()` и для внешнего мониторинга.

---

## R

**removeOnComplete**  
Опция BullMQ задачи: автоматически удалять из Redis после завершения. Форматы: `true` (удалить сразу), `{ count: N }` (хранить последние N), `{ age: seconds }` (хранить N секунд). Без этой опции — completed задачи накапливаются в Redis бесконечно.

**removeOnFail**  
Опция BullMQ задачи: автоматически удалять из Redis после финального сбоя. Аналог `removeOnComplete`. Для DLQ паттерна — `removeOnFail: false` или `{ count: N }` большой.

**replay**  
Повторный запуск задачи из DLQ. Паттерн: создать новую задачу с теми же данными что и упавшая, удалить из DLQ. Возможен через Bull Board UI или программно.

**retry**  
Повторное выполнение задачи после сбоя. Количество: `attempts - 1`. Каждый retry инкрементирует `job.attemptsMade`. Задержка между retry определяется `backoff` конфигурацией.

---

## S

**schedule**  
pg-boss метод для Cron задач: `boss.schedule('name', '0 9 * * *', data)`. Хранит расписание в `pgboss.schedule` таблице. BullMQ аналог: `queue.add('name', data, { repeat: { pattern: '0 9 * * *' } })`.

**SIGTERM**  
Unix сигнал запрашивающий корректное завершение процесса. Kubernetes и Docker посылают SIGTERM перед остановкой контейнера. Обработчик должен вызывать `worker.close()` / `boss.stop()` и завершать процесс после очистки.

**SKIP LOCKED**  
PostgreSQL расширение для `SELECT ... FOR UPDATE SKIP LOCKED`. Позволяет нескольким воркерам конкурентно брать задачи из таблицы без блокировки друг друга. Основной механизм pg-boss для параллельной обработки.

**stalled**  
Состояние задачи BullMQ: задача была `active` но воркер не продлил lock в течение `lockDuration`. Причины: воркер упал, deadlock, infinite loop. BullMQ автоматически возвращает stalled задачи в `waiting` для повторной обработки.

**stalledInterval**  
Частота проверки stalled задач в BullMQ (мс). Дефолт: 30000. BullMQ периодически сканирует `active` список и возвращает просроченные задачи в `waiting`.

---

## T

**teamSize**  
Параметр pg-boss Work: число параллельных обработчиков внутри одного `boss.work()` вызова. Аналог `concurrency` в BullMQ.

**teamRefill**  
Параметр pg-boss Work: немедленно запрашивать новые задачи после завершения текущих. Без `teamRefill: true` — воркер ждёт следующего `pollingIntervalSeconds` после освобождения слота.

**tx (pg-boss option)**  
Параметр `boss.send(name, data, { tx: pgClient })`: выполнить INSERT задачи в контексте переданной pg транзакции. Если транзакция откатится — задача тоже откатится. Единственный способ достичь exactly-once семантики.

---

## U

**UnrecoverableError**  
BullMQ класс: выбрасывается в processor когда retry бессмысленны. Задача немедленно переходит в `failed` без дополнительных попыток. Применение: внешний сервис недоступен навсегда, данные задачи невалидны, ресурс удалён.

---

## W

**waiting**  
Начальное состояние задачи BullMQ после `queue.add()`. Хранится в LIST `bull:{name}:waiting` (FIFO) или ZSET (при использовании priority). Worker берёт задачи из `waiting` через BLPOP.

**waiting-children**  
Состояние родительской задачи FlowProducer: ждёт завершения всех дочерних задач. Переходит в `waiting` когда последний child завершился. Остаётся в `waiting-children` навсегда если child исчерпал попытки — критическая метрика для мониторинга.

**waitUntilFinished**  
Метод `job.waitUntilFinished(queueEvents, timeoutMs)`: блокирует до получения `completed` или `failed` события. Реализует request-reply паттерн поверх очереди. Не использовать для задач с длительным временем обработки в синхронных HTTP endpoint.

**Worker**  
BullMQ класс для обработки задач. Создаёт отдельное Redis соединение. Параметры: `concurrency`, `limiter`, `lockDuration`, `stalledInterval`. Один процесс может содержать несколько Worker экземпляров для разных очередей.
