## Философия курса

Мир изменился. AI-кодеры пишут код быстрее любого человека.  
Но они не умеют **думать системами**, **выбирать архитектуру** и **принимать решения в условиях неопределённости**.

Этот курс создаётся через **диалог автора с моделью**: автор провоцирует на глубину, получает знания, верифицирует их собственным опытом — так рождается содержание. Поэтому:

- Давай глубину, граничные случаи и архитектурные антипаттерны — не базовые объяснения
- Указывай, где наивный подход ломается — это ценнее, чем happy path
- При неясности — один конкретный вопрос, не заполнять пробелы самостоятельно

## Правило актуальности — ОБЯЗАТЕЛЬНО

Устаревшие данные разрушают доверие к курсу целиком.

**Перед каждым модулем** — поиск актуальных версий всего что упоминается. Никаких версий из головы. Актуальный стек и топ open-source моделей — в `README.md` проекта (раздел «Актуальный стек»). Использовать как отправную точку, затем проверять.

**Устаревшие модели запрещены** во всех контекстах, кроме раздела «Актуальные версии» модуля. Критерий: модель старше ~6 месяцев без активной поддержки, либо вышло следующее поколение от того же вендора.

## Структура модуля

Каждый модуль = `README.md` + `GLOSSARY.md`. Один день изучения.

### README.md — разделы по порядку:

1. `# Модуль NN — Название`
2. Blockquote: `> **Для AI-архитектора:** ...` / `> Один день изучения — ...`
3. Содержание — нумерованный список якорей
4. `## Актуальные версии` — таблица с датой
5. Тематические разделы
6. `## Реальный кейс` — входные данные → гипотеза → результат → вывод, противоречащий интуиции. Только реальный опыт автора. Нет данных — запросить, не придумывать. *(AI/ML — обязательно; остальные — по наличию опыта)*
7. `## Антипаттерны` — решения, которые кажутся правильными, но являются ошибкой. *(AI/ML — обязательно; остальные — по ситуации)*
8. `## Anti-checklist ☠️` — 5–7 пунктов «что НЕ делать» в формате `- [ ] ... — почему`. Только если есть что сказать, не для галочки.
9. `## Задачи AI-кодеру`
10. `## Чеклист архитектора` — `- [ ]` по категориям

### Структура тематического раздела:

```
## N. Название

### Подраздел
[механика]
[код если нужен]
**Практический вывод для архитектора:** [конкретно]

### Граничные случаи — где ломается
[кейсы с кодом]
**Почему это важно архитектору:** [последствие]
```

Конец модуля:

```
---
*Модуль NN завершён.*
*Следующий: [Модуль NN+1 — Название](../NN+1-папка/README.md)*
```

## Форматирование

- `#` — только заголовок модуля; `##` — разделы; `###` — подразделы
- `---` между крупными блоками
- Код всегда с языком: ````javascript`, ````bash`, ````typescript`
- Mermaid для ключевых схем: ````mermaid` (process flows, architecture, timelines)
- ASCII-диаграммы — plaintext без языка (для простых схем)
- Комментарии в коде на русском; `// ✅` / `// ❌` для паттернов
- Таблицы с `:--` выравниванием

### Задачи AI-кодеру — формат:

```
Плохая формулировка: > «...»
Хорошая формулировка: > «...»
Формула: что делает + ограничения + конкретные API + версия платформы
```

## Стиль

Тон: технический, прямой, коллеге-архитектору.

**Запрещено:** «Введение в...», «для начинающих», «это важно», «обратите внимание», «не забудьте», hello world примеры, синтаксис без архитектурного контекста, модели вне раздела «Актуальные версии».

**Обязательно:** реальный контекст, actionable выводы, специфичные граничные случаи, развилка джун vs архитектор.

Объём `###`: 150–400 слов не считая код. Объём README.md: ~800–1200 строк.

## Как работать

- «Обсудим модуль X» → предложить угол подачи и ключевые разделы, дождаться подтверждения — только потом писать
- «Напиши модуль X» → полный README.md + GLOSSARY.md по структуре выше
- «Добавь раздел Y» → в правильное место, соблюдая нумерацию и стиль
- «Отредактируй» → сохранять стиль, не переписывать структуру
- Неясность → один конкретный вопрос, не заполнять пробелы самостоятельно
