## Пример: ADR-001 — Cascade Filter для batch extraction

```markdown
# ADR-001: Cascade Filter (SLM gate) для batch extraction

## Статус

Принято

## Контекст

- Pipeline обрабатывает 2000–3000 изображений товаров из Telegram
- Большинство изображений не содержит цен — их обрабатывать не нужно
- Железо: GTX 1660 6 ГБ, Ryzen 5 3600
- Облачный VLM вызов: ~$0.01/image, latency ~3-5s
- Локальный SLM вызов: ~$0 (electricity), latency ~1-2s

## Рассмотренные варианты

### Вариант A: Всё через облачную VLM

**Описание:** Каждое изображение отправляется в cloud VLM для extraction.

**Плюсы:** Простота, один pipeline
**Минусы:** $20-30/day на 2000 изображений, 50% тратится на изображения без цен

**Ссылка на модуль:** [Модуль 11 — Multi-model Orchestration](../11-multi-model-orchestration/README.md#4-cascade-filter)

### Вариант B: Cascade Filter (SLM gate + cloud VLM)

**Описание:** SLM 0.8B локально детектирует наличие цены, только прошедшие gate идут в cloud VLM.

**Плюсы:** Экономия 70% cost, gate latency ~1s
**Минусы:** Recall gate не 100% — риск false negative, сложнее pipeline

**Ссылка на модуль:** [Модуль 11 — Cascade Filter](../11-multi-model-orchestration/README.md#4-cascade-filter)

## Решение

Выбран: **Вариант B (Cascade Filter)**

**Обоснование:**
1. Gate recall 0.95 на тестовой выборке 500 изображений
2. Pass rate ~30% — только 600/2000 идут в cloud
3. Экономия: (2000 × $0.01) vs (600 × $0.01 + overhead) = $20 vs $6 = −70%
4. False negative rate 5% приемлем для данного бизнес-кейса (не юридические данные)

**Ключевой trade-off:** 5% потеря данных против 70% экономии cost

## Последствия

**Что изменилось:**
- Добавлен Gate VLM pipeline перед Main VLM
- Добавлен компонент оптимизации изображений (Sharp resize 1000px WebP)

**Новые ограничения:**
- Gate и Main не могут работать параллельно на одной GPU
- Нужен мониторинг pass rate и false negative rate

**Что стало проще:**
- Cost pipeline стал предсказуемым: $180/мес вместо $600

**Что стало сложнее:**
- Два pipeline вместо одного
- Нужен evaluator для gate качества

## Связанные решения

- [Модуль 11 — Cascade Filter](../11-multi-model-orchestration/README.md)
- [Модуль 08 — Local Inference](../08-local-inference/README.md) — выбор модели
```

## Пример: ADR-002 — BullMQ vs pg-boss для очереди

```markdown
# ADR-002: Выбор очереди задач

## Статус

Принято

## Контекст

- Postgres уже есть в стеке, Redis — нет
- Throughput: ~1000 задач/день (batch processing документов)
- Важна exactly-once гарантия (financial data)
- Нужен DAG-пайплайн (обработка → extraction → summarization)

## Рассмотренные варианты

### Вариант A: BullMQ + Redis

**Описание:** BullMQ 5.x + Redis 7.x

**Плюсы:** DAG (FlowProducer), высокая производительность, Bull Board UI
**Минусы:** Нужен Redis → ещё один сервис, at-least-once гарантия

**Ссылка на модуль:** [Модуль 18 — Task Queues](../18-task-queues/README.md#2-bullmq-архитектура-и-lifecycle-задачи)

### Вариант B: pg-boss

**Описание:** pg-boss 12.x на существующем Postgres

**Плюсы:** Zero дополнительной инфраструктуры, exactly-once, транзакционный enqueue
**Минусы:** Нет нативного DAG, ниже throughput (~1-5K job/s)

**Ссылка на модуль:** [Модуль 18 — Task Queues](../18-task-queues/README.md#7-pg-boss-очередь-без-redis)

## Решение

Выбран: **Вариант B (pg-boss)**

**Обоснование:**
- Redis не было — добавлять ради очереди неоправданно
- Exactly-once важнее DAG для финансовых документов
- 1000 задач/день << 5000 задач/с порога pg-boss

**Ключевой trade-off:** DAG (FlowProducer) придётся реализовать вручную

## Последствия

**Что изменилось:**
- Вместо Redis — схема pgboss в существующем Postgres
- DAG pipeline реализован через ручное управление статусами (parent_job_id)

**Новые ограничения:**
- Нет Bull Board — мониторинг через SQL запросы
- Нужен polling interval для worker

## Связанные решения

- [Модуль 18 — Task Queues](../18-task-queues/README.md#7-pg-boss-очередь-без-redis)
- [Модуль 12 — RAG](../12-rag/README.md) — чанкинг (кэш для pgvector)
```

## Рекомендации по использованию

1. **Когда писать ADR:** перед реализацией архитектурно значимого решения (выбор БД, очереди, стратегии кэширования, паттерна оркестрации)
2. **Куда сохранять:** `docs/adr/NNN-title.md` в репозитории проекта
3. **Связь с курсом:** в каждом ADR указывать ссылку на модуль курса, где разбирается технология
4. **Жизненный цикл:** статус меняется от «Предложено» → «Принято» → может быть «Заменено ADR-NNN» при изменении решения
