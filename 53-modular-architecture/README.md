## 1. Где проходит граница модуля

Модуль — это единица, внутри которой изменение не требует правок снаружи. Не папка и не «компонент архитектуры», а наименьшая единица, у которой есть **свой API, своё состояние и своя причина меняться**.

Три признака, что граница настоящая:

1. **API модуля меньше, чем его реализация.** Модуль прячет детали за маленькой поверхностью. Если публичный API растёт вместе с числом внутренних классов — границы нет.
2. **Внутри модуля не нужно знать про соседей.** Из `billing` не вызывается `http` напрямую, а приходит вызов извне. Иначе при смене HTTP-фреймворка меняется `billing`.
3. **Модуль можно заменить, не переписывая его пользователей.** Не «переименовать папку», а подставить другую реализацию за тем же контрактом. Это и есть проверка границы.

```text
❌ Не граница:              ✅ Граница:
src/                        src/modules/
  controllers/               parsing/    ← свой API, своё состояние
  services/                   contract/
  repositories/            core/
  models/                   http/       ← реализация, никто не импортируется
  utils/                    cli/
```

**Практический вывод для архитектора:** вопрос «какие папки создать» — неправильный. Правильный вопрос: «какие вещи в этом проекте меняются вместе». Папки — следствие ответа.

## 2. Виды связности

Связность (coupling) — не одно свойство, а пять разных. Разделение важно: они ломаются по-разному и лечатся по-разному.

| Вид | Что связывает | Чем рвётся | Цена разрыва |
|:--|:--|:--|:--|
| **Temporal** | «Сначала A, потом B» | очередью, событием, outbox | высокая, но честная — порядок виден |
| **Spatial** | «A и B лежат рядом, значит связаны» | границей модуля | низкая, это дефект по умолчанию |
| **Data** | «Знание о структуре чужой таблицы» | DTO, anti-corruption layer | средняя, всегда нужно явно |
| **Semantic** | «Оба знают, что такое счёт-фактура» | общим языком домена, контекстом | очень высокая, это DDD-уровень |
| **Deployment** | «Оба деплоятся вместе» | раздельным жизненным циклом | высокая, но только если нужна |

### Temporal coupling — «сначала, потом»

Самый вредный вид, потому что невидим. `save()` пишет в две таблицы, потом шлёт в очередь, потом обновляет кэш. Никто не может использовать `save()` частично — порядок зашит в тело функции.

Разрыв — outbox-таблица в той же транзакции, что и запись (модуль 18):

```sql
-- порядок фиксируется транзакцией, а не соглашением в коде
BEGIN;
  INSERT INTO cases (...) VALUES (...);
  INSERT INTO outbox (topic, payload) VALUES ('case.created', $json);
COMMIT;
-- дальше отдельный процесс читает outbox — может lagging, может повторить
```

**Граничные случаи — где ломается:**

**Порядок как неявное знание переживает рефакторинг.** Три вызова в функции меняют местами при «улучшении читаемости» — поведение тихо меняется, тесты на моках этого не видят, потому что моки проверяют «вызвали», а не «в каком порядке».

**Разрыв temporal coupling стоит денег в согласованности.** Outbox даёт «в итоге», а не «вместе». Для кода, который читает сразу после записи, это неприемлемо — значит, outbox тут не подходит и разрывать temporal coupling нельзя. Честный ответ: «здесь порядок — часть контракта».

**Почему это важно архитектору:** temporal coupling маскируется под «простое требование». Оно всегда кажется бесплатным, пока первая параллельная запись не покажет, что половина сценариев теперь гоняется.

### Data coupling — знание о чужой структуре

Вопрос: откуда модуль знает, что в таблице `cases` есть поле `court_id` типа `bigint`? Если ответ «из общего слоя моделей» — data coupling сломан.

Разрыв — DTO на границе:

```typescript
// ❌ Внутренняя модель протекает наружу
export type CaseRow = { id: string; court_id: string; payload: Record<string, unknown> };

// ✅ Контракт модуля: только то, что гарантировано
export type CaseRef = {
  readonly id: string;
  readonly court: CourtRef;
};
```

### Spatial coupling — «лежат рядом, значит связаны»

Дефект, который появляется сам. Общий `utils/` собирает функции из всех модулей, и через неё возникает связность между модулями, которых никто не проектировал: `logging` → `utils/formatDate` → `domain/Period`.

Разрыв: `utils/` не существует. Общее либо попадает в конкретный модуль (потому что первым понадобилось там), либо сознательно становится библиотекой с контрактом и тестами.

**Почему это важно архитектору:** циклы импортов — не «неаккуратность», а диагноз. Цикл `A → B → A` означает, что границы между A и B не существует, и они должны быть одним модулем.

### Semantic coupling — «оба знают одно и то же слово»

Самый дорогой вид и самый плохо визуализируемый. Два модуля используют слово «клиент» в разном смысле: один — юридическое лицо, второй — плательщик по счёту. Формально связности нет, данных не делится, а дыра в понимании появляется при первой же сверке.

Разрыв — явный общий язык: одно определение, импорт в оба модуля, расхождение запрещено.

**Практический вывод для архитектора:** перед проектированием границ составь словарь: какие термины используются, кем и в каком смысле. Термины с двумя смыслами — это и есть будущие инциденты на границе. Это же вход для bounded context (модуль 55, когда появится).

## 3. Слои против вертикальных срезов

Слои — самая популярная и самая частая ошибка организации кода. Проблема не в том, что слои «плохие», а в том, что они **растут вместе**: изменение одной фичи требует правки в четырёх слоях, и эти четыре правки невозможно сделать атомарно в одном коммите без «полусломанного» состояния в промежутке.

```text
❌ Слои — фича разрезана на 4 несвязных части:

src/
  controllers/caseController.ts      ← знает про HTTP
  services/caseService.ts            ← знает про все слои
  repositories/caseRepository.ts    ← знает про SQL
  models/case.ts                     ← знает про всё

  + кросс-модульные импорты:
    services/caseService.ts → services/paymentService.ts → repositories/caseRepository.ts
    (billing знает про SQL cases, domain знает про billing)

✅ Срезы — каждая фича целиком:

src/modules/parsing/     ← API модуля + реализация + тесты
src/modules/contract/
src/modules/core/
src/modules/http/        ← единственное место с HTTP
src/modules/cli/
```

Разница видна на конкретном изменении: «запросить сверку с судом» в слоях — это новый метод в `caseController`, `caseService`, `caseRepository`, плюс правка DI. В срезе — одна папка и её публичный `index.ts`, который меняется один раз.

```typescript
// src/modules/contract/index.ts — единственная точка входа в модуль.
// Внутренние файлы напрямую не импортируются (правило ниже).
export { createContract } from './create.js';
export type { ContractDraft } from './types.js';
```

**Граничные случаи — где ломается:**

**Частичная фича в слоях даёт несобираемый main.** Переименовал метод в `repositories`, забыл в одном из трёх мест в `services`. CI красный — это ещё не беда. Беда — когда в проде это доехало до merge в обход проверки.

**«Мы переименуем папку, зато будет чисто»** — рефакторинг без изменения поведения всё равно тащит за собой весь импорт-граф. Срезы рефакторятся локально: папка модуля переехала, внешние импорты не тронуты.

**Общий `models/` — скрытый срез.** Это хуже, чем явные слои: папка называется нейтрально, но через неё связаны все модули. Правило: у каждой сущности есть **один** владеющий модуль; остальные берут её оттуда по импорту.

**Почему это важно архитектору:** слои и срезы дают одинаковый результат на демо и радикально разный на шестом месяце. Решение принимается один раз и стоит потом каждый день.

**Практический вывод для архитектора:** режь по вариации, а не по технической роли. Новый вид отчёта — это новый срез, а не новый слой.

## 4. Глубокие модули

Критерий из Ousterhout, который работает и для слоёв, и для срезов: **сложность модуля должна быть пропорциональна его полезности, а не его размеру**.

Глубокий модуль: сложность спрятана за маленьким API. `pg` за 80 строками прячет пул, таймауты, ретраи и формат ошибок. Поверхность API — десять методов.

Мелкий модуль: сложность торчит наружу. API — тридцать методов, и вызывающий обязан знать правильный порядок.

```text
❌ Мелкий (высокий API, утечка внутреннего):
   SqlCaseStore.insert()
   SqlCaseStore.insertAndInvalidateCache()
   SqlCaseStore.insertRaw()
   buildInsertSql()
   SqlCaseStore.tx(fn)

✅ Глубокий (маленький API, порядок скрыт):
   cases.save(draft)        ← внутри: транзакция, outbox, инвалидация
```

### Тест «убери меня из интерфейса»

Для каждого метода публичного API модуля: можно ли его убрать, не сломав использование? Если метод существует только потому, что его вызывает один-единственный сосед, у которого нет своей абстракции — метод не нужен, границу можно перерисовать.

```typescript
// ❌ Публичный интерфейс повторяет внутреннюю структуру
export interface CaseStore {
  selectById(id: string): Promise<CaseRow | null>;
  selectByCourt(courtId: string): Promise<CaseRow[]>;
  insertBatch(rows: CaseRow[]): Promise<void>;
  updateStatus(id: string, status: Status): Promise<void>;
}

// ✅ Интерфейс отражает намерение, не таблицу
export interface CaseStore {
  find(id: CaseId): Promise<Case | null>;
  listByCourt(court: CourtRef): Promise<readonly Case[]>;
  save(case: Case): Promise<void>;
}
```

Обрати внимание: `find` возвращает доменный `Case`, а не `CaseRow`. Иначе data coupling возвращается через заднюю дверь, и модуль больше не может сменить хранилище.

### Признаки мелкого модуля

- Число публичных экспортов больше, чем сущностей
- Вызывающий обязан знать внутренний порядок (`begin()` → `save()` → `commit()`)
- Наружу торчат типы хранилища (`*Row`, `*Record`)
- Изменение внутреннего способа хранения меняет вызывающий код
- Два вызывающих используют непересекающееся подмножество API — сигнал, что это два модуля

**Граничные случаи — где ломается:**

**«Глубокий модуль» как оправдание для бога.** Модуль на 4000 строк с API из трёх функций — это не глубокий, а непрозрачный. Разница в том, можно ли его понять по интерфейсу. Три функции, скрывающие четыре независимые подсистемы, — это четыре модуля с общим именем.

**Абстракция без второй реализации.** `CaseStore` с одним классом `SqlCaseStore` — не граница, а переименование. Граница появляется, когда реализация вторая или её можно написать, не переписывая остальное. Не «нужна ли абстракция», а «что её сломает».

**Почему это важно архитектору:** «прятать сложность» — девиз модуля, но не способ избежать её. Спрятанная сложность возвращается в момент, когда модуль меняют, а менять будут обязательно.

## 5. Композиционный корень

Место, где собирается граф объектов. Одна функция, явные зависимости, никакой магии.

```typescript
// src/main.ts — единственное место, где известны все конкретные классы
import { createApp } from './modules/http/app.js';
import { createParser } from './modules/parsing/index.js';
import { SqlCaseStore } from './modules/core/sql-store.js';
import { HttpCourtClient } from './modules/http/court-client.js';

export function main(env: NodeJS.ProcessEnv): void {
  const store = new SqlCaseStore(env.DATABASE_URL!);
  const courtClient = new HttpCourtClient(env.COURT_API_URL!, {
    timeoutMs: 10_000,
    retries: 2,
  });
  const parser = createParser({ courtClient });

  const app = createApp({ store, parser, courtClient });
  app.listen({ port: Number(env.PORT ?? 3000) });
}
```

Читается сверху вниз, дебажится без инструментов, ставится breakpoint в одной точке. Это и есть весь смысл: **зависимости объявлены, а не найдены**.

### Три способа и почему явный выигрывает

| Способ | Как выглядит | Цена |
|:--|:--|:--|
| **Явный корень** | `new` в одной функции | граф читается, зависимости видны |
| **Контейнер** | `container.get(CaseStore)` | рефлексия в рантайме, граф скрыт, дебаг — через фреймворк |
| **Ambient** | доступен из любого места по имени | неявная зависимость, тест требует подмены глобала |

```typescript
// ❌ Ambient: откуда взялся logger — не видно
export async function handleCase(id: string) {
  logger.info('start');          // откуда logger?
  const case = await store.find(id);  // откуда store?
  return case;
}
```

**Граничные случаи — где ломается:**

**Контейнер выигрывает, когда зависимостей 200 и они однотипные.** В TypedIoC-стиле без типов контейнер — это удобство. Но тогда нужны типизированные декораторы, и выигрыш уже не в контейнере, а в типах. Отсюда вывод: бери типы из TypeScript, а не рефлексию.

**Контейнер протухает при модульной структуре.** Кросс-модульные зависимости через контейнер не видны в графе импортов: модуль `billing` формально ни от кого не зависит, а на деле тянет `mailer` из корня. Границы, проверенные `dependency-cruiser`, такие зависимости пропускают — их нет в коде.

**Циклы в графе при явном корне видны сразу.** Если `A` требует `B`, а `B` требует `A` — конструктор не напишется. В контейнере это вылезет в рантайме как `Circular dependency detected` посреди запроса.

**Почему это важно архитектору:** корень — единственное место, где видно форму системы целиком. Если её не видно нигде, форма системы определена случаем: тем, кто какой файл первым открыл.

**Практический вывод для архитектора:** явная сборка в одной точке. Рефлексию добавляют, когда зависимостей больше, чем можно прочитать, — и это момент, когда стоит остановиться и пересмотреть структуру, а не добавлять фреймворк.

## 6. Functional core, imperative shell

Ядро без эффектов: чистые функции, принимают вход, возвращают результат. Оболочка — всё, что читает файлы, ходит в сеть и пишет в базу.

```typescript
// core: ни одного эффекта, тестируется без моков
export type QuoteInput = {
  readonly lineItems: readonly LineItem[];
  readonly vatRate: number;
};

export type Quote = {
  readonly lines: readonly PricedLine[];
  readonly totalNet: number;
  readonly vat: number;
  readonly totalGross: number;
};

export function calculateQuote(input: QuoteInput): Quote { /* ... */ }

// shell: единственное место, где есть эффекты
export async function quoteFromRequest(req: Request, deps: Deps): Promise<Quote> {
  const raw = await deps.http.readBody(req);
  const parsed = parseQuoteDraft(raw);            // тоже чисто
  return calculateQuote(parsed);                  // эффектов нет
}
```

Что это даёт:

- **Тесты без моков.** Домен покрывается вызовами с аргументами, без `vi.mock()`
- **Переезд между рантаймами.** Логика расчёта не знает, Node это или Go
- **Детерминированность.** Один и тот же вход — один и тот же выход, значит воспроизводимый баг

**Граничные случаи — где ломается:**

**«У нас и так функционально» — на уровне модуля, а не системы.** Внутри модуля чисто, но модуль делает `await db` в середине вычисления. Формально не функционально, и тесты всё равно требуют БД.

**Чистое ядро с эффектами в аргументах.** Функция принимает `db: Pool` и делает чистый расчёт — это не ядро, а ядро с хвостом. Эффект не должен проникать даже через аргумент, если он меняет результат в зависимости от мира.

**Дата и время — скрытый эффект.** `new Date()` внутри чистой функции делает её недетерминированной: тот же вход сегодня и завтра даёт разный результат, и это не воспроизводится. Дата передаётся аргументом.

**Почему это важно архитектору:** для AI-пайплайнов (модули 06–12) чистое ядро — ещё и способ проверить парсер без повторного вызова VLM. Дешёвый тест на чистой функции против дорогого прогона модели — разница в стоимости теста на два порядка.

## 7. Гексагональная архитектура без церемонии

Обычно гексагональную архитектуру продают как «слои вокруг домена» с папками `ports/`, `adapters/`, `application/`. Проблема не в идее, а в том, что папки появляются раньше второй реализации и живут вечно.

Минимальная форма, которая даёт пользу:

```typescript
// Порт объявляет потребитель, а не поставщик.
// Поставщик о порте ничего не знает.
src/modules/contract/contract-store.ts
  export interface ContractStore {
    save(c: Contract): Promise<void>;
    find(id: ContractId): Promise<Contract | null>;
  }

src/modules/core/sql-contract-store.ts
  export class SqlContractStore implements ContractStore { /* ... */ }
```

Правило: **интерфейс живёт в папке потребителя**, реализация — в папке владельца данных. Направление зависимостей инвертировано, и это проверяемо правилом линта.

Когда вводить порт:

| Ситуация | Вводить |
|:--|:--|
| Одна реализация, смена хранилилища не планировалась | нет — это лишний слой |
| Данные принадлежат другому модулю | да — иначе протечка его схемы |
| Нужно подменить в тесте, но подмена тривиальна | нет — достаточно функции-параметра |
| Планируется вторая реализация | нет, пока не появилась — но решение зафиксируй в ADR |
| Один из нескольких внешних поставщиков | да |

**Граничные случаи — где ломается:**

**Generic-репозиторий — антипаттерн, маскирующийся под порт.** `interface Repository<T> { find(id): T | null; save(t: T): void; }` не выражает ничьих намерений и заставляет каждый модуль работать с чужой сущностью: `Repository<Contract>` означает, что `contract` знает про `Contract`, но не знает, как его найти. Смысл порта — в методе `listByCounterparty()`, которого у `Repository<T>` быть не может.

**`any` вместо интерфейса — та же болезнь в другой обёртке.** `store: any` проходит ту же проверку типов и даёт ноль пользы.

**Порт, который знает про свою реализацию.** `interface SqlLikeStore { query(sql: string): void }` — не порт, а утечка SQL в интерфейс.

**Почему это важно архитектору:** главная польза инверсии зависимостей — не «тестируемость» (её даёт и подстановка функции), а **направление изменений**. Если модуль объявил, что ему нужно, а не «куда он пишет», замена хранилилища не трогает его тело.

## 8. Anti-corruption layer на границе с чужой системой

Слой, который переводит чужую модель в свою и не пускает дальше. Нужен везде, где есть внешняя система: 1С, Битрикс, платёжка, ФНС, чужой API.

```typescript
// ❌ Чужая модель в домене
export type Case = {
  id: string;
  court_id: string;            // именование и тип из 1С
  courtName: string;           // дублирование, которое разъедется
  status: 'new' | 'in_work' | 'done';  // enum чужой системы
};

// ✅ Своя модель + адаптер на границе
export type Case = {
  readonly id: CaseId;
  readonly court: CourtRef;
  readonly stage: CaseStage;   // 'new' | 'review' | 'ready'
};

export function caseFrom1C(raw: OneCCaseResponse): Case {
  return {
    id: asCaseId(raw.ID),
    court: { id: asCourtId(raw.CourtID), name: raw.CourtName.trim() },
    stage: STAGE_MAP[raw.Status] ?? 'new',
  };
}
```

Что обязательно в адаптере:

1. **Сырой ответ сохраняется целиком.** Парсинг может быть неверным, а поддержка нужна через полгода. Логировать только распарсенное — значит нечем чинить.
2. **Неизвестное значение не роняет систему.** Новый статус в 1С не должен ронять импорт всего.
3. **Нормализация на границе.** Таймзона, формат даты, пустая строка против `null` — всё приводится здесь, дальше домен работает в своих типах.
4. **Кэш сырого ответа.** Граница — единственное место, где ответ меняется без нашего участия, и одновременно самое дорогое место вызова.

**Граничные случаи — где ломается:**

**«Адаптер вырождается в pass-through и удаляется.»** Первый месяц он ничего не добавляет, потому что чужая система удобна. Потом неудобна — и чинить надо уже всё, потому что её форма разошлась по домену.

**Enum-изоляция дороже, чем кажется.** Второй статус значит вторую ветку в `STAGE_MAP`, третьего — вторую функцию перевода. Это осознанная плата за то, что смена модели поставщика не станет аварией.

**Почему это важно архитектору:** заказчик всегда скажет «это же просто справочник». Просто справочник превращается в 40 полей, половина из которых приходит `null` у клиента, у которого другая версия конфигурации.

## 9. Монолит или микросервисы

Решение организации, а не кода. Критерии — по числу, а не по вкусу.

| Критерий | Значение | Порог |
|:--|:--|:--|
| Команды с разными зонами владения | независимый релиз спасает от координации | 5+ команд |
| Изменение одного модуля ломает деплой другого | цена координации растёт с размером репозитория | в вики команды |
| Язык/рантайм сильно различаются | единый репозиторий начинает мешать | 2+ языка |
| Нагрузка одного модуля отличается на порядок | масштабируется отдельно дешёво | 100× по ресурсам |
| Отдельный жизненный цикл релизов | нужно деплоить независимо и часто | разные команды |

Пока хоть один пункт не выполнен — микросервисы меняют code complexity на operational complexity без выигрыша. При этом операционная часть (деплой, наблюдаемость, версии, on-call) стоит дорого и не уходит при «правильной архитектуре».

### Промежуточная ступень — модульный монолит

Модуль в отдельном процессе, но в одном репозитории и общем деплое. Даёт независимость кода без операционной цены. Модуль 51 разбирает такой вариант на реальном API для 1С: сети внутри ядра нет, доменные операции атомарны одной транзакцией, сетевые вызовы живут только на границах.

### Что микросервисы действительно решают

- **Независимый деплой** по расписанию команд, а не по решению одного релизного инженера
- **Изоляция ресурсов**: один модуль не может исчерпать пул всего процесса
- **Изоляция отказов** в границах, которые и так проходят по границам домена
- **Организация**: команда владеет своим деплоем, чужой чужое не ломает

Чего они **не** решают: сложность кода, производительность, надёжность. Все три микросервисы обычно ухудшают.

**Граничные случаи — где ломается:**

**«Сервисы — это про масштабирование.»** Масштабируется узкое место, а не всё приложение. Один воркер с блокирующим CPU (модули 04, 22) выносится в воркер или отдельный сервис — это не микросервис, это очередь.

**«Разделим по таблицам БД.»** Таблица — не граница бизнеса. Половина запросов пересекает несколько таких «сервисов», и каждая половина едет по сети в последовательную транзакцию, которая всё равно не атомарна.

**Сетевой вызов внутри доменной операции.** Пока в модуле есть вызов соседнего сервиса, он не может быть в своей транзакции. Внутри ядра — только локальные вызовы, атомарность одна.

**Почему это важно архитектору:** прежде чем дробить, посчитай, сколько раз в неделю два модуля релизились вместе. Если ответ «каждый день» — дробить рано, деплой перестанет быть событием.

**Практический вывод для архитектора:** сначала границы в коде и проверка их линтом, потом процессы. Границы, которые держатся только на честном слове команды, разъедутся за месяц.

## 10. Границы под наблюдением

Договорённость о границах без проверки — это пожелание. Три уровня контроля, от дешёвого к дорогому.

**Уровень 1 — циклы. Самое дешёвое и ловит больше всего.**

```bash
npx madge --circular --extensions ts src/
# Circular dependency: src/modules/core/a.ts -> src/modules/core/b.ts -> a.ts
```

Ноль конфига, ноль зависимостей, работает на первом же запуске.

**Уровень 2 — карта зависимостей и правила.** `dependency-cruiser` (18.5.0) строит граф и проверяет собственные правила: циклы, orphans, зависимости, которых нет в `package.json`, production-код, тянущий `devDependencies`.

```javascript
// .dependency-cruiser.cjs
module.exports = {
  forbidden: [
    // Внутренние модули не импортируют чужие внутренние файлы
    { name: 'no-deep-imports', from: { path: '^src/modules/[^/]+/' },
      to: { path: '^src/modules/', pathNot: '^src/modules/[^/]+/index\\.ts$' } },
    // Слои: только http знает про http, только cli — про argv
    { name: 'http-only-in-http', from: { pathNot: '^src/modules/http/' },
      to: { path: '^node_modules/(express|undici)/' } },
    { name: 'no-orphans', from: { orphan: true }, to: {} },
  ],
  options: {
    doNotFollow: { path: 'node_modules' },
    tsPreCompilationDeps: true,
    tsConfig: { fileName: 'tsconfig.json' },
  },
};
```

```bash
npx depcruise --validate src/
npx depcruise src --include-only "^src" --output-type dot | dot -T svg > deps.svg
```

**Уровень 3 — правила границ в линте.** `eslint-plugin-boundaries` (7.2.0) описывает элементы архитектуры и разрешённые зависимости между ними; нарушение видно в редакторе, до коммита.

```javascript
// eslint.config.js (flat config, ESLint 10)
import boundaries from 'eslint-plugin-boundaries';

export default [
  {
    plugins: { boundaries },
    settings: {
      'boundaries/elements': [
        { type: 'module', pattern: 'src/modules/*' },
        { type: 'entry',   pattern: 'src/{main,cli}.ts' },
      ],
      'boundaries/files': [
        { pattern: '**/*.test.ts', category: 'test' },
      ],
    },
    rules: {
      'boundaries/dependencies': [2, {
        default: 'disallow',
        policies: [
          // Модуль не знает про точку входа и про тесты
          { disallow: { to: [{ element: { type: 'entry' } },
                            { file: { categories: 'test' } }] } },
          // Внутренние файлы модуля видны только своему модулю
          { from: { element: { type: 'module' } },
            disallow: { to: { module: { path: '^src/modules/[^/]+/' } } } },
        ],
      }],
    },
  },
];
```

**Практический вывод для архитектора:** уровень 1 внедряется за пять минут и сразу показывает, есть ли границы вообще. Уровни 2–3 имеют смысл, когда уровень 1 чист — иначе сначала чини структуру, потом настраивай правила.

## 11. Реальный кейс

### Контекст

API-сервис CourtDesk (модули 51, 47, 49) отдаёт наружу 26 REST-эндпоинтов в формате, который понимает 1С. Первые месяцы исходная структура выглядела привычно: контроллеры, сервисы, репозитории, общий слой моделей. Наружу торчали DTO, названные по именам таблиц, а модуль сбора данных знал, что в таблице `cases` поле `court_id` — строка.

### Симптом

Изменение требования «показывать карточку дела по номеру жалобы» потребовало правки в шести файлах. Три из них — в модулях, которые к карточке дела отношения не имели: общий слой моделей, фабрика репозиториев, сборка зависимостей. Причина — `models/` был скрытым срезом, а spatial coupling через него связывал всё.

### Гипотеза

Разложить по вертикальным срезам: `parsing`, `contract`, `core`, `http`, `cli`. Данные каждого среза объявить его собственностью, наружу отдавать доменные типы, сборку перенести в один корень.

### Что получилось

- Карточка дела живёт в `modules/core` и не знает про HTTP. Эндпоинт `GET /cases/{id}` — тонкая обёртка.
- 1С-специфика (плоский ответ, поля по-английски, без вложенности) реализована в `modules/http` как отдельный сериализатор, а не в домене. При изменении формата 1С менялся один файл.
- Проверка циклов нашла 3 цикла, существовавших до перехода: все три шли через `utils/`. Папка `utils/` исчезла — её содержимое разошлось по владельцам, один файл стал отдельным модулем.
- Правило «внутренние файлы модуля не импортируются напрямую» через `dependency-cruiser` остановило возврат к глубоким импортам, который неизбежно вернулся бы в первой же задаче «быстро поправить».
- Внутренние сетевые вызовы в ядре остались: они оказались не внутренними, а границей с судом, и переехали в `modules/http`.

### Вывод, противоречащий интуиции

Ожидание было, что переход на срезы даст «чистую архитектуру» и ускорит разработку. Реальный эффект другой: **скорость разработки не изменилась, изменилась цена изменения**. Шесть файлов превратились в один, но только потому, что границы стали проверяемыми. До перехода те же шесть файлов были причиной того, что любое изменение требовало согласования с теми, кто их писал.

Второе наблюдение: `utils/` стоил дороже, чем весь слоистый пирог вокруг него. Ни один файл в ней не был «просто утилитой» — у каждого нашёлся владелец.

### Дополнение из практики: штаб-сессия как граница решения

Та же система столкнулась с тем, что решения о границах принимались в разных сессиях и не сходились: одна добавила порт для хранилища, другая — прямой импорт реализации, третья — общий хелпер «на всякий случай». Файловая передача задания и приёмка по diff'у (глава о штабе) сократили число расхождений: правило «не расширять API модуля без записи в приёмке» оказалось важнее любого правила о папках.

## 12. Антипаттерны

### «Слои: controllers / services / repositories»

Работает на демо, разъезжается всегда. Изменение фичи разрезано на четыре несвязных правки, которые невозможно сделать атомарно. Маскируется тем, что каждая папка выглядит осмысленно.

---

### «Generic-репозиторий»

`interface Repository<T> { find(id): T | null; save(t: T): void }` — не порт, а отказ от проектирования. Порт отвечает на вопрос потребителя (`listByCounterparty`), generic-репозиторий — на вопрос хранилища (`save`). Результат: у каждой сущности свой репозиторий, интерфейс у всех одинаковый и бесполезный, домен знает про то, как его сохраняют.

---

### `utils/` как свалка

Функция попадает в `utils/` в тот день, когда её понадобились двое. Через месяц её зовут из трёх модулей, и у неё нет владельца. Общее без владельца деградирует: правка под одно место ломает другое. Вместо `utils/` — два вопроса: это внутренняя часть модуля (вернуть туда) или это сознательная библиотека (контракт, тесты, версия).

---

### God-модуль с маленьким API

4000 строк за тремя экспортами — не глубокий модуль, а четыре независимые подсистемы с общим именем. Признак: чтобы понять модуль, приходится читать его целиком, а API не даёт подсказки. Делить по вариации: что меняется независимо — то и отдельный модуль.

---

### DI-контейнер с рефлексией по умолчанию

Скрывает граф зависимостей от `dependency-cruiser`, от дебаггера и от code review. В проекте на 200 зависимостей удобен — но только если зависимости однотипные. Если у каждой зависимости своя форма, экономия на `new` не окупает потерю видимости.

---

### «Общий слой моделей»

Нейтральное имя, скрытый срез. Сущность принадлежит ровно одному модулю; остальные берут её оттуда. Общий `models/` превращает любую правку сущности в правку всего приложения.

---

### Микросервисы «на будущее»

Меняют code complexity на operational complexity до того, как появилась организационная необходимость. Обратный переход дорог: общий деплой, версии, наблюдаемость, on-call — всё это придётся строить заново, уже с зависимостями, которых не было.

---

### Границы на словах

«Модуль не должен знать про соседей» в вики, без правила линта. Первая же задача с дедлайном нарушает её, и через месяц правило не работает. Граница без проверки — пожелание; проверка уровня 1 (циклы) стоит пяти минут.

---

### Порождённый интерфейс под одну реализацию

`IRepository` с единственным классом и тремя методами — не граница, а переименование. Если интерфейс невозможно нарушить (нечего подменять, нечего тестировать), он только добавляет файл. Порядок действий: сначала вторая реализация или вторая подстановка, потом интерфейс.

---

## Anti-checklist ☠️

- [ ] Структура по слоям (`controllers/services/repositories`) при трёх и более независимо меняющихся частях — правка фичи требует правок в несвязных местах
- [ ] Generic-репозиторий `Repository<T>` — интерфейс не отражает ничьих намерений, домен знает про способ хранения
- [ ] Папка `utils/`/`helpers` без владельца — общее без владельца деградирует при первой же правке под одно место
- [ ] Общий `models/`/`entities/` — скрытый срез, сущность принадлежит ровно одному модулю
- [ ] Зависимости через DI-контейнер или ambient-глобал — граф не виден ни линтеру, ни code review
- [ ] Публичный API модуля шире, чем его реализация сложна — модуль мелкий, сложность вынесена наружу
- [ ] Интерфейс, объявленный поставщиком, а не потребителем — направление зависимостей не инвертировано
- [ ] Порты и `adapters/` созданы до появления второй реализации — церемония без выигрыша
- [ ] Микросервисы при менее чем 5 командах с разными зонами владения — операционная цена без выигрыша
- [ ] Сетевой вызов внутри доменной операции — транзакция перестаёт быть атомарной
- [ ] Границы, зафиксированные только в вики — без `madge --circular` и правил линта разъедутся за месяц
- [ ] `new Date()` и чтение окружения внутри «чистого» домена — детерминизм потерян, воспроизвести баг нельзя

## Задачи AI-кодеру

Плохая формулировка:
> «Сделай архитектуру модульного приложения для обработки судебных дел, используя слоистую структуру и паттерн репозиторий.»

Разбор: не указаны границы, количество модулей, направление зависимостей. AI выдаст `controllers/services/repositories` с generic-репозиторием — то есть ровно то, что нужно было предотвратить. Требование «паттерн репозиторий» actively провоцирует антипаттерн из §12.

Хорошая формулировка:
> «Реализуй модуль `modules/contract` на TypeScript 7 (Node.js 24 LTS). Модуль владеет таблицей `contracts` (PostgreSQL 18) и экспортирует ровно `save(contract)`, `find(id)`, `listByCounterparty(counterpartyId)`. Другие модули не должны импортировать внутренние файлы модуля — только `modules/contract/index.ts`. Проверь правило через `dependency-cruiser` 18.5.0 в CI: глубокие импорты и циклы — ошибка. Хранилище вводи как класс `SqlContractStore` без интерфейса; вторая реализация не планируется. Дата и время передавай аргументом, `new Date()` внутри домена запрещён.»

Формула: что делает + ограничения + конкретные API + версия платформы + проверяемый критерий.

Вторая задача — на распознавание дефекта:
> «В проекте 40 модулей лежат в `src/modules/`, каждый импортирует `src/utils/format.ts` и `src/utils/logger.ts`. Назови три причины, по которым границы этих модулей не существует, и предложи минимальный набор проверок в CI, который это зафиксирует.»

Ожидаемый ответ: `utils` — скрытый срез; нет правила на глубокие импорты; нет проверки циклов; проверка — `madge --circular` плюс правило границ в `dependency-cruiser` или `eslint-plugin-boundaries`.

## Чеклист архитектора

### Границы
- [ ] У каждого модуля свой API, своё состояние и своя причина меняться
- [ ] API модуля меньше реализации; для каждого экспорта пройден тест «убери меня из интерфейса»
- [ ] Наружу торчат доменные типы, а не `*Row`/`*Record`
- [ ] Из модуля не вызываются чужие внутренние файлы — только публичные входы
- [ ] У каждой сущности ровно один владелец; общего `models/` нет
- [ ] `utils/`/`helpers/` нет; всё общее либо внутри модуля, либо библиотека с контрактом

### Связность
- [ ] Temporal coupling: порядок зафиксирован транзакцией или outbox, а не соглашением
- [ ] Data coupling: чужой схеме не известна ни одна внешняя структура
- [ ] Semantic coupling: термины с двумя смыслами выявлены и сведены к одному определению
- [ ] `dependency-cruiser` в CI: нет циклов, нет orphans, нет глубоких импортов

### Структура
- [ ] Срезы по вариации, а не слои по технической роли
- [ ] Композиционный корень один; зависимости объявлены, а не найдены рефлексией
- [ ] Functional core без эффектов; дата и время — аргументы
- [ ] Порты объявлены потребителем; портов нет под одну реализацию
- [ ] Anti-corruption layer на каждой внешней системе; сырой ответ сохраняется

### Монолит или микросервисы
- [ ] Каждый критерий дробления проверен числом, а не вкусом
- [ ] Нет сетевых вызовов внутри доменной операции
- [ ] Если сервисы есть — операционная часть (деплой, наблюдаемость, on-call) построена

### Связь с соседними модулями
- [ ] Идемпотентность на границе (модуль 51), resilience на той же границе (модуль 52)
- [ ] Схема и миграции принадлежат владельцу данных (модуль 49)
- [ ] Тесты проверяют контракт модуля, а не вызовы его соседей (модуль 21)
