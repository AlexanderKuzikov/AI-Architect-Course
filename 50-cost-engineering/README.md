## 1. Введение и актуальность

### 1.1. Почему cost — архитектурная проблема

AI-система экономически умирает тремя способами:

```text
1. Стоимость растёт линейно с N запросов → бюджет не выдерживает объёма
2. Cost per task превышает выручку (или ценность) задачи
3. Модель/провайдер дорогие, хотя дешёвая справилась бы
```

Cost — не «финансовая тема», а архитектурная: определяется выбором модели, каскадами, кэшами, fallback и наблюдаемостью. Всё это решается на этапе проектирования.

**Правило:** cost per task — это KPI архитектуры, как latency и accuracy. Его нужно мерить, бюджетировать и гейтить.

### 1.2. Цена не только модели

| Компонент | Пример |
|:--|:--|
| Генерация | tokens × цена модели |
| Tools | каждый вызов внешнего API |
| Memory | retrieval, хранение, обновление |
| Rerankers | cross-encoder на каждый запрос |
| LLM judge | evals в CI и pre-release |
| Retries | повторные вызовы при ошибках |
| Fallback | дублирование дорогой→дешёвой |

**Практический вывод для архитектора:** «считать только model cost» — антипаттерн. В multi-agent системах tools, memory и judge часто стоят больше самой генерации. Cost model обязан включать все компоненты.

### Граничные случаи — где ломается

**Cost растёт незаметно**: провайдер сменил тариф, fallback включился на слабую модель, retrieval стал возвращать больше чанков. Без cost-мониторинга это обнаружат через месяц по счёту.

**Дешёвая модель дороже дорогой**: если дешёвая модель генерирует 2 вызова вместо 1 (retry, уточнение) — итог дороже. Сравнивать не цену токена, а **cost per task**.

**Почему это важно архитектору:** cost engineering — про бюджетирование архитектуры, а не про «сэкономить». Задача — держать cost per task в бюджете при растущем N.

## 2. Архитектурная механика

### 2.1. Cost model: формула

```text
cost_per_task = input_tokens × price_in + output_tokens × price_out
             + n_tool_calls × cost_per_tool
             + n_retries × cost_per_call
             + amortized_judge_cost

месячный бюджет = N_tasks × cost_per_task
```

Cost model — это не «посчитаем потом», а прогноз до запуска. Он определяет, какую модель можно использовать при заданном бюджете.

### 2.2. Cascade Filter: дешёвый gate перед дорогой моделью

```text
Вход → SLM gate (0.8B, локально) → дорогая VLM (только ~30%)
                    │
                    └→ pytesseract + text LLM (70%, в 5× дешевле)
```

Каскад: дешёвый компонент решает «нужна ли дорогая обработка». Ключевое — **измеренная pass rate**: если gate пропускает 90%, каскад не окупился.

```text
Хорошая экономика: 30% × дорого + 70% × дёшево = cost_per_task ниже в 2–3×
Плохая экономика: 90% × дорого + 10% × дёшево — gate не окупился
```

### 2.3. Key rotation и провайдеры

| Провайдер | Сценарий |
|:--|:--|
| RouterAI | рубли, один ключ, маршрутизация по цене |
| OpenRouter | ротация ключей, fallback |
| LM Studio / Ollama | нулевой marginal cost, приватность |
| Прямой вендор | прямой контракт, лучшая цена при объёме |

**Key rotation**: несколько ключей одного провайдера для обхода rate limit; ротация по нагрузке. Fallback: при отказе/превышении бюджета — дешёвая модель.

### 2.4. Cost per task бюджеты

```yaml
# Бюджет на задачу
budget:
  cost_per_task: 0.02   # $ или ₽
  p95_latency: 3s
  tokens_per_task: 40K
  fallback_rate: 5%
```

Контроль:
- cost attribution per task (фактическая модель, учёт fallback);
- alert при превышении бюджета;
- качество против cost: нельзя резать cost до деградации качества без evals.

### 2.5. Кэширование и дедупликация

```text
Embedding cache: L1 (in-memory) + L2 (Redis) → hit 94% → cost on embeddings −90%
Повторные запросы: хэш промпт+параметры → кэш ответа
Дедупликация задач в очереди: тот же документ не обрабатывается дважды
```

Кэш — самый дешёвый способ снизить cost: один раз посчитали, N раз переиспользовали.

### 2.6. Observability cost

```text
per-task: cost, tokens, model, fallback_flag
per-day:  cost по модели, по агенту, по клиенту
alert:    cost_per_day > 2× среднего
```

Без cost-метрик нельзя ответить на «сколько стоит задача» и «где уходит бюджет».

### Граничные случаи — где ломается

**Cost attribution при fallback**: запрос ушёл на дешёвую модель, но в метриках записан как дорогая. Dashboards врут, fallback незаметен. `gen_ai.model` = фактическая модель + `fallback: true`.

**LLM judge дороже пайплайна**: evals на каждый PR через судью могут стоить дороже самой генерации. Sampling evals + deterministic checks первыми.

**Ретриты взрывают cost**: «retry сожрал весь RPM» — каждый retry платит за токены. Меньше retry + Retry-After уважение = ниже cost.

**Почему это важно архитектору:** в cost engineering всё сводится к измерению. Нельзя оптимизировать то, что не измеряется. Cost attribution — обязательный слой, как и tracing.

## 3. Production trade-offs

| Решение | Выигрыш | Цена | Когда выбирать |
|:--|:--|:--|:--|
| Одна мощная модель | простота | cost растёт с N | малый объём |
| Cascade (SLM → VLM) | cost −2–3× | сложность, latency | большой объём, измеримый pass-rate |
| Локальная модель | нулевой marginal cost | качество, железо | приватность, офлайн |
| Cloud + кэш embeddings | cost −90% на embeddings | инфра кэша | повторяющиеся запросы |
| Самый дешёвый провайдер | цена | качество, отказ | не критичные задачи |
| Ротация ключей | обход rate limit | сложность | большие объёмы |

## 4. Failure modes

| Failure mode | Симптом | Контроль |
|:--|:--|:--|
| Cost explosion | счёт в 10× | cost budget + alert |
| Silent degradation | дешёвая модель хуже | evals + fallback rate |
| Fallback незаметен | качество упало, метрики зелёные | fallback_flag в метриках |
| Gate не окупился | каскад без экономии | измерять pass rate |
| Judge дороже пайплайна | evals съедают бюджет | sampling, deterministic first |
| Retry storm | cost ×3 из-за ретраев | Retry-After, меньше попыток |

## Реальный кейс

### Входные данные

Пайплайн обработки документов, 2000 документов/день. Итерация 1: всё через облачную VLM — `$15/день`. Итерация 2: cascade filter + кэш embeddings — `$4.20/день`. Бюджет заказчика: `$50/мес`.

### Гипотеза

Cascade (SLM gate → VLM) + L1/L2 embedding cache + дешёвый fallback удержат cost в бюджете без потери качества.

### Что получилось

```text
Итерация 1:  500 документов/день × $0.03 = $15/день
Итерация 2:  2000 документов/день → $4.20/день
  ├── Cascade: 30% в VLM, 70% pytesseract + text LLM (в 5× дешевле)
  ├── Embedding cache L1+L2: hit 94%, cost −90%
  └── Cost/task: $0.003 (против $0.03 в итерации 1)
```

**Что неожиданно:** главный выигрыш дал не выбор «дешёвой модели», а **перенос 70% трафика с VLM на детерминированный OCR + text LLM**. Каскад изменил структуру cost, а не цену токена. Второй выигрыш — кэш embeddings: повторные запросы не платят вообще.

### Вывод, противоречащий интуиции

Cost engineering — это не «выбрать подешевле», а **изменить структуру обработки**: какие задачи вообще не требуют дорогой модели, какие результаты можно кэшировать. Экономия на удельной цене токена даёт проценты; экономия на структуре — разы.

## 6. Антипаттерны

### «Считать только model cost»

**Выглядит правильно:** модель — главная статья.

**Почему ошибка:** tools, memory, rerankers, judge, retries часто стоят больше генерации. Cost model — весь пайплайн.

---

### «Самая дешёвая модель»

**Выглядит правильно:** экономия.

**Почему ошибка:** если модель требует retry/уточнений — cost per task выше. Сравнивать cost per task, не цену токена.

---

### «Каскад без измерений»

**Выглядит правильно:** gate экономит.

**Почему ошибка:** если pass rate 90%, каскад не окупился. Pass rate измеряется, иначе каскад — лишняя сложность.

---

### «Резать cost без evals»

**Выглядит правильно:** бюджет важнее.

**Почему ошибка:** дешёвая модель без evals — молчаливая деградация. Каждое сокращение cost валидируется качеством.

---

## Anti-checklist ☠️

- [ ] Считать только model cost — tools/memory/judge/retries часто дороже
- [ ] Самая дешёвая модель — cost per task выше из-за retry
- [ ] Каскад без измерения pass rate — gate не окупился
- [ ] Резать cost без evals — молчаливая деградация качества
- [ ] Fallback без пометки в метриках — качество упало, метрики врут
- [ ] Нет cost budget на задачу — explosion виден через месяц по счёту
- [ ] Все evals через LLM judge — judge дороже пайплайна
- [ ] Нет кэша embeddings — повторные запросы платят снова

## Задачи AI-кодеру

Плохая формулировка: > «Сделай дёшево»

Хорошая формулировка: > «Реализуй на TypeScript `CostTracker`: метод `track(call: {model, inputTokens, outputTokens, cost, fallback, taskId})` пишет в JSONL. Метод `summaryByModel(from, to)` возвращает cost по модели и долю fallback. Метод `alertIfOverBudget(taskId, budgetUsd)` — предупреждение при превышении. Тест: fallback-вызов помечается и не искажает cost основной модели.»

Формула: точные методы + структура записей + агрегация + тест на fallback attribution.

---

**Задача 1 — Cost tracker**

> Реализуй на TypeScript `CostTracker`: `track(call: {model, inputTokens, outputTokens, cost, fallback, taskId})` пишет в JSONL. `summaryByModel(from, to)` — cost по модели и доля fallback. Test: fallback-вызов помечается и не искажает cost основной модели.

---

**Задача 2 — Cascade decision**

> Реализуй `shouldUseExpensive(input, gate: (input) => {shouldUse, confidence})`: gate-функция решает, нужна ли дорогая модель. Логируй pass rate. Верни `{model: 'cheap'|'expensive', reason}`. Тест: gate с pass rate 90% логирует это для решения о каскаде.

---

**Задача 3 — Budget guard**

> Реализуй `assertBudget(costPerTask, budget, {alertThreshold})`: если cost_per_task > budget — выброс или alert в зависимости от `alertThreshold`. Верни `{ok, costPerTask, budget}`. Тест: cost 0.03 при бюджете 0.02 → alert.

---

**Задача 4 — Embedding cache экономика**

> Реализуй `cacheEconomy(stats: {hits, misses, costPerCall})`: возвращает `{savings, hitRate}`. Тест: hit 94% при 1000 запросов и cost $0.003 → savings ≈ $2.8.

## Чеклист архитектора

### Cost model
- [ ] cost per task включает все компоненты (tools, memory, judge, retries)
- [ ] Прогноз cost на N задач до запуска
- [ ] Сравнение по cost per task, не по цене токена

### Архитектура
- [ ] Каскад измерен (pass rate)
- [ ] Кэш embeddings/ответов есть
- [ ] Fallback явный и помечается
- [ ] Key rotation там, где нужен

### Бюджеты
- [ ] cost budget на задачу есть
- [ ] Alert при превышении
- [ ] Fallback rate в мониторинге
- [ ] Cost attribution по фактической модели

### Качество
- [ ] Каждое сокращение cost валидируется evals
- [ ] LLM judge используется с sampling
- [ ] Deterministic checks первыми
- [ ] Baseline cost+quality сравним с текущим
