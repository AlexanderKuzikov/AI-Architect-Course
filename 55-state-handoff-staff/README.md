# Модуль 55 — Передача состояния: handoff и штаб

> **Для AI-архитектора:** работа с агентами почти всегда идёт несколькими сессиями, и тогда состояние лежит не в голове сессии, а в файлах. Это меняет требования к архитектуре: контекстное окно становится дефицитным ресурсом, а «источник истины» переезжает из живой сессии в репозиторий. Две механики решают одну задачу — передачу состояния: `handoff` переносит состояние между сессиями, `штаб` распределяет работу между сессиями и принимает результат. Обе ломаются одинаково: размытым заданием, устаревшим описанием и отсутствием критерия приёмки.
>
> Один день изучения — от файла состояния проекта до приёмки по diff'у: что обязано попасть в handoff, что в него не попадает, как штаб ставит задание и как принимает результат.

## 1. Контекстное окно как дефицитный ресурс

Агент не помнит предыдущую сессию. Он начинает с того, что лежит в файлах и в переданном сообщении. Отсюда следствие, которое ломает привычную модель работы:

**Состояние проекта, не записанное в файл, не существует для следующей сессии.**

Это не «неудобно, лучше записать». Это разница между состоянием, которое переживает переключение, и состоянием, которое умирает вместе с окном.

```text
Состояние проекта =
  что в коде (git)           ← переживает всё
+ что в документации (файлы)  ← переживает сессию, если записано
+ что в голове сессии         ← умирает при закрытии
+ что в контексте агента      ← конечный ресурс, расходуется
```

Последняя строка — главная. Контекстное окно расходуется навсегда и не восстанавливается: прочитанный файл кода, вывод команды, длинный дифф. При переключении сессии всё это нужно заново. Отсюда правило экономии: **в контекст кладётся только то, что нельзя прочитать**, а всё, что можно прочитать, кладётся в файл.

Что это меняет в проектировании:

- Документация становится частью системы, а не приложением к ней
- Правила проекта (`AGENTS.md`) — механизм, а не вежливость: агент читает их всегда
- ADR нужен не для памяти автора, а для передачи решения между сессиями

**Практический вывод для архитектора:** если изменение нельзя объяснить файлом за пять минут чтения, оно не будет объяснено ни в какой сессии. Это ограничение проектировщика, а не документатора.

## 2. Файловый источник истины

Рабочее состояние лежит в git. Локальная копия — рабочая копия, синхронизируемая с remote. Правило простое и жёсткое:

**Записал в файл — закоммитил. Не закоммитил — состояния нет.**

```bash
# Порядок фиксации состояния
1. Правки в файлы
2. Проверка (сборка, аудит, тесты)
3. git add -A
4. git commit -m "Что и зачем"
5. git push origin main
```

Шаг 5 — не формальность. Следующая сессия может быть на другой машине и без твоего рабочего каталога. Единственное место, где состояние гарантированно есть, — remote.

### Что должно жить в файлах

| Артефакт | Что фиксирует | Почему в файле |
|:--|:--|:--|
| `AGENTS.md` | правила проекта, команды, чего не делать | агент читает при каждом старте |
| `docs/CONTEXT.md` | текущее состояние, открытые проблемы, журнал | ответ на «что сейчас происходит» |
| `ADR` | решение и его причины | решение переживает автора решения |
| `QUICKREF` | однострочные правила | экономит окно на перечитывании |
| `HANDOFF.md` | состояние на момент переключения | единственный носитель «что успели» |

### Что не должно попадать в git

Артефакты сборки (`course.html`, `index.html`), зависимости (`node_modules/`, `venv/`), секреты, временные результаты экспериментов. Причина не в размере: при переключении сессии мусор в состоянии вытесняет полезное из окна.

**Граничные случаи — где ломается:**

**Локальный коммит без пуша даёт иллюзию сохранения.** Всё выглядит зафиксированным, сессия закрывается, следующая открывает рабочий каталог на другой машине — и файла нет. Исчезновение работы без ошибок — худший вид потери данных, потому что его не замечают.

**Документация, которую пишут после кода, всегда отстаёт.** Контекст проекта, заполненный в конце сессии по памяти, содержит планы, а не состояние. Полезнее короткая запись сразу после изменения: «добавил поле X, миграция Y, что не сделано» — даже если позже она превратится в полноценный раздел.

**Файл состояния, который никто не обновляет, хуже отсутствующего.** Читающий тратит окно на текст, который протух. Признак: журнал в `CONTEXT.md` датирован месячной давности, а код менялся ежедневно.

**Почему это важно архитектору:** состояние проекта — такой же актив, как схема БД. Если он меняется без миграции (то есть без записи в источник истины) и без версии, через полгода никто не сможет объяснить, почему решение принято.

## 3. Handoff: что это и зачем

Handoff — файл, описывающий состояние работы в момент передачи из одной сессии в другую. Не отчёт о сделанном, а входные данные для следующей.

Ключевое различие:

| Тип документа | Отвечает на вопрос | Читает |
|:--|:--|:--|
| Отчёт о работе | «что сделано» | человек, для истории |
| **Handoff** | «что делать дальше и что для этого нужно знать» | следующая сессия, для работы |

Второе важнее. Отчёт без состояния бесполезен для продолжения: он описывает прошлое, а следующей сессии нужно настоящее.

### Когда handoff нужен

- Переполнение контекста — сессия длинная, состояние уже не помещается
- Смена исполнителя: штаб передаёт задание кодовой сессии
- Смена стратегии: гипотеза не подтвердилась, нужен другой подход
- Передача контекста человеку или другой системе

Когда не нужен: сессия короткая и работа завершена. Handoff, написанный «на всякий случай» после каждой задачи, превращается в мусор, который придётся читать.

**Практический вывод для архитектора:** пиши handoff в момент, когда состояние ещё актуально, — то есть перед переключением, а не «когда вспомню». Разница в качестве — во всём: через день половина записанного уже неверна.

## 4. Анатомия handoff-файла

Всё, что не проходит по трём фильтрам, в handoff не пишется.

**Фильтр 1: прочитает ли это следующая сессия?** Информация, нужная только тебе для памяти, — не проходит. Хороший пример плохой записи: «пользовался вчера до обеда» (зачем это читать?).

**Фильтр 2: нельзя ли это прочитать иначе?** Состояние git восстанавливается `git log` и `git status` за секунды. Дублировать его в handoff — трата окна. Проходит только то, чего в git нет: почему такое решение, что пробовали и не сработало, что дальше.

**Фильтр 3: изменится ли это до конца работы?** Значения, которые устареют за час (текущий PID, размер временного файла), в handoff не живут.

```markdown
# HANDOFF — <проект>

## Статус
Одно предложение: где работа остановилась.

## Готово
- <что сделано> — <файл или коммит>

## Не сделано
- <что осталось> — <почему застряло или почему отложено>

## Решения
- <решение> — <причина> (ADR: <ссылка>)

## Проверено
- <команда> → <результат>

## Ключи сессии
- <что было сделано в этой сессии, чего нет в git>
- <черновые идеи, отброшенные варианты>

## Первым делом
1. <конкретный следующий шаг>
```

### Обязательные поля

| Поле | Зачем | Что отсутствует без него |
|:--|:--|:--|
| **Статус** | одно предложение вместо чтения всего файла | сессия тратит окно на выяснение, где находилась работа |
| **Не сделано** | граница работы | следующая сессия дублирует сделанное или пропускает дыры |
| **Решения с причинами** | не даёт пересмотреть закрытый вопрос | следующая сессия тратит время на уже отвергнутый вариант |
| **Проверено** | экономит повторную проверку | та же сборка гоняется заново |
| **Первым делом** | снимает зависание на старте | сессия начинается с «с чего начать?» |
| **Ключи сессии** | единственное, чего нет в git | теряется вывод эксперимента, который нигде не зафиксирован |

Поле **«Проверено»** недооценено. Команда с результатом экономит следующей сессии минуты на каждой проверке. Один формат: `команда → что получилось`.

### Чего в handoff быть не должно

- Полного diff'а — он в git
- Пересказа документации, которая и так читается
- Планов без горизонта («когда-нибудь разобраться с кэшем»)
- Оценок времени
- Секретов и ключей — их место в переменных окружения

**Граничные случаи — где ломается:**

**Handoff на 300 строк.** Читается целиком, съедает окно, и к концу чтения актуальна только первая половина. Работает обратное правило: если handoff не помещается на один экран, состояние плохо структурировано — скорее всего, не разделены «решения» и «факты».

**Handoff без «не сделано».** Самая частая форма. Сессия выглядит законченной, и следующая начинает с нуля — переделывает или, что хуже, дублирует. Поле «не сделано» — единственное, что отличает передачу состояния от отчёта.

**Handoff, который описывает намерение, а не состояние.** «Планирую добавить кэш» вместо «кэш не добавлен, причина — инвалидация». Следующая сессия тратит время, чтобы выяснить, сделано это или нет.

**Почему это важно архитектору:** стоимость ошибки в передаче состояния асимметрична. Лишний раздел в handoff стоит минуту, отсутствующее «не сделано» — час повторной работы или, что хуже, тихий дефект в коде, которого никто не искал.

## 5. Деградация handoff

Двойное переключение — источник почти всех ошибок. Механизм:

```text
Сессия A пишет Handoff-A
        ↓ (читает сессия B)
Сессия B пишет Handoff-B, не удаляя Handoff-A
        ↓ (читает сессия C)
Сессия C читает Handoff-A и Handoff-B, выбирает «свежий по дате»
```

Ошибка выбора здесь почти невозможна: обе даты написаны автором, обе выглядят валидными, а актуально только второе. Что хуже — Handoff-A может содержать инструкции, которые B уже отменил.

### Четыре правила против деградации

**Правило 1: один активный handoff.** Старый удаляется в том же коммите, в котором появляется новый. Не «завтра вычищу», а сразу: иначе через три переключения в репозитории лежат три файла, и ни один не выигрывает.

**Правило 2: источник истины — git, а не handoff.** Handoff описывает состояние, но не заменяет его. Разошлись описание и код — правильно код.

**Правило 3: приёмка проверяет репозиторий, а не читает.** Первое действие принимающей сессии — `git log`, `git status`, `git diff`. Описание без проверки состояния бесполезно.

**Правило 4: handoff удаляется в начале следующей сессии.** Не в конце. Пока он лежит, следующая сессия может его перечитать и принять за актуальный — то есть вернуться к деградации.

```bash
# Приёмка: сначала состояние, потом описание
git log --oneline -10
git status --short
git diff --stat
# и только потом: чтение HANDOFF.md
```

**Граничные случаи — где ломается:**

**Handoff удалён при коммите, а не при приёме.** Файл исчез из репозитория раньше, чем следующая сессия его прочитала. Правило звучит парадоксально, но отказ от удаления хуже: см. правило 1.

**Состояние в рабочем каталоге, но не в git.** Приёмка проверяет remote, а изменения остались локально и не видны. Симптом — «всё по плану, а файла нет».

**Один handoff на несколько несвязанных задач.** Пять задач, пять handoff'ов в разных ветках истории. Ни один не отражает целого состояния. Правильно: один активный handoff на проект, внутри — разделы по задачам.

**Почему это важно архитектору:** состояние — единственное, что нельзя восстановить догадкой. Всё остальное в коде выводится из кода, состояние проекта — нет. Поэтому его передача требует формализованной дисциплины ровно в той степени, в какой её требует миграция схемы.

## 6. Штаб: распределение работы

Штаб — одна сессия, которая планирует, раздаёт задания кодовым сессиям и принимает результат. Кодовые сессии выполняют и отчитываются.

Оркестрация та же, что в модуле 42 (A2A), но для людей и сессий:

```text
Штаб-сессия
  ├── планирует: читает состояние, решает что делать
  ├── ставит задание: файл, не переписка
  ├── принимает: по diff'у и проверкам, не по отчёту
  └── обновляет состояние: контекст проекта, handoff

Кодовая сессия
  ├── читает задание и правила проекта
  ├── делает работу
  ├── проверяет сам (сборка, тесты)
  └── пишет отчёт: что сделано, что нет, что нашёл по дороге
```

### Что это даёт

- **Параллельность без потери контроля**: сессии работают одновременно, штаб видит целое
- **Разделение ролей**: планирование и приёмка не смешаны с правкой кода
- **Сохранение контекста штаба**: он не тратит окно на чтение кода, только на решения
- **Воспроизводимость решений**: задание записано, а не сообщено

### Чего это не даёт

Штаб не решает задачи, которые требуют чтения кода. Если решение упирается в незнакомую часть системы, штаб тратит окно на разведку дешевле, чем кодовая сессия, которая работает в этом коде постоянно. Практическое правило: **штаб решает, что и почему; кодовая сессия решает, как**.

**Граничные случаи — где ломается:**

**Штаб как «ещё одна сессия, которая всё делает сама».** Тогда распределения работы нет, а стоимость — координационная накладная: задание, отчёт, приёмка вместо прямой работы. Признак — задания формулируются «разберись с кэшем», и кодовая сессия тратит половину окна на выяснение границ.

**Параллельные задания в одном файле.** Две сессии правят один файл параллельно, обе коммитят — теряется работа, нужен разбор конфликта, который дешевле было предотвратить. Правило: одно задание — один файл, либо явное указание «не трогай этот файл».

**Отчёт без проверки.** Кодовая сессия пишет «готово», штаб принимает на слово. Единственная проверка — `npm run check` в CI. Если он зелёный, а задание не выполнено, никто этого не увидит: зелёная сборка не означает выполненную работу.

**Почему это важно архитектору:** штаб — это организационное решение, выраженное в инструментах. Он работает, пока у каждого задания есть один владелец, один критерий готовности и одна проверка. Без любого из трёх это ритуал.

## 7. Постановка задания

Задание передаётся файлом. Переписка не годится: она не переживает переключение, не версионируется и не попадает в историю.

### Структура задания

```markdown
## Задание: <что сделать, одной строкой>

**Контекст** — 2–3 предложения: где это в системе, почему нужно сейчас.

**Границы** — что НЕ трогать. Список файлов и подсистем.

**Требования**
- <проверяемое требование>
- <проверяемое требование>

**Критерии готовности**
- <команда> → <ожидаемый результат>
- <что должно работать>

**Контекст проекта** — прочитать: `AGENTS.md`, `docs/CONTEXT.md`, ADR-<...>
```

### Обязательные части

| Часть | Без неё |
|:--|:--|
| **Контекст** | сессия начинает с разведки кода, тратя окно |
| **Границы** | правит чужое, расширяет дифф, спорит с соседней сессией |
| **Проверяемые требования** | результат оценивается на вкус, приёмка превращается в торг |
| **Критерии готовности** | «готово» означает разные вещи, приёмка затягивается |
| **Ссылки на файлы контекста** | правила проекта нарушаются, потому что не прочитаны |

**Требование должно быть проверяемым.** Разница видна на паре:

| ❌ Непроверяемое | ✅ Проверяемое |
|:--|:--|
| «улучшить обработку ошибок» | «`npm run check` → 0 замечаний; ошибки 1С возвращаются как `{code, message, request_id}`» |
| «добавить тесты» | «покрыты ветки: пустой ответ, таймаут, ошибка парсинга; `npm test` → зелёный» |
| «привести стиль к единому» | «комментарии на русском, `// ✅` / `// ❌` для паттернов» |
| «не ломать API» | «все 26 эндпоинтов из `docs/API.md` отвечают как раньше; проверка — контрактный тест в CI» |

### Как формулировать для агента

Агент не знает контекста проекта и не догадывается о намерениях. Формула: **что делает + ограничения + конкретные API + версия платформы + проверяемый критерий**.

```markdown
❌ «Оптимизируй модуль парсинга».

✅ «В `modules/parsing` разбор одного дела занимает 800 мс на файле
   в 5000 строк. Гипотеза: регулярное выражение с вложенными квантификаторами
   даёт квадратичное время на строках без совпадений (ReDoS).
   Задача: найди и исправь, добавь тест с таймаутом 100 мс на файл
   в 5000 строк. Границы: не трогать `modules/http`, не менять публичный API.
   Критерий: `npm test` → зелёный, новый тест падает на исходном коде
   и проходит после правки».
```

Разница принципиальна: во втором случае задание можно принять, не читая код, — есть команда и ожидаемый результат.

**Граничные случаи — где ломается:**

**Задание-цель вместо задания-работы.** «Сделай модуль устойчивым» — у этого задания нет критерия готовности, и приёмка превращается в обсуждение вкуса. Переформулировать в проверяемое требование либо честно признать, что критерия нет.

**Задание без границ.** Сессия делает «больше, чем просили» — расширяет API, попутно чинит соседний модуль. Дифф вырастает втрое, приёмка замирает на ревью, откатить всё целиком нельзя.

**Задание, выдаваемое устно.** Работа начинается, а через час выясняется, что задание поняли иначе. Два часа переделки, которые не видны в истории.

**Почему это важно архитектору:** качество задания определяет качество результата сильнее, чем качество модели. Одна и та же модель на хорошем задании даёт пригодный результат, на плохом — уверенную неправильную работу, и это хуже, потому что выглядит как готовая работа.

## 8. Приёмка результата

Порядок приёмки нарушать нельзя: сначала состояние, потом отчёт.

```bash
# 1. Состояние — источник истины
git log --oneline -10
git status --short
git diff --stat main

# 2. Проверки
npm run check

# 3. Объём изменений
git diff --stat main

# 4. И только потом отчёт
```

### Что проверяется

| Проверка | Вопрос | Провал означает |
|:--|:--|:--|
| Сборка и аудит зелёные | «работает ли это вообще» | не принято |
| Критерии задания выполнены | «сделано ли то, что просили» | не принято, вернуть с указанием пункта |
| Границы не нарушены | «не полез ли куда не просили» | на ревью, лишний дифф |
| Размер диффа разумен | «одна задача или пять» | задача декомпозирована неверно |
| Границы модулей целы | «нет ли нарушения архитектуры» | к рефакторингу (модуль 53) |

### Когда вернуть задание

Вернуть стоит, если: критерий не выполнен; границы нарушены; дифф втрое больше ожидаемого; нарушена граница модуля; задание оказалось неоднозначным. **Не вернуть стоит, если** всё это выполнено, а стиль отличается от привычного: стиль правится в приёмке, а не отправляется на переделку. Переделка ради стиля — это ещё один цикл работы агента и ещё одна передача состояния.

### Что делает штаб после приёмки

1. Обновляет состояние проекта: что изменилось, что осталось
2. Фиксирует решение, если в ходе работы появилось архитектурное
3. Пишет handoff, если продолжать предстоит в другой сессии
4. Коммитит и пушит состояние — иначе работа не существует для следующей сессии

**Граничные случаи — где ломается:**

**Приёмка по отчёту без `git diff`.** Отчёт описывает намерение; дифф показывает реальность. Расхождение — норма, особенно для агента, склонного описывать сделанное в терминах задачи.

**Дифф втрое больше задания, принятый «в целом».** Внутри почти всегда есть либо недоделанное, либо лишнее. И то и другое требует отдельного цикла.

**Возврат задания без указания пункта.** «Переделай» без ссылки на критерий даёт второй круг той же работы. Возврат — это список конкретных пунктов, которые не выполнены.

**Принятая работа не закоммичена.** Ничего не произошло: следующая сессия не увидит изменений, а handoff будет описывать то, чего нет.

**Почему это важно архитектору:** приёмка — единственный момент, где можно поймать нарушенную границу модуля или инфраструктурное решение, сделанное в одном коммите. Пропустил — это в коде навсегда.

## 9. Реальный кейс

### Контекст

Учебник из 52 модулей собирается скриптом Node.js в один HTML. Правки вносятся в несколько сессий параллельно: содержательные разделы, версии инструментов, аудит исходников. Каждая сессия работает с общим деревом модулей, глоссарием и служебными файлами.

### Симптом

Вечером сессия А дописала разделы в модуль 02 и сверила версии. Наутро сессия Б работала с модулем 09, сверила версии там же — и нашла в корневом `GLOSSARY.md` устаревшую версию Vitest, которая расходилась с модульным глоссарием. Модульный был прав, корневой — нет.

Вторая проблема обнаружилась позже: сессия В, добавлявшая новый модуль, обновила `scripts/modules.mjs`, но не обновила счётчик в корневом `README.md` и трек в `ARCHITECTURE_LANDSCAPE.md`. Сборка прошла, аудит не заметил — он проверяет наличие секций, а не согласованность счётчиков в прозе.

### Гипотеза

Два вывода. Первый: глоссарий в корне живёт своей жизнью и расходится с модульными, потому что агрегация ничем не проверяется. Второй: числа в прозе — это утверждения о состоянии, и они расходятся с источником истины так же, как код.

### Что получилось

- **Расхождение версий закрыто, причина найдена:** корневой `GLOSSARY.md` собирается вручную из модульных и живёт отдельно. Проверка «версия термина в корне равна версии в модуле» добавлена в аудит — иначе расхождение вернётся на следующей же сверке.
- **Счётчики модулей в прозе признаны дефектом проверки:** аудит гарантирует, что 52 секции в HTML, но не гарантирует, что «52 модуля» в `README.md`, `AGENTS.md` и карте соответствуют реестру. Добавлена проверка соответствия счётчиков реестру.
- **Правило закрепилось в `AGENTS.md`:** изменение числа модулей тянет обновление счётчиков во всех корневых файлах, потому что это одна операция, а не пять.
- **Работа стала фиксироваться в состояние явно:** после каждой завершённой правки — проверка, коммит, пуш; журнал в `docs/CONTEXT.md` дополняется. Именно это потом позволило другой сессии понять, что было сделано, без чтения истории вручную.

### Вывод, противоречащий интуиции

Интуиция: «согласованность глоссария — вопрос внимания». Реальность: это **отсутствующая проверка**. Внимание заканчивается, автоматическая проверка — нет. Как и в случае с границами модулей из главы 53: договорённость без проверки — это пожелание, а расхождение обнаруживается тем, что кто-то потратил час на сверку.

Второй вывод: **состояние проекта — такой же актив, как схема БД**. И к нему применимы те же требования: изменение фиксируется в источнике истины, версионируется, и расхождение описания с реальностью считается багом, а не мелочью.

## 10. Антипаттерны

### Handoff на 300 строк

Читается целиком и съедает окно; к концу чтения актуальна первая половина. Симптом плохой структурированности состояния, а не длины файла.

---

### «Не сделано» без раздела

Самая частая форма. Сессия выглядит законченной, следующая либо переделывает сделанное, либо, что хуже, пропускает дыру. Единственный способ отличить передачу состояния от отчёта — этот раздел.

---

### Несколько handoff'ов одновременно

После двух переключений в репозитории лежат два файла с валидными датами. Ни один не выигрывает, а инструкции из первого уже отменены вторым. Один активный handoff, старый удаляется в том же коммите.

---

### Отчёт вместо handoff

Описывает «что сделано» вместо «что делать дальше и что для этого знать». Исторически полезно, для продолжения бесполезно.

---

### Штаб, который делает всё сам

Распределения работы нет, координационная накладная есть. Задания вида «разберись с кэшем» заставляют кодовую сессию тратить окно на выяснение границ.

---

### Задание-цель

«Сделай устойчивым», «приведи к единому стилю» — у таких заданий нет критерия готовности, приёмка превращается в торг о вкусе, а результат оценивается постфактум.

---

### Две сессии правят один файл

Параллельные задания с общим файлом дают конфликт, разбор которого дороже, чем сериализация работы.

---

### Приёмка по отчёту

Отчёт описывает намерение, дифф показывает реальность. Приёмка без `git diff` пропускает и недоделанное, и лишнее.

---

### «Переделай» без указания пункта

Возврат задания без ссылки на конкретный критерий даёт второй круг той же работы. Возврат — это список пунктов.

---

### Работа без пуша

Локальный коммит выглядит как сохранение, но следующая сессия может быть на другой машине. Исчезновение работы без ошибок — худший вид потери.

---

### Секреты в handoff

Ключи, пароли и токены не пишутся в передаваемые файлы: handoff коммитится и пушится. Место секретов — переменные окружения.

---

## Anti-checklist ☠️

- [ ] Handoff без раздела «не сделано» — следующая сессия дублирует работу или пропускает дыру
- [ ] Handoff копирует `git log` и диффы — тратит окно на то, что восстанавливается за секунды
- [ ] Handoff длиннее одного экрана — актуальна только первая половина к концу чтения
- [ ] Несколько активных handoff'ов — никто не выигрывает, инструкции из старого уже отменены
- [ ] Handoff удалён при приёме до того, как прочитан, — следующая сессия его не увидит
- [ ] Приёмка по отчёту без `git diff` — расхождение отчёта и реальности не замечено
- [ ] Принятая работа не закоммичена и не запушена — её не существует
- [ ] Задание без проверяемых критериев — приёмка превращается в торг о вкусе
- [ ] Задание без границ «что не трогать» — сессия правит чужое, дифф разрастается
- [ ] Задание выдано устно — через час выясняется, что понято иначе
- [ ] Две кодовые сессии правят один файл параллельно — конфликт дороже сериализации
- [ ] Ключи и токены в handoff или `CONTEXT.md` — файлы пушатся в remote
- [ ] Документация обновляется в конце сессии по памяти — описывает планы, а не состояние
- [ ] Handoff пишется «на всякий случай» после каждой задачи — мусор, который придётся читать

## Задачи AI-кодеру

Плохая формулировка:
> «Наведи порядок в документации проекта.»

Разбор: не указано, что именно не так, какие файлы трогать, как проверять. Результат — переписанные файлы без изменения состояния и без критерия приёмки. Переформулировать в проверяемое требование либо признать, что критерия нет.

Хорошая формулировка:
> «В `AI-Architect-Course` корневой `GLOSSARY.md` содержит определения терминов с версиями, которые расходятся с модульными глоссами.
>
> Задача: добавь в `scripts/audit.mjs` проверку, которая для каждого термина с версией сравнивает её в корневом и модульном глоссах и падает при расхождении.
>
> Границы: не трогать содержимое `GLOSSARY.md` — только аудит; не менять формат терминов в модулях.
>
> Критерии готовности:
> - `npm run audit` → ненулевой код, если расхождение воспроизведено искусственно
> - после исправления расхождения → `npm run check` → код 0
> - `npm run check` на текущем состоянии репозитория → 0 замечаний
>
> Контекст проекта: `AGENTS.md`, `docs/CONTEXT.md` (журнал: аудит 2026-10-02)».

Формула: что делает + границы + конкретный критерий с ожидаемым кодом выхода + ссылки на контекст проекта.

Вторая задача — на формулировку задания:
> «Переформулируй это задание так, чтобы его можно было принять, не читая код: 'почини парсер выписок банка, он иногда падает на пустых файлах'. Что должно быть в формулировке, чего не хватает сейчас и какой критерий готовности ты предложишь.»

Ожидаемый ответ: не хватает контекста (какой файл, какой модуль, почему падает — неизвестно даже чинильщику), границ, критерия готовности. Критерий: `npm test` → зелёный, добавлен тест на пустой файл и на файл в 0 байт, тест падал до правки.

## Чеклист архитектора

### Состояние проекта
- [ ] Правила проекта в `AGENTS.md` — читаются при каждом старте сессии
- [ ] Живое состояние и открытые проблемы в `docs/CONTEXT.md`
- [ ] Архитектурные решения в ADR с причиной и следствиями
- [ ] После каждой завершённой правки: проверка → коммит → пуш
- [ ] Ничего, что не должно попадать в remote (артефакты сборки, зависимости, секреты), не коммитится

### Handoff
- [ ] Пишется перед переключением, а не «когда вспомню»
- [ ] Есть разделы: статус, готово, не сделано, решения, проверено, первым делом, ключи сессии
- [ ] Не содержит копии `git log`, диффов и документации — только то, чего нет в git
- [ ] Помещается на один экран
- [ ] Один активный handoff; старый удалён в том же коммите
- [ ] Удаляется в начале следующей сессии, а не в конце работы

### Штаб
- [ ] Штаб решает «что и почему», кодовая сессия — «как»
- [ ] Задания передаются файлом, не перепиской
- [ ] У каждого задания: контекст, границы, проверяемые требования, критерии готовности, ссылки на файлы контекста
- [ ] Одно задание — один файл либо явное «не трогай этот файл»
- [ ] Приёмка: `git log` → `git status` → проверки → `git diff --stat` → и только потом отчёт
- [ ] Возврат задания — со списком невыполненных пунктов, не словом «переделай»
- [ ] Стилистика правится на месте, а не отправляется на переделку
- [ ] После приёмки состояние обновлено и запушено
