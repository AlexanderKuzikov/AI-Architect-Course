# Модуль 57 — Сверка без доступа к учётной системе

> **Для AI-архитектора:** модуль 56 дал предмет — граф первички. Этот модуль даёт доступ: какие данные реально можно получить извне, в каких форматах они приходят, что с ними происходит по дороге и почему «просто подключиться к 1С» — это проект на месяцы, а не на день. Разбирается архитектурное решение «читать, но не встраиваться», разбирается цена каждого способа входа и граничные случаи, где формат молча искажает суммы.
>
> Один день изучения — от выгрузки оборотно-сальдовой до работающей сверки по трём источникам: выписка банка, состояния ЭДО, сведения из реестра.

Следовательно, первым артефактом проекта является не код интеграции, а адаптер на границе с явной моделью внутренних данных.

## 1. Пять легальных входов

Способы получить данные для сверки, от простых к дорогим:

| Вход | Что отдаёт | Приватность | Сложность |
|:--|:--|:--|:--|
| выгрузка ОСВ из учётной системы | остатки и обороты по счетам | внутри компании | минимальная |
| файлы банк-клиента / выписка | деньги | внутри компании | низкая |
| API банка (Sber API, T-API) | деньги с задержкой в часы | наружу, по договору | средняя |
| API оператора ЭДО | статусы, подписи, отказы | наружу, по договору | высокая |
| True API Честного ЗНАКА | движение маркированного товара | наружу, по договору с УКЭП | высокая |
| ЕГРЮЛ / ЕГРИП ФНС | регистрационные сведения контрагента | открытые данные | низкая |

Ключевое наблюдение: **первые два входа не требуют ни одного соглашения с внешним поставщиком.** Их достаточно, чтобы закрыть 80% ценности. Это же означает, что продукт может быть начат без юридической работы и без интеграционных контрактов — а это же снимает главный барьер входа в отрасль.

**Практический вывод для архитектора:** порядок подключения источников определяется не технической сложностью, а соотношением ценности к цене подключения. Начинать надо с того, что не требует согласований.

## 2. Цена каждого способа входа

Выбор способа — это выбор между скоростью, приватностью и стоимостью. Разложение:

| Путь | Скорость появления данных | Что уходит наружу | Риск |
|:--|:--|:--|:--|
| файлы выгрузки | дни | ничего | расхождение форматов, ручной труд |
| API банка | часы | реквизиты счёта и операций | отзыв токена, лимиты, договор |
| чтение базы учётной системы | мгновенно | ничего | **согласие 1С, блокировки, лицензия** |

Вариант «зайти в базу 1С напрямую» почти всегда выглядит самым быстрым и оказывается худшим. Причины:

1. **Схема базы меняется при обновлении конфигурации.** Любая интеграция превращается в постоянное сопровождение.
2. **Обращения к базе 1С блокируются рабочим процессом.** Проверка в рабочее время мешает пользователям, проверка ночью нарушает регламент обслуживания.
3. **Нужен доступ, который бухгалтер не даст и не должен давать.** Права на изменение данных из сверки не нужны; возможность их получить разрушает доверие.
4. **Стоимость лицензирования.** Работа с 1С через их API имеет отдельную модель лицензирования, которая в сумме превышает стоимость задачи.

При этом официальные точки входа существуют и легальны: веб-сервисы 1С `GetData` / `PutData`, формат EnterpriseData, файловые выгрузки. Они дают нужные данные без вторжения внутрь.

**Практический вывод для архитектора:** «не лезть внутрь 1С» — не отказ от интеграции, а выбор легальной точки входа. Формулировка «мы читаем через стандартные интерфейсы обмена» снимает возражение бухгалтера, формулировка «мы не работаем с вашей учётной системой» заставляет клиента недооценивать стоимость внедрения.

**Граничные случаи — где ломается:**

**У клиента нет прав на выгрузку, потому что учёт ведётся в облаке.** Файл выгрузки получить можно, но с задержкой в сутки и через личный кабинет вручную. Продукт, построенный на файлах, деградирует до ежедневной ручной операции — и это меняет весь его ценовой класс.

**У клиента два учётные системы: бухгалтерия и склад.** Данные о продажах есть в одной, о поступлении — в другой. Сверка «учёт ↔ банк» работает, сверка «склад ↔ бухгалтерия» требует второго источника правды, которого у вас нет. Несовместимость схем здесь не техническая, а организационная, и она не лечится кодом.

**Бухгалтер ведёт учёт в двух системах параллельно.** Объясняется это просто: одна для ФНС, другая для себя. Источник правды не выбирается — он распределён, и правило сверки становится неоднозначным по определению.

**Почему это важно архитектору:** контракт с клиентом фиксирует, откуда берётся истина. Если источников два и они не согласованы, продукт не может выдать однозначный вывод, а значит, вся работа превращается в список вопросов клиенту.

## 3. Форматы на входе

Разнообразие форматов — не проблема, а рутина. Проблема возникает, когда разнообразие протекает внутрь системы.

| Формат | Что это | Подводное место |
|:--|:--|:--|
| XML | EnterpriseData, банковские форматы, ЭДО | версии схем, кодировка, отличия реализаций |
| JSON | API банков, API ЭДО | пагинация, курсоры, токены |
| XLSX | выгрузки банк-клиентов, отчёты | объединённые ячейки заголовков, числа как текст |
| MT940 | банковский стандарт выписки | состав полей опциональный, у каждого банка свой |
| TXT / CSV | фискальные выгрузки, выгрузки 1С | разделители, кодировки CP1251, порядок колонок |
| PDF | печатные формы выписок, сканы документов | извлечение текста, см. модуль 15 |

Главное правило: **внутренняя модель не должна быть похожа ни на один внешний формат.** Внешний формат живёт в адаптере и умирает вместе с ним.

```text
Банк A (XLSX)  ─┐
Банк B (MT940) ─┤
Банк C (JSON)  ─┼─→ [адаптер] → внутренняя модель → [правила] → отчёт
ОСВ (CSV)      ─┤        (уникальная)   (из модуля 56)
ЭДО (XML)      ─┘
```

**Практический вывод для архитектора:** внутренняя модель — это то, ради чего потом пишутся проверки. Если она диктуется форматом выписки, каждое изменение формата банком становится изменением модели, а вместе с ней — миграцией и перевыпуском проверок.

## 4. Банковская выписка

Банк — самый предсказуемый источник, потому что у него есть отраслевой стандарт. Рабочий путь от простого к сложному:

1. **Файл выгрузки из банк-клиента.** XLSX или MT940. Ноль интеграций, всё локально.
2. **API банка.** Часовая-дневная задержка, авторизация по токену, требует договора.
3. **Инкрементальная выписка.** Запрос операций за интервал внутри операционного дня. Экономит трафик, но вводит понятие задержки данных.

Формат MT940 — отраслевой стандарт, но **опциональные поля** в нём опциональны по-разному у разных банков: поле может отсутствовать, присутствовать пустым или заполненным по правилам банка. Парсер, написанный под один банк, на другом ломается на отсутствии поля, а не на неверном значении.

```json
{
  "account": "40702810***********",
  "currency": "RUB",
  "generatedAt": "2026-10-15T18:04:11+03:00",
  "entries": [
    {
      "bankOperationId": "F1234567890",
      "operationDate": "2026-10-14",
      "valueDate": "2026-10-14",
      "direction": "in",
      "amount": "125000.00",
      "counterpartyName": "ООО Ромашка",
      "counterpartyInn": "7701234567",
      "purpose": "Оплата по сч. 41 от 12.10.2026 за тов. по дог. 17/2026",
      "purposeNormalized": "Оплата по сч. 41 от 12.10.2026 за тов. по дог. 17/2026",
      "isCorrection": false
    }
  ],
  "openingBalance": "480000.00",
  "closingBalance": "605000.00"
}
```

Три поля в этой модели — не декорация:

- `bankOperationId` — основа идемпотентности. Без него повторная выгрузка даёт двойные расхождения.
- `isCorrection` — банк помечает операции, изменённые после первоначального проведения. Их нужно обрабатывать как отмену предыдущей, а не как новую.
- `operationDate` и `valueDate` — расходятся при операциях в валюте и при задержке исполнения. Сверка по одной дате даёт ложные расхождения на границе периода.

### Граничные случаи — где ломается

**Сумма приходит строкой с неразделителем.** «125000,00» или «125 000.00» или «125,000.00» — три записи одной суммы. Наивный `parseFloat` даёт 125000 и 125 соответственно. Это ошибка на порядки, и она не проявится в тестах на «нормальных» данных.

**Назначение платежа не разбирается правилами.** Реальные назначения — «за ж/у, сч. 41 от 12.10, дог. 17/2026, в т.ч. НДС 20%», «оплата по Договору поставки №17 от 01.09.2026 за март», «за приобретение тов. согласно УПД № 0000123 от 14.10». Правила здесь хрупкие: год вычета НДС, написание «дог.», пробелы, латиница против кириллицы в ИНН.

**Комиссия банка сажается на ту же сумму.** Операция 100 000 с комиссией 500 приходит двумя строками или одной с разделителем. Сверка «сумма платежа = неоплаченный документ» ломается, хотя бизнес в порядке.

**Конвертация валюты.** Оплата 1 000 EUR от 14.10 и проведение 14.10 по курсу на 13.10 дают разницу. Это не расхождение, но правило должно уметь это объяснить, иначе оно сработает на каждой валютной операции.

**Отсутствие оборотов за день.** Пустой день в выписке — норма. Код, который считает его пропуском операций, генерирует ложные тревоги ежедневно.

**Почему это важно архитектору:** банковская выписка — источник №1 по ценности и №1 по числу граблей в парсинге. Здесь нужны golden-тесты на реальных обезличенных выписках, а не моки: мок воспроизводит только те случаи, о которых разработчик подумал заранее.

## 5. Электронный документооборот

ЭДО отвечает на вопрос «существует ли документ в согласованном состоянии» — это ровно тот факт, которого нет в учётной системе. Клиент может провести УПД, но контрагент его не подписал: сумма висит в учёте, а обязательства сторон не возникли.

Ценность статуса ЭДО: подписан → отказ → маршрут подписи → отклонён при проверке схемы. Каждый статус — причина расхождения, а не сам дефект.

```text
черновик → подписан отправителем → отправлен → доставлен →
  подписан получателем ✅ (согласован)
  отказ получателя ❌ (документа нет)
  отклонён оператором (ошибка схемы) ❌ (реквизиты неполны)
```

Тонкость, определяющая архитектуру: **операторы ЭДО отличаются API.** У одного это SDK с колбэками, у другого REST с курсорами, у третьего — вебхуки по подписке. Поэтому код против конкретного оператора — это отдельный адаптер, а общая модель должна описывать состояние документа, а не способ доставки этого состояния.

Регуляторная часть, которую надо отслеживать: переход на универсальные сообщения вместо извещения о получении и уведомления об уточнении. Если интеграция завязана на старые сущности, она отстанет от регулятора раньше, чем от бизнеса.

**Практический вывод для архитектора:** интеграция с ЭДО — это не «получить данные», а «держать актуальное состояние». Различие проявляется в архитектуре: нужен локальный кэш состояний с временем жизни и правило, что делать при недоступности оператора, а не просто периодический опрос.

**Граничные случаи — где ломается:**

**Документ отправлен, но доставка не подтверждена.** Это не значит, что доставки не будет. Построенный на этом вывод продукт отправит контрагенту повторный документ — то есть создаст двойной УПД.

**Двойной приём через роуминг.** Два оператора вернули одно и то же. Дедупликация обязана идти по номеру и дате документа, а не по идентификатору сообщения у оператора.

**Реквизиты документа содержат только то, что заполнил бухгалтер.** УПД без ИНН получателя принимается оператором и уходит в никуда — документ в статусе «доставлен» при отсутствии адресата. Проверка «статус хороший» без проверки «реквизиты полны» даёт ложный успех.

**Контрагент отказал с основанием «ошибка в реквизитах», но причина — его внутренняя настройка.** Текст отказа не машиночитаем. Классификация отказа — задача нормализации, а не парсинга, и ошибка здесь стоит повторного цикла документооборота.

**Почему это важно архитектору:** состояние ЭДО — единственный источник, который отличает «документ есть» от «документ имеет силу». Ошибка в этой классификации даёт ложное подтверждение, а ложное подтверждение хуже отсутствия сигнала: клиент прекратит читать отчёт целиком.

## 6. Сверка как процесс

Сверка — не запрос к источнику, а трёхшаговый процесс с явными состояниями и повторяемостью.

```mermaid
flowchart LR
  A[получение данных] --> B[нормализация]
  B --> C[проверка целостности]
  C -->|ошибка| D[стоп: отчёт о входе]
  C -->|ок| E[применение правил]
  E --> F[обогащение: ЕГРЮЛ, срок договора]
  F --> G[приоритизация по цене пропуска]
  G --> H[отчёт: что делать и сколько стоит]
```

Три свойства, которые обязаны быть в конструкции:

1. **Идемпотентность.** Повторный запуск на тех же данных даёт тот же результат и не плодит дубли. Основа — ключ операции и версия правила.
2. **Версионирование правил.** Каждый результат хранит, какой версией правила он получен. Иначе через месяц нельзя объяснить, почему сигнал был или не был.
3. **Отказ вместо тихой пустоты.** Если источник не отдал данные, это результат, а не отсутствие результата. «Нет данных» и «данных нет» — разные состояния, и второе обязано быть видно.

```text
Результат сверки = набор сигналов, каждый из которых несёт:
  ruleId + ruleVersion + severity
  + предмет (что именно расходится)
  + источник правды
  + действие (кто и что делает)
  + цена (в рублях, на дату расчёта)
```

**Практический вывод для архитектора:** пустой отчёт и невыполненная сверка не должны выглядеть одинаково. Это различие стоит одной строки в модели результата и экономит месяц расследования «почему у клиента всё хорошо» при наличии непроверенного источника.

## 7. Нормализация и единицы

Прежде чем что-то сравнивать, нужно привести к общему виду. Слой нормализации — самый недооценённый и самый дорогой по числу часов.

**Деньги.** Хранение в копейках целым числом — не рекомендация, а требование. Округление применяется один раз, при выводе в отчёт.

```typescript
// ❌ Накопление ошибки и невозможность объяснить расхождение в 1 копейку
const total = rows.reduce((sum, r) => sum + parseFloat(r.amount), 0);

// ✅ Деньги как целые копейки, разбор в адаптере формата
type Kopecks = bigint;
const parseAmount = (raw: string): Kopecks => {
  const normalized = raw.replace(/[\s\u00a0']/g, '').replace(',', '.');
  const [whole, frac = ''] = normalized.split('.');
  const sign = whole.startsWith('-') ? -1n : 1n;
  const abs = whole.replace('-', '');
  const digits = (frac + '00').slice(0, 2);
  return sign * (BigInt(abs) * 100n + BigInt(digits));
};
```

**Идентификаторы.** ИНН — строка, а не число: 12 значащих цифр, а JS `Number` хранит 15–16 значащих цифр и потеряет точность на длинных значениях. Плюс проверка контрольного разряда ИНН отсекает опечатки раньше, чем они попадут в сверку.

**Даты.** Год, месяц, день — компоненты, а не одна строка. Разбор «12.10.2026» без указания формата путает 2 октября и 12 октября; обе даты встречаются в реальных выписках.

**Названия.** Сравнение названий контрагентов по строке не работает: «ООО Ромашка», «Общество с ограниченной ответственностью Ромашка», «Ромашка» — один контрагент. Ключ — ИНН плюс КПП для обособленных подразделений. Название используется только для показа и как последний резерв.

**Назначение платежа.** Свободный текст. Здесь уместна модель — извлечение реквизитов из текста, но с явным правилом: извлечённое значение — гипотеза, а не факт, и оно требует подтверждения совпадением суммы и даты.

**Практический вывод для архитектора:** слой нормализации — единственное место, где формат влияет на предметную область. Если он протекает глубже, дальше по коду начнут множиться частные случаи. Тест на этот разрыв: в бизнес-логике не должно быть ни одного упоминания внешнего формата.

## 8. Реальный кейс

**Входные данные.** Гипотеза: сверка из трёх источников — выписка банка, ОСВ, статусы ЭДО. Первый клиент — малое ООО на общей системе с одним расчётным счётом, одним оператором ЭДО и типовой конфигурацией учётной системы.

**Ход рассуждения.** Реализация началась с чтения базы учётной системы: это было быстрее всего, и позволяло получить любые данные без настройки выгрузок. Проверка гипотезы показала, что это решение делает невозможной передачу продукта другому клиенту: у каждого своя конфигурация и своя схема, а версии платформы обновляются. Стоимость подключения нового клиента линейно росла.

**Результат.** Переход на два входа — файл выгрузки ОСВ и выгрузка выписки из банк-клиента — дал две вещи, которых не давал первый вариант:

- Подключение нового клиента свелось к двум ручным операциям и настройке правил под его учётную политику.
- Продукт стал работать без согласований: ни договора с банком, ни с оператором ЭДО, ни с вендором учётной системы.

При этом выяснилось, что файлов достаточно для большинства проверок: расхождение банк ↔ учёт и расхождение между периодами определяются двумя файлами. ЭДО потребовался позже и только для проверки комплектности первички.

**Вывод, противоречащий интуиции.** Интеграция с API выглядит как развитие продукта, а оказалась архитектурным ущербом: она добавляет юридическую зависимость, требует поддержки форматов при смене вендора и уменьшает число клиентов, которых можно подключить без согласований. Файловая сверка выглядела как «деревенский вариант» и выиграла на дистанции.

Второй вывод: большая часть усилий ушла не в правила сверки, а в нормализацию — разбор сумм, дат, ИНН и назначений платежа. Правила сверки заняли меньше половины времени. План, в котором правила стоят первыми, систематически недооценивает срок в 2–3 раза.

## 9. Антипаттерны

### Чтение базы учётной системы «для скорости»

Кажется быстрее, чем договор. Результат: блокировки в рабочее время, поломка при обновлении конфигурации, необходимость согласования, невозможность подключить другого клиента. Быстрый доступ к данным в одной базе покупает ценой невозможности масштабирования.

### Нормализация, размазанная по бизнес-логике

Проверка начинает знать про формат выписки. Через месяц в ней появляется частный случай для второго банка, потом третий. Итог: правила не переиспользуются, добавление банка — это ревью всей кодовой базы.

### Идемпотентность по номеру строки

Номер строки меняется при повторной выгрузке. Повторный запуск даёт двойные расхождения, а пользователь после первого такого ложного сигнала начинает игнорировать отчёт целиком.

### Проверка без модели задержки источника

Сравнение «текущее состояние учёта» с «последней выпиской» даёт ложные срабатывания в течение суток после каждого платежа. Пользователь отключает проверку, и она больше не включается.

### LLM как источник реквизитов из назначения платежа

Модель разбирает назначение платежа уверенно и ошибается на 2–5% случаев, причём ошибается правдоподобно: не «не поняла», а «поняла не тот номер счёта». Нужны подтверждение суммой и датой, статус «гипотеза» в выводе и отсутствие автоматического действия по неподтверждённому разбору.

## Anti-checklist ☠️

- [ ] Обращения идут к базе учётной системы — блокировки, поломка при обновлении, невозможность масштабирования
- [ ] Формат внешнего источника протекает в правила сверки — добавление банка становится ревью кодовой базы
- [ ] Идемпотентность по номеру строки — повторная выгрузка даёт ложные двойные расхождения
- [ ] `parseFloat` над суммой из выписки — тихая потеря копеек или потеря разряда
- [ ] ИНН хранится как число — потеря точности на 12-значном идентификаторе
- [ ] Сверка без модели задержки источника — ложные срабатывания отключаются пользователем
- [ ] Пустой отчёт неотличим от невыполненной сверки — «всё хорошо» при непроверенном источнике
- [ ] Результат не хранит версию правила — через месяц нельзя объяснить сигнал
- [ ] Операция с флагом коррекции обработана как новая — расхождение в учёте навсегда
- [ ] Реквизиты ЭДО проверяются по статусу, а не по заполненности — ложное подтверждение

## Задачи AI-кодеру

Плохая формулировка:
> «Сделай парсер банковских выписок и сверяй их с учётной системой.»

Разбор: не указаны форматы, способ входа, что считается расхождением, как обрабатываются коррекции и что делает пользователь при сигнале. Результат — парсер, работающий на одном банке, и сверка, которую отключают после первого ложного срабатывания.

Хорошая формулировка:
> «В модуле 57 описаны входы для сверки: файл выгрузки ОСВ, выписка из банк-клиента (XLSX, MT940), API банка, API оператора ЭДО.
>
> Задача: реализовать слой адаптеров, приводящих каждый вход к единой внутренней модели операции и остатка по счёту. Внутренняя модель описана в модуле 57 (раздел 4).
>
> Границы: не реализовывать правила сверки — это модуль 56; не добавлять зависимостей; не обращаться к базе учётной системы ни при каких условиях; не работать с API банков и операторов ЭДО — только файловые входы.
>
> Требования:
> - сумма разбирается в копейки целым числом, форматы «125000,00», «125 000.00», «125,000.00» дают одинаковый результат
> - дата операции и дата исполнения хранятся раздельно
> - флаг коррекции банка представлен во внутренней модели
> - адаптер не выпускает наружу строковый тип для денег и идентификаторов
>
> Критерии готовности:
> - `npm test` → зелёный, тест на три написания одной суммы даёт один результат
> - `npm test` → зелёный, тест на строку без разделителя дробной части
> - `npm test` → зелёный, тест на отсутствующее опциональное поле MT940 у другого банка
> - `npm test` → зелёный, golden-тест на обезличенной реальной выписке
> - `npm run check` → код 0
>
> Контекст проекта: `AGENTS.md`, `docs/CONTEXT.md`, модули 56 (разделы 5, 7) и 57 (разделы 3, 4, 7)».

Формула: что делает + границы (включая явный запрет) + конкретные проверяемые свойства + критерии готовности с ожидаемым результатом.

Вторая задача — на границу ответственности:
> «Определи, где в системе сверки проходит граница между нормализацией формата и бизнес-правилами, и какие признаки в коде показывают, что граница нарушена. Ответ дай в виде правил, а не в виде описания текущего кода.»

Ожидаемый ответ: граница проходит по типу внутреннего значения — во внутренней модели нет строковых денег, строковых ИНН и неразобранных дат. Признаки нарушения: `parseFloat`, `new Date(str)`, разбор строки назначения в коде правила, обращение к колонке внешнего файла в модуле правил. Критерий проверки: в каталоге правил нет ни одного упоминания внешнего формата.

## Чеклист архитектора

### Источники
- [ ] Каждый источник назван, у каждого определена ожидаемая задержка данных
- [ ] Отсутствие данных от источника отличается от нулевого результата
- [ ] Порядок подключения источников обоснован ценностью, а не сложностью
- [ ] Ни один путь до данных не идёт к внутренней базе чужой системы
- [ ] Для внешних API зафиксирована версия спецификации и дата её проверки

### Форматы и нормализация
- [ ] Внутренняя модель не повторяет ни один внешний формат
- [ ] Деньги — целые копейки; округление только на выходе
- [ ] Идентификаторы — строки с проверкой контрольного разряда, где он есть
- [ ] Дата операции и дата исполнения хранятся раздельно
- [ ] Извлечение из свободного текста помечено как гипотеза и требует подтверждения

### Сверка
- [ ] Обработка идемпотентна по ключу операции
- [ ] Результат хранит версию правила и цену пропуска
- [ ] Модель задержки источника участвует в правилах
- [ ] Покрытие golden-тестами на реальных обезличенных данных, а не на моках
- [ ] Отчёт отвечает на «что делать» и «сколько стоит»

### Приватность и эксплуатация
- [ ] Режим обработки данных соответствует требованию клиента о коммерческой тайне
- [ ] Логи не содержат полных реквизитов и назначений платежей
- [ ] Смена версии внешнего контракта проверяется вручную до обновления
