# Глоссарий — Evaluator / Benchmark Design

---

## A

**Absolute Scoring**
Схема LLM-as-Judge: судья выставляет числовую оценку (например, 1–5) по критериям.
Быстро и масштабируется, но имеет высокую variance между запусками и anchor bias.
Менее стабилен чем pairwise comparison.

**Anchor Bias**
Систематическое смещение LLM-судьи в сторону определённого диапазона оценок
независимо от реального качества. Судья «якорится» на примерах из обучения.
Митигируется через few-shot калибровку с явными примерами крайних оценок.

## B

**Baseline**
Зафиксированные метрики качества pipeline в конкретный момент времени.
Содержит: mean score, p10/p90, failure rate, версию модели, hash промпта, версию датасета.
Хранится в git. Без baseline quality gate не имеет смысла — нет точки отсчёта.

**BERTScore**
Метрика семантического сходства текстов через контекстные эмбеддинги BERT.
Не требует LLM-судью, работает локально. Не измеряет фактическую точность —
только текстовое сходство. Применение: summarization, перефразирование.

## C

**Calibration (калибровка судьи)**
Валидация корреляции оценок LLM-судьи с human labels на репрезентативной выборке.
Метрика: Spearman ρ > 0.7 — приемлемый порог.
Минимальный объём для калибровки: 50 кейсов с human labels.

**CI/CD Quality Gate**
Автоматическая проверка метрик качества в pipeline CI/CD.
Два условия фейла: регрессия > порога И абсолютный score < минимума.
Только один критерий — недостаточно: пропускает системно плохие или системно хорошие состояния.

**Context Precision**
Ragas метрика: доля релевантных фрагментов среди всех извлечённых контекстов.
Измеряет точность retrieval. Низкий context precision → LLM получает лишний шум.

**Context Recall**
Ragas метрика: доля ground truth информации покрытой извлечёнными контекстами.
Измеряет полноту retrieval. Низкий context recall → LLM не получила нужные факты.

## D

**Data Drift**
Изменение распределения входных данных со временем относительно eval датасета.
Симптом: CI/CD зелёный, production деградирует. Причина: датасет не обновлялся.
Митигация: версионирование датасета, периодическое обновление при изменении источников данных.

**DeepEval**
Python-фреймворк для LLM evaluation с pytest-совместимым API.
Версия 3.9.2 (март 2026). Apache 2.0.
50+ метрик, G-Eval, поддержка локальных моделей через `DeepEvalBaseLLM`.

**Difficulty Level**
Категоризация тест-кейсов по сложности: easy, medium, hard, edge.
Используется для анализа провалов по категориям и обеспечения репрезентативности датасета.
Минимум 30 кейсов на категорию для статистически значимых метрик.

## E

**Exact Match**
Детерминированная метрика: 1.0 если predicted == expected (после strip()), иначе 0.0.
Применима только когда ожидаемый вывод однозначен. Не требует LLM-вызовов.
Основа Tier 1 evaluation — запускается на каждый коммит.

**Evaluation Tier**
Уровень evaluation pipeline с разным соотношением стоимость/качество:
Tier 1 — exact metrics (каждый PR, секунды, $0);
Tier 2 — LLM-as-Judge (ночной прогон, минуты, копейки при локальном судье);
Tier 3 — human evaluation (pre-release, часы, дорого).

## F

**Faithfulness**
Ragas метрика: степень поддержки ответа извлечёнными контекстами.
Значение 1.0 означает что каждый факт в ответе поддерживается контекстом.
Не измеряет правильность контекста — только консистентность ответа с ним.

**Failure Rate**
Доля тест-кейсов с score ниже установленного порога (например, < 0.5).
Более информативен чем mean score для обнаружения системных провалов.
Модель с mean 0.85 и failure rate 15% неприемлема для production.

**Field-Level Accuracy**
Метрика для extraction задач: точность по каждому полю схемы отдельно.
Позволяет обнаружить что конкретное поле (например, адрес) всегда ошибается
при общем высоком mean score. Основная метрика для structured extraction pipeline.

## G

**G-Eval**
Паттерн LLM-оценки с явным chain-of-thought: судья описывает шаги оценки
перед выставлением итоговой оценки. Снижает variance по сравнению с прямым scoring.
Реализован нативно в DeepEval 3.9.2.

**Ground Truth**
Эталонный правильный ответ для тест-кейса, размеченный человеком.
Используется в reference-based scoring и для калибровки судьи.
Без ground truth — только relative сравнение (pairwise), не absolute оценка качества.

## H

**Human Evaluation**
Tier 3 evaluation: экспертная разметка качества ответов людьми.
Самый надёжный метод, не масштабируется. Применяется на выборке hard/edge кейсов
перед значимыми production релизами.

## L

**LLM-as-Judge**
Паттерн evaluation: отдельная LLM оценивает качество вывода основной модели.
Три схемы: absolute scoring, pairwise comparison, reference-based scoring.
Требует калибровки против human labels перед использованием в CI/CD.

## P

**Pairwise Comparison**
Схема LLM-as-Judge: судья сравнивает два вывода и выбирает лучший.
Стабильнее absolute scoring, но требует двойного количества LLM-вызовов.
Position bias митигируется через двойной прогон с reversed порядком вариантов.

**Perplexity (PPL)**
Метрика качества языковой модели на тестовом корпусе.
В контексте evaluation — не метрика пайплайна, а метрика модели при выборе квантизации.
Не коррелирует напрямую с качеством на конкретных задачах.

**Position Bias**
Систематическое смещение LLM-судьи в сторону первого варианта при pairwise сравнении.
Митигация: двойной прогон AB + BA, результат засчитывается только при консистентности.

**Promptfoo**
YAML-driven инструмент для LLM evaluation и prompt comparison.
Версия 0.121.3 (март 2026). MIT лицензия. В марте 2026 приобретён OpenAI.
CLI-first, CI/CD gates через `--fail-threshold`, поддержка мультипровайдерного сравнения.

## Q

**Quality Gate**
См. CI/CD Quality Gate.

## R

**Ragas**
Python-фреймворк для RAG-специфичной evaluation.
Версия 0.4.3 (январь 2026). Apache 2.0.
Метрики: faithfulness, answer relevancy, context precision, context recall.
Synthetic test generation из реальных документов через `TestsetGenerator`.

**Regression**
Снижение метрики качества относительно зафиксированного baseline.
В quality gate: `regression = baseline_score - current_score`.
Допустимый порог: 2–3% для production pipeline.

**ROUGE**
Семейство метрик overlap n-gram между prediction и reference.
ROUGE-L (longest common subsequence) — основная метрика для summarization.
Ограничение: копирование исходного текста даёт высокий score без реального понимания.

## S

**Self-Enhancement Bias**
Тенденция LLM-судьи завышать оценки текстов сгенерированных моделью того же семейства.
Митигация: использовать модель другого семейства или провайдера в качестве судьи.

**Spearman ρ (ранговая корреляция)**
Метрика монотонной корреляции между двумя ранжированиями.
Устойчивее к выбросам чем Pearson r. Используется для калибровки судьи:
ρ > 0.7 — приемлемый уровень согласованности с human labels.

**Synthetic Test Generation**
Автоматическая генерация тест-кейсов из реальных документов через LLM.
Инструмент: Ragas `TestsetGenerator`. Ускоряет старт, не заменяет ручную разметку.
Ограничение: не покрывает специфичные edge cases реальных данных.

## T

**Test-Train Leakage**
Использование тест-кейсов из eval датасета при разработке промпта.
Результат: завышенные метрики, не коррелирующие с production качеством.
Митигация: строгое разделение dev_examples и eval_dataset с первого дня.

**Tier (evaluation tier)**
См. Evaluation Tier.

**Train/Test Split**
Разделение датасета на dev_examples (для разработки промпта) и eval_dataset (для измерения).
Строгое разделение обязательно — пересечение инвалидирует метрики.

## V

**Verbosity Bias**
Тенденция LLM-судьи предпочитать более длинные и развёрнутые ответы.
Митигация: явная инструкция в системном промпте судьи что длина не является критерием качества.
