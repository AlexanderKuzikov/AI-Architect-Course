## 1. Введение и актуальность

### 1.1. Сначала выбор хранилища

| Хранилище | Когда | Когда нет |
|:--|:--|:--|
| PostgreSQL | связи, транзакции, миллионы строк, запросы по фильтрам | простой файловый кэш, read-only корпус |
| SQLite | локальное, один процесс, файл-перенос | concurrent writes, multi-user |
| JSONL + append | инкрементальная история, аудит, без БД | нужны запросы по нескольким полям сразу |
| Vector (pgvector) | семантический поиск, RAG | точные запросы по полям |
| + полнотекстовый (TSVECTOR) | гибрид: точное + семантика | |

**Практический вывод для архитектора:** выбор хранилища — первое архитектурное решение. Если данные read-only и нужна инкрементальная история — JSONL дешевле и проще БД. Если нужны запросы, связи, транзакции — Postgres с первого дня, а не «потом перенесём».

### 1.2. Почему схема дорогая

Изменение схемы — это миграция данных, обратная совместимость, переиндексация, downtime. Схема в production меняется в 100 раз дороже, чем в прототипе. Поэтому:

- тип поля — решение на годы (добавить — легко, изменить — миграция);
- `NULL` vs `NOT NULL` — семантика бизнес-данных, не «мелочь»;
- версионирование схемы (`schema_migrations`) — с первой миграции, не «потом».

### Граничные случаи — где ломается

**«JSONL, потому что без БД проще»**: когда данных становится 10M записей и нужен запрос «сколько было в августе», JSONL превращается в полный скан. Порог перехода в БД — не «когда удобно», а «когда нужен второй индекс».

**«Postgres для всего»**: для кэша, очереди, полнотекста и векторов в одном Postgres — удобно, но каждый workload имеет свои требования (TTL, streaming, репликация). Не смешивать OLTP и аналитические нагрузки без нужды.

**Почему это важно архитектору:** выбор хранилища и схема — это контракт, который переживёт код. Ошибка здесь стоит больше, чем любой баг в приложении.

## 2. Архитектурная механика

### 2.1. Типы и семантика

```sql
-- Разные типы для разного смысла
-- id: identity/generated, не business id
CREATE TABLE cases (
    id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    court_id      INTEGER NOT NULL REFERENCES courts(id),
    case_number   TEXT NOT NULL,          -- '1-123/2026' — не число!
    status        TEXT NOT NULL DEFAULT 'pending',
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- business-unique: номер дела уникален в пределах суда
ALTER TABLE cases ADD CONSTRAINT uq_cases_court_number
    UNIQUE (court_id, case_number);
```

Правила:
- **номер дела — TEXT, не INTEGER** (ведущие нули, дефисы, суффиксы);
- **деньги — NUMERIC, не FLOAT** (точность);
- **даты — TIMESTAMPTZ, не TIMESTAMP** (timezone);
- **id не бизнес-поле**: уникальность по бизнес-ключу — отдельный constraint.

Деньги — это дальше, чем просто тип в колонке.

**Как хранятся.** Строкой с точкой. Считаются в NUMERIC, в целых копейках — единственное правило округления живёт в одном доменном модуле, в UI расчётов нет вообще.

**Как версионируются.** Тарифные шкалы привязаны к редакции закона: новая редакция — новая функция или версионированная таблица ставок. Капы заданы именованными константами, а не «мёртвой арифметикой за капом».

**Движения и балансы.** Таблица `money_entries` хранит требования и оплаты, балансы — представление из неё же. Мусорный формат в строке считается нулём по белому списку, а не роняет всё представление.

Критерий готовности расчётов — выгрузка из старой системы и дифф-отчёт с нулём расхождений.

### 2.2. Нормализация vs денормализация

| Подход | Плюсы | Минусы |
|:--|:--|:--|
| Нормализация (3NF) | нет дублей, консистентность | JOIN-ы, сложнее запросы |
| Денормализация (denormalized) | быстрые чтения, простые запросы | дубли, риск рассинхрона |
| JSONB-колонка для «мягких» полей | гибкость, без миграций | не индексируется просто так, не валидируется схемой |

Правило: **нормализуй по умолчанию, денормализуй по измеренной проблеме**. JSONB — для полей, которые меняются по составу (настройки, артефакты разных вендоров), но тогда часть данных не участвует в JOIN.

### 2.3. Индексы

```sql
-- Индекс на каждую «точку входа» в запросах
CREATE INDEX idx_cases_status ON cases(status);
CREATE INDEX idx_cases_created ON cases(created_at DESC);
-- Композитный — для фильтра по двум полям
CREATE INDEX idx_cases_court_status ON cases(court_id, status);

-- Уникальный индекс — если constraint не подходит
CREATE UNIQUE INDEX uq_cases_external ON cases(external_id) WHERE external_id IS NOT NULL;
```

Ошибки индексов:
- индексировать каждый столбец «на всякий случай» — замедляет INSERT, раздувает storage;
- забыть индекс на FK — JOIN/каскады деградируют;
- индекс не помогает при `%LIKE%` — нужен полнотекстовый или триграммный.

```sql
-- Полнотекстовый для поиска по тексту
CREATE INDEX idx_cases_text ON cases USING GIN (to_tsvector('russian', document_text));
```

### 2.4. Миграции

```text
schema_migrations — таблица версий
  └── 001_init.sql
  └── 002_add_cases_status.sql
  └── 003_idx_cases_court_status.sql
```

Правила миграций:
- одна миграция — одно изменение, append-only;
- **не редактировать опубликованные миграции** — добавлять новую;
- обратная совместимость: `NOT NULL` с дефолтом для существующих строк;
- большие таблицы: `CREATE INDEX CONCURRENTLY` (не блокирует записи);
- тестировать миграции против продакшен-подобных данных.

```sql
-- ❌ Ломает старый код: пишущий запрос без region не пройдёт
ALTER TABLE cases ADD COLUMN region TEXT NOT NULL DEFAULT '';

-- ✅ Старый код колонку не видит и продолжает работать
ALTER TABLE cases ADD COLUMN region TEXT NULL;
```

Одна строка `NOT NULL DEFAULT` — не «безопасный» шаг, а разовый. Она работает, только если в момент миграции не пишет старый код, а через час после деплоя нового кода работать начнёт. В системе с внешним потребителем (1С) это условие не выполняется никогда, поэтому переход к `NOT NULL` делается позже и отдельным шагом (модуль 54).

### 2.4.0. Миграции, которые берут блокировку

Маленький модуль может остановить приём заявок на минуты: дело не в размере таблицы, а в том, что `ALTER TABLE` без `lock_timeout` встаёт в очередь за блокировкой и держит её до конца ожидания.

```sql
-- В начале каждой миграции, меняющей схему
SET lock_timeout = '3s';
SET statement_timeout = '60s';
-- не успел за lock_timeout → миграция падает и переносится,
-- вместо того чтобы встать в очередь и заблокировать всех пишущих
```

| Операция | Блокирует запись | Обходной путь |
|:--|:--|:--|
| `ADD COLUMN` без дефолта | нет | — |
| `ADD COLUMN` с константой (PG 11+) | нет | — |
| `ADD COLUMN` с неконстантным дефолтом (`now()`, `uuid_generate_v4()`) | да | nullable + дефолт отдельно |
| `SET NOT NULL` | нет на PG 12+ | `CHECK ... NOT VALID`, затем `VALIDATE CONSTRAINT` |
| `ALTER COLUMN TYPE` | да | новая колонка + бэкфилл + переключение |
| `DROP COLUMN` | нет | переименовать в `_deprecated` и ждать |
| `CREATE INDEX` | да | `CONCURRENTLY` вне транзакции |
| `ADD FOREIGN KEY` | да | `NOT VALID`, затем `VALIDATE CONSTRAINT` |

```sql
-- Ограничение вводится мгновенно, история проверяется отдельно
ALTER TABLE cases ADD CONSTRAINT cases_region_check
  CHECK (region <> '') NOT VALID;                    -- проверяет только новые строки

ALTER TABLE cases VALIDATE CONSTRAINT cases_region_check;  -- держит слабую DDL-блокировку
```

**Граничные случаи — где ломается:**

**`CONCURRENTLY` внутри транзакции — ошибка, а индекс остаётся `INVALID`.** Такой индекс не используется планировщиком, то есть внешне всё работает, а запросы идут по последовательному сканированию. Проверять после каждой сборки:

```sql
SELECT indexrelid::regclass, indisvalid FROM pg_index WHERE NOT indisvalid;
```

**Длинная транзакция приложения держит блокировку — миграция падает каждую попытку.** Увеличение таймаута не помогает: искать надо транзакцию (`pg_stat_activity` + `pg_locks`), а не ждать её.

**Бэкфилл миллиона строк одной транзакцией.** Блокировка плюс раздутый WAL и отставание репликации. Батчами по тысяче с паузой — минута на паузы вместо минут простоя.

**Почему это важно архитектору:** миграция, берущая `ACCESS EXCLUSIVE`, — это остановка обслуживания, а не «медленная миграция». Она случается в пятницу вечером, потому что CI зелёный и развёртывание прошло по расписанию.

### 2.4.1. Дополнение из практики: расширения, blind-индекс, проверка после pull

Расширения — в первой миграции, а не «когда понадобится»: полнотекст, крипто и триграммы включаются в 0001, иначе первое же окружение нового разработчика падает на отсутствующем индексе. Правило после каждого pull — сверить миграции до старта API: журнал применённых против журнала кода, неприменённая миграция чинится миграцией, а не правкой кода.

Шифрованные поля нельзя искать напрямую — рядом с ciphertext лежит колонка hmac- наводка для поиска и дедупликации. Заложить с первого дня: задним числом перешифровывать сотни записей больно, а поиск по шифротексту невозможен в принципе. Выбор ORM из той же серии: близость к SQL и нативные JSONB и триграммы важнее «магии» — миграции остаются читаемыми SQL-шагами, а не чёрным ящиком.

### 2.4.2. GIN-индекс для триграмм без операторного класса молча не работает

Ошибка, которая выглядит как «индекс есть, а поиск не находит» — и поэтому не находится месяцами.

**Симптом.** Создан GIN-индекс на текстовую колонку, запрос с `similarity()` и порогом отсечения возвращает ноль строк на данных, где похожие названия очевидно есть. В коде всё верно: расширение установлено, индекс на месте, `EXPLAIN` показывает, что планировщик им пользуется.

**Почему так.** `USING gin (col)` на колонке `text` **без указания операторного класса** резолвится в `btree_gin` → `text_ops`, а не в `gin_trgm_ops`. Индекс создаётся, занимает место, даже используется планировщиком — но это индекс точного и префиксного совпадения, а не триграмм. Триграммного индекса в базе не существует, при этом `CREATE INDEX` отработал без ошибки.

```sql
-- ❌ Молча не то, что нужно: btree_gin → text_ops
CREATE INDEX idx_cp_name_trgm ON counterparties USING gin (name);

-- ✅ Явный операторный класс триграмм
CREATE INDEX idx_cp_name_trgm ON counterparties
  USING gin (name gin_trgm_ops);
```

Проверка в одну строку — тип индекса в каталоге:

```sql
SELECT indexdef FROM pg_indexes
 WHERE indexname = 'idx_cp_name_trgm';
-- ожидаемо: USING gin (name gin_trgm_ops)
-- если в выводе gin_trgm_ops нет — индекс не триграммный
```

**Что покажет `EXPLAIN` и почему это не отговорка.** Планировщик использует индекс, сканирование идёт быстро — просто по нему. При этом функция `similarity()` требует триграммного индекса для ускорения, а без него выполняется как последовательное сравнение. Итог: запрос отрабатывает, индекс «работает», результата нет. Единственный способ заметить — смотреть в `pg_indexes`, а не в план.

**Порог отсечения — вторая половина грабли.** Даже с правильным индексом `similarity(name, $1) > 0.3` на длинных русских фамилиях даёт ноль строк: триграммы коротких и длинных строк сравниваются неодинаково. Что делать:

| Причина | Проверка | Что делать |
|:--|:--|:--|
| Нет `gin_trgm_ops` | `pg_indexes.indexdef` | Пересоздать индекс с операторным классом |
| Порог слишком высокий | Выполнить `similarity()` без `WHERE`, посмотреть распределение | Снизить порог или сортировать по `similarity` с `LIMIT` вместо отсечения |
| Расширение не установлено в этой БД | `SELECT extname FROM pg_extension` | Расширения — в первой миграции (см. 2.4.1), а не вручную |

**Граница.** Правило «индекс создан — значит работает» здесь неверно: `CREATE INDEX` не проверяет, что выбран нужный операторный класс. В коде это выглядит как готовое решение и проходит ревью, пока в проде не начинают спрашивать, почему поиск по названию не находит ничего.

**Почему это важно архитектору:** любая оптимизация, эффект которой нельзя измерить, не является оптимизацией. Триграммный индекс без `gin_trgm_ops` — это оптимизация, которая не даёт эффекта, но выглядит как работающая, потому что ошибки нет.

### 2.5. Векторный поиск (pgvector)

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE embeddings (
    id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    source_id     BIGINT NOT NULL REFERENCES documents(id),
    model_version TEXT NOT NULL,          -- версия embedding-модели
    chunk_text    TEXT NOT NULL,
    embedding     vector(768) NOT NULL
);

CREATE INDEX idx_embeddings_hnsw ON embeddings
    USING hnsw (embedding vector_cosine_ops);
```

Ключевое (из модуля 12): `model_version` в каждой строке — при смене embedding-модели старые векторы несовместимы. Запрос фильтрует по актуальной версии.

### 2.6. Связи-зеркала, история и нумерация с дырками (практика, сентябрь 2026)

Парные связи — одна строка на пару. Упорядоченная пара плюс уникальный индекс закрывают переворот на уровне БД, направление хранится в поле деталей. Данные строки одни на двоих и правятся с любой стороны.

Один механизм с дискриминатором вида тянет и супругов, и доли, и руководителей, и места работы: виды разные, таблица и функции чтения — общие.

Флаги выводятся только сервером по связям и игнорируются на входе. Снос записи пересчитывает соседей.

История изменений — append-only таблица без ручной правки: пишет сервер по факту изменения, чтение от нового к старому. Аудит двумя уровнями: старое-новое по полям сущности плюс журнал чтения чувствительных полей для закона о персональных данных.

Нумерация внутренних дел — последовательность с допустимыми дырками: сквозные номера без блокировок ради красоты не делаются, дырки проговариваются с заказчиком, а не закрываются транзакционной магией.

### Граничные случаи — где ломается

**Число как id в отчётах**: `case_number` как INTEGER ломается на «1-123/2026» и «1-123-26/2026». Нормализация номера ДО хранения — отдельная задача, не в БД.

**Ведущие нули**: `'007'` как INTEGER станет `7`. Номера, коды (ОКТМО, ГАР) — всегда TEXT.

**Точка на разряд левее**: выгрузка из старой системы через драйвер дала суммы в 10 раз больше — доказано сырыми байтами, чинено поразрядно без деления на 10, с маркером однократности. Правило: расхождение с источником сверяется побайтово до фикса, фикс идемпотентен.

**Строгая схема вытирает сырые ключи**: реал несёт сотни сырых ключей источника, которых нет в схеме. Без сохраняющего режима любой PATCH профиля молча вытирал бы их из JSONB. Известные поля валидируются, неизвестные проходят как есть, перевод на строгие схемы — постепенно.

**Миграция на живой таблице**: `ALTER TABLE ... ADD COLUMN NOT NULL` без дефолта на 10M строк — блокировка таблицы. `CONCURRENTLY` и поэтапные ALTER обязательны.

**Почему это важно архитектору:** SQL — это не «написать SELECT», а моделирование реального мира: что является уникальным ключом, что может быть NULL, как данные меняются. Каждая ошибка типа поля переживает весь жизненный цикл системы.

## 3. Production trade-offs

| Решение | Выигрыш | Цена | Когда выбирать |
|:--|:--|:--|:--|
| Postgres с первого дня | связи, индексы, миграции | overhead инфры | данные с запросами и связями |
| SQLite | ноль инфры, файл | single-writer | локальный инструмент |
| JSONL append | просто, аудит, без БД | полный скан при запросах | инкрементальная история, read-mostly |
| Нормализация | консистентность | JOIN-ы | по умолчанию |
| Денормализация | скорость чтения | дубли | по измеренной проблеме |
| pgvector + TSVECTOR | гибрид | сложнее | RAG + точный поиск |

## 4. Failure modes

| Failure mode | Симптом | Контроль |
|:--|:--|:--|
| Schema drift | миграции не сходятся | append-only миграции, тесты |
| Missing index | медленные запросы при росте | EXPLAIN, мониторинг slow queries |
| Wrong column type | «007» → 7, деньги теряют копейки | типы по семантике, review |
| Locked table | ALTER на 10M строк | CONCURRENTLY, поэтапность |
| JSONB without validation | мусор в «гибких» полях | check constraints, schema-валидация на границе |
| Embedding drift | старые векторы несовместимы | model_version + migration |
| Import без бэкапа | DELETE сносит маппинг, фронт показывает пустые строки | бэкап перед импортом, dry-run по умолчанию |
| Двойной перекод | кириллица превращается в мусор через консольную кодировку | дамп и заливка только бинарно |

## Реальный кейс

### Входные данные

Два реальных решения из практики:

**Кейс A — SerpWatcher (SEO-трекер):** история позиций по запросам. Данные: queryId, дата проверки, позиции по 100+ ключам. Характер: append-only, read-mostly, запросы «график по queryId за месяц».

**Кейс B — судебные данные:** справочник судов (GAR-схемы), карточки дел, события. Запросы: поиск по номеру/участникам, связи суд↔дела↔события, нормализация номеров.

### Гипотеза

Кейс A: JSONL история + снапшоты. Кейс B: Postgres с нормализованной схемой и индексами.

### Что получилось

- **SerpWatcher**: JSONL append для истории (неизменяемые записи, инкрементальный сбор «пропустить уже проверенные сегодня»), JSON-снапшоты для текущего состояния. Без БД — нет миграций, нет индексов, файл копируется. Запрос «график по queryId» — линейный скан по файлу, но это миллионы строк в год при 100 запросах/день — приемлемо.
- **Судебные данные**: Postgres, нормализовано: `courts`, `cases`, `case_events`, `case_participants`. `case_number` — TEXT, нормализуется до хранения (канон `1-123/2026`). Уникальность — `(court_id, case_number)`. Индексы на статус, даты, участников. Миграции с первого дня.

**Что неожиданно:** решение «JSONL vs БД» оказалось не про объём, а про **характер запросов**. SerpWatcher с 10M строк JSONL на диске быстрее и проще, чем тот же объём в SQLite без индексов. Драйвер перехода в БД — не «много данных», а «нужен второй индекс/связь/транзакция».

### Вывод, противоречащий интуиции

Начинать с БД «на всякий случай» — такая же ошибка, как начинать с JSONL. Хранилище выбирается по характеру запросов, а не по предполагаемому объёму. Правильный вопрос — «какие запросы я буду делать», а не «сколько у меня будет данных».

### Дополнение из практики: авария импорта (август 2026)

Скрипт импорта в версии без маппинга перезаписал нормализованный профиль сырым, затем удалил помеченные записи — фронт показал сотни пустых строк, проверка наличием ключа вернула ноль локально. Дока была чистая, виноват был порядок операций, а не текст.

Три упора после аварии:

- Бэкап перед импортом обязателен, без бэкапа скрипт не стартует. Ночной бэкап таймером плюс проверка восстановления до прода.
- Dry-run по умолчанию, боевое удаление только с явным подтверждением. Правка плана и контекста никогда не триггерит удаление.
- Кодировка только бинарно: дамп на сервере в файл, перенос бинарной копией, заливка файлом на сервере. Текстовый конвейер через консоль с другой кодовой страницей даёт двойной перекод кириллицы.

Диагностика одной строкой: посчитать записи с ключом маппинга. Ноль — авария, целевое число — порядок.

## 6. Антипаттерны

### «Всё в JSONB, чтобы не мигрировать»

**Выглядит правильно:** гибко, без ALTER.

**Почему ошибка:** JSONB не валидируется схемой, не участвует в JOIN, индексируется хуже. Гибкость за счёт контракта — данные превращаются в «мусорную корзину».

---

### «Индексы на каждый столбец»

**Выглядит правильно:** всё быстро.

**Почему ошибка:** каждый индекс замедляет INSERT/UPDATE, раздувает storage. Индексируй по измеренным запросам (EXPLAIN), не по интуиции.

---

### «Номер как число»

**Выглядит правильно:** это же число.

**Почему ошибка:** ведущие нули, дефисы, суффиксы, «007». Бизнес-идентификаторы — TEXT, точность — NUMERIC, время — TIMESTAMPTZ.

---

### «Редактировать миграции»

**Выглядит правильно:** исправил и перезапустил.

**Почему ошибка:** миграции append-only. Отредактированная миграция расходится у команд/окружений. Новая миграция — единственный способ.

---

### «GIN по тексту — значит триграммы»

**Выглядит правильно:** `CREATE INDEX … USING gin (name)` на текстовой колонке, запрос с `similarity()` — всё на месте.

**Почему ошибка:** без операторного класса `gin_trgm_ops` индекс резолвится в `btree_gin` → `text_ops`. Он создаётся без ошибки, занимает место, планировщик его использует — но триграммного индекса в базе не существует. `similarity()` уходит в последовательное сравнение, результат пустой на заведомо похожих данных. Проверка одна строка: в `pg_indexes.indexdef` должно быть `gin_trgm_ops`.

## Anti-checklist ☠️

- [ ] Начинать с БД «на всякий случай» — выбор хранилища по характеру запросов
- [ ] Всё в JSONB — гибкость за счёт контракта данных
- [ ] Индексы на каждый столбец — замедляют запись, раздувают storage
- [ ] Номер/код как INTEGER — «007» → 7, ломаются коды и номера
- [ ] Деньги как FLOAT — потеря копеек при операциях
- [ ] Редактировать опубликованные миграции — schema drift у команд
- [ ] ALTER NOT NULL на 10M строк без CONCURRENTLY — блокировка таблицы
- [ ] Векторы без model_version — после смены embedding всё несовместимо
- [ ] GIN-индекс по тексту без `gin_trgm_ops` — создаётся без ошибки, не даёт эффекта, `similarity()` отдаёт пусто
- [ ] Порог `similarity()` выше фактического распределения — поиск «не находит» заведомо похожие строки
- [ ] Расширения не в первой миграции — окружение без `initdb`-скрипта падает на отсутствующем расширении
- [ ] Представление (view) создаётся руками, а не миграцией — не воспроизводится на новом окружении

## Чеклист архитектора

### Выбор хранилища
- [ ] Хранилище выбрано по характеру запросов, не по объёму
- [ ] Использование JSONL/БД/vector осознано
- [ ] Понятен порог перехода на следующий уровень

### Схема
- [ ] Типы по семантике (TEXT для номеров, NUMERIC для денег, TIMESTAMPTZ)
- [ ] `id` не бизнес-поле, business-unique — отдельный constraint
- [ ] NULL/NOT NULL отражают бизнес-семантику
- [ ] Нормализация по умолчанию, денормализация по проблеме

### Индексы
- [ ] Индексы по измеренным запросам (EXPLAIN)
- [ ] FK индексированы
- [ ] Полнотекстовый/триграммный для LIKE-поиска
- [ ] Векторный слой с model_version

### Миграции
- [ ] Append-only, одна миграция — одно изменение
- [ ] EXISTS-проверки в миграциях
- [ ] Большие таблицы — CONCURRENTLY вне транзакции
- [ ] Миграции тестируются на продакшен-подобных данных
- [ ] `lock_timeout` и `statement_timeout` заданы в начале каждой миграции
- [ ] Неконстантные дефолты не используются в `ADD COLUMN`
- [ ] `NOT NULL` через `CHECK NOT VALID` + `VALIDATE CONSTRAINT`
- [ ] После сборки — проверка `pg_index WHERE NOT indisvalid` (модуль 54)
- [ ] Порядок изменений: expand → релиз → бэкфилл → contract, оба кода работают на обоих шагах
