## 1. Введение и актуальность

### 1.1. Сначала выбор хранилища

| Хранилище | Когда | Когда нет |
|:--|:--|:--|
| PostgreSQL | связи, транзакции, миллионы строк, запросы по фильтрам | простой файловый кэш, read-only корпус |
| SQLite | локальное, один процесс, файл-перенос | concurrent writes, multi-user |
| JSONL + append | инкрементальная история, аудит, без БД | нужны запросы по нескольким полям сразу |
| Vector (pgvector) | семантический поиск, RAG | точные запросы по полям |
| + полнотекстовый (TSVECTOR) | гибрид: точное + семантика | |

**Практический вывод для архитектора:** выбор хранилища — первое архитектурное решение. Если данные read-only и нужна инкрементальная история — JSONL дешевле и проще БД. Если нужны запросы, связи, транзакции — Postgres с первого дня, а не «потом перенесём».

### 1.2. Почему схема дорогая

Изменение схемы — это миграция данных, обратная совместимость, переиндексация, downtime. Схема в production меняется в 100 раз дороже, чем в прототипе. Поэтому:

- тип поля — решение на годы (добавить — легко, изменить — миграция);
- `NULL` vs `NOT NULL` — семантика бизнес-данных, не «мелочь»;
- версионирование схемы (`schema_migrations`) — с первого миграции, не «потом».

### Граничные случаи — где ломается

**«JSONL, потому что без БД проще»**: когда данных становится 10M записей и нужен запрос «сколько было в августе», JSONL превращается в полный скан. Порог перехода в БД — не «когда удобно», а «когда нужен второй индекс».

**«Postgres для всего»**: для кэша, очереди, полнотекста и векторов в одном Postgres — удобно, но каждый workload имеет свои требования (TTL, streaming, репликация). Не смешивать OLTP и аналитические нагрузки без нужды.

**Почему это важно архитектору:** выбор хранилища и схема — это контракт, который переживёт код. Ошибка здесь стоит больше, чем любой баг в приложении.

## 2. Архитектурная механика

### 2.1. Типы и семантика

```sql
-- Разные типы для разного смысла
-- id: identity/generated, не business id
CREATE TABLE cases (
    id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    court_id      INTEGER NOT NULL REFERENCES courts(id),
    case_number   TEXT NOT NULL,          -- '1-123/2026' — не число!
    status        TEXT NOT NULL DEFAULT 'pending',
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- business-unique: номер дела уникален в пределах суда
ALTER TABLE cases ADD CONSTRAINT uq_cases_court_number
    UNIQUE (court_id, case_number);
```

Правила:
- **номер дела — TEXT, не INTEGER** (ведущие нули, дефисы, суффиксы);
- **деньги — NUMERIC, не FLOAT** (точность);
- **даты — TIMESTAMPTZ, не TIMESTAMP** (timezone);
- **id не бизнес-поле**: уникальность по бизнес-ключу — отдельный constraint.

### 2.2. Нормализация vs денормализация

| Подход | Плюсы | Минусы |
|:--|:--|:--|
| Нормализация (3NF) | нет дублей, консистентность | JOIN-ы, сложнее запросы |
| Денормализация (denormalized) | быстрые чтения, простые запросы | дубли, риск рассинхрона |
| JSONB-колонка для «мягких» полей | гибкость, без миграций | не индексируется просто так, не валидируется схемой |

Правило: **нормализуй по умолчанию, денормализуй по измеренной проблеме**. JSONB — для полей, которые меняются по составу (настройки, артефакты разных вендоров), но тогда часть данных не участвует в JOIN.

### 2.3. Индексы

```sql
-- Индекс на каждую «точку входа» в запросах
CREATE INDEX idx_cases_status ON cases(status);
CREATE INDEX idx_cases_created ON cases(created_at DESC);
-- Композитный — для фильтра по двум полям
CREATE INDEX idx_cases_court_status ON cases(court_id, status);

-- Уникальный индекс — если constraint не подходит
CREATE UNIQUE INDEX uq_cases_external ON cases(external_id) WHERE external_id IS NOT NULL;
```

Ошибки индексов:
- индексировать каждый столбец «на всякий случай» — замедляет INSERT, раздувает storage;
- забыть индекс на FK — JOIN/каскады деградируют;
- индекс не помогает при `%LIKE%` — нужен полнотекстовый или триграммный.

```sql
-- Полнотекстовый для поиска по тексту
CREATE INDEX idx_cases_text ON cases USING GIN (to_tsvector('russian', document_text));
```

### 2.4. Миграции

```text
schema_migrations — таблица версий
  └── 001_init.sql
  └── 002_add_cases_status.sql
  └── 003_idx_cases_court_status.sql
```

Правила миграций:
- одна миграция — одно изменение, append-only;
- **не редактировать опубликованные миграции** — добавлять новую;
- обратная совместимость: `NOT NULL` с дефолтом для существующих строк;
- большие таблицы: `CREATE INDEX CONCURRENTLY` (не блокирует записи);
- тестировать миграции против продакшен-подобных данных.

```sql
-- Добавление NOT NULL поля в существующую таблицу
ALTER TABLE cases ADD COLUMN region TEXT NOT NULL DEFAULT '';  -- безопасно
-- потом снять дефолт, если он временный
```

### 2.5. Векторный поиск (pgvector)

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE embeddings (
    id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    source_id     BIGINT NOT NULL REFERENCES documents(id),
    model_version TEXT NOT NULL,          -- версия embedding-модели
    chunk_text    TEXT NOT NULL,
    embedding     vector(768) NOT NULL
);

CREATE INDEX idx_embeddings_hnsw ON embeddings
    USING hnsw (embedding vector_cosine_ops);
```

Ключевое (из модуля 12): `model_version` в каждой строке — при смене embedding-модели старые векторы несовместимы. Запрос фильтрует по актуальной версии.

### Граничные случаи — где ломается

**Число как id в отчётах**: `case_number` как INTEGER ломается на «1-123/2026» и «1-123-26/2026». Нормализация номера ДО хранения — отдельная задача, не в БД.

**Ведущие нули**: `'007'` как INTEGER станет `7`. Номера, коды (ОКТМО, ГАР) — всегда TEXT.

**Миграция на живой таблице**: `ALTER TABLE ... ADD COLUMN NOT NULL` без дефолта на 10M строк — блокировка таблицы. `CONCURRENTLY` и поэтапные ALTER обязательны.

**Почему это важно архитектору:** SQL — это не «написать SELECT», а моделирование реального мира: что является уникальным ключом, что может быть NULL, как данные меняются. Каждая ошибка типа поля переживает весь жизненный цикл системы.

## 3. Production trade-offs

| Решение | Выигрыш | Цена | Когда выбирать |
|:--|:--|:--|:--|
| Postgres с первого дня | связи, индексы, миграции | overhead инфры | данные с запросами и связями |
| SQLite | ноль инфры, файл | single-writer | локальный инструмент |
| JSONL append | просто, аудит, без БД | полный скан при запросах | инкрементальная история, read-mostly |
| Нормализация | консистентность | JOIN-ы | по умолчанию |
| Денормализация | скорость чтения | дубли | по измеренной проблеме |
| pgvector + TSVECTOR | гибрид | сложнее | RAG + точный поиск |

## 4. Failure modes

| Failure mode | Симптом | Контроль |
|:--|:--|:--|
| Schema drift | миграции не сходятся | append-only миграции, тесты |
| Missing index | медленные запросы при росте | EXPLAIN, мониторинг slow queries |
| Wrong column type | «007» → 7, деньги теряют копейки | типы по семантике, review |
| Locked table | ALTER на 10M строк | CONCURRENTLY, поэтапность |
| JSONB without validation | мусор в «гибких» полях | check constraints, schema-валидация на границе |
| Embedding drift | старые векторы несовместимы | model_version + migration |

## Реальный кейс

### Входные данные

Два реальных решения из практики:

**Кейс A — SerpWatcher (SEO-трекер):** история позиций по запросам. Данные: queryId, дата проверки, позиции по 100+ ключам. Характер: append-only, read-mostly, запросы «график по queryId за месяц».

**Кейс B — судебные данные:** справочник судов (GAR-схемы), карточки дел, события. Запросы: поиск по номеру/участникам, связи суд↔дела↔события, нормализация номеров.

### Гипотеза

Кейс A: JSONL история + снапшоты. Кейс B: Postgres с нормализованной схемой и индексами.

### Что получилось

- **SerpWatcher**: JSONL append для истории (неизменяемые записи, инкрементальный сбор «пропустить уже проверенные сегодня»), JSON-снапшоты для текущего состояния. Без БД — нет миграций, нет индексов, файл копируется. Запрос «график по queryId» — линейный скан по файлу, но это миллионы строк в год при 100 запросах/день — приемлемо.
- **Судебные данные**: Postgres, нормализовано: `courts`, `cases`, `case_events`, `case_participants`. `case_number` — TEXT, нормализуется до хранения (канон `1-123/2026`). Уникальность — `(court_id, case_number)`. Индексы на статус, даты, участников. Миграции с первого дня.

**Что неожиданно:** решение «JSONL vs БД» оказалось не про объём, а про **характер запросов**. SerpWatcher с 10M строк JSONL на диске быстрее и проще, чем тот же объём в SQLite без индексов. Драйвер перехода в БД — не «много данных», а «нужен второй индекс/связь/транзакция».

### Вывод, противоречащий интуиции

Начинать с БД «на всякий случай» — такая же ошибка, как начинать с JSONL. Хранилище выбирается по характеру запросов, а не по предполагаемому объёму. Правильный вопрос — «какие запросы я буду делать», а не «сколько у меня будет данных».

## 6. Антипаттерны

### «Всё в JSONB, чтобы не мигрировать»

**Выглядит правильно:** гибко, без ALTER.

**Почему ошибка:** JSONB не валидируется схемой, не участвует в JOIN, индексируется хуже. Гибкость за счёт контракта — данные превращаются в «мусорную корзину».

---

### «Индексы на каждый столбец»

**Выглядит правильно:** всё быстро.

**Почему ошибка:** каждый индекс замедляет INSERT/UPDATE, раздувает storage. Индексируй по измеренным запросам (EXPLAIN), не по интуиции.

---

### «Номер как число»

**Выглядит правильно:** это же число.

**Почему ошибка:** ведущие нули, дефисы, суффиксы, «007». Бизнес-идентификаторы — TEXT, точность — NUMERIC, время — TIMESTAMPTZ.

---

### «Редактировать миграции»

**Выглядит правильно:** исправил и перезапустил.

**Почему ошибка:** миграции append-only. Отредактированная миграция расходится у команд/окружений. Новая миграция — единственный способ.

---

## Anti-checklist ☠️

- [ ] Начинать с БД «на всякий случай» — выбор хранилища по характеру запросов
- [ ] Всё в JSONB — гибкость за счёт контракта данных
- [ ] Индексы на каждый столбец — замедляют запись, раздувают storage
- [ ] Номер/код как INTEGER — «007» → 7, ломаются коды и номера
- [ ] Деньги как FLOAT — потеря копеек при операциях
- [ ] Редактировать опубликованные миграции — schema drift у команд
- [ ] ALTER NOT NULL на 10M строк без CONCURRENTLY — блокировка таблицы
- [ ] Векторы без model_version — после смены embedding всё несовместимо

## Задачи AI-кодеру

Плохая формулировка: > «Сделай БД для дел»

Хорошая формулировка: > «Спроектируй схему PostgreSQL для судебных дел: таблицы `courts`, `cases`, `case_events`, `case_participants`. `case_number` — TEXT, нормализованный до хранения. Уникальность `(court_id, case_number)`. Индексы на `status`, `created_at`, `participant_id`. Добавь миграции 001_init.sql и 002_add_case_events.sql. Напиши тесты миграций на продакшен-подобных данных.»

Формула: таблицы + типы по семантике + constraints + индексы + миграции + тесты.

---

**Задача 1 — Схема судебных дел**

> Спроектируй и напиши `001_init.sql`: таблицы `courts`, `cases`, `case_events`, `case_participants`. `id` — identity, `case_number` — TEXT, `court_id` — FK, уникальность `(court_id, case_number)`. Комментарии к типам. Индексы на `status`, `created_at`, `participant_id`. Проверь миграцию apply и rollback.

---

**Задача 2 — Нормализация номера**

> Реализуй функцию `normalizeCaseNumber(raw string) (string, error)` на TypeScript: `'1-123/2026'`, `'1-123-26/2026'`, `'1‑123/2026'` (неразрывный дефис) → канон `'1-123/2026'`. Верни ошибку для нераспознанного. Тесты на варианты.

---

**Задача 3 — Миграция с индексами**

> Напиши `003_idx_cases_window.sql`: индексы для запросов «дела суда по статусу за месяц» и «дела участника». Используй композитные индексы и `CONCURRENTLY` для больших таблиц. Объясни выбор в комментариях.

---

**Задача 4 — Векторный слой для RAG**

> Напиши `004_embeddings.sql`: таблица `embeddings` с `model_version`, `chunk_text`, `embedding vector(768)`, FK на документ, HNSW-индекс. Запрос по `model_version` обязателен. Добавь CHECK, что `model_version` не пуст.

## Чеклист архитектора

### Выбор хранилища
- [ ] Хранилище выбрано по характеру запросов, не по объёму
- [ ] Использование JSONL/БД/vector осознано
- [ ] Понятен порог перехода на следующий уровень

### Схема
- [ ] Типы по семантике (TEXT для номеров, NUMERIC для денег, TIMESTAMPTZ)
- [ ] `id` не бизнес-поле, business-unique — отдельный constraint
- [ ] NULL/NOT NULL отражают бизнес-семантику
- [ ] Нормализация по умолчанию, денормализация по проблеме

### Индексы
- [ ] Индексы по измеренным запросам (EXPLAIN)
- [ ] FK индексированы
- [ ] Полнотекстовый/триграммный для LIKE-поиска
- [ ] Векторный слой с model_version

### Миграции
- [ ] Append-only, одна миграция — одно изменение
- [ ] EXISTS-проверки в миграциях
- [ ] Большие таблицы — CONCURRENTLY
- [ ] Миграции тестируются на продакшен-подобных данных
