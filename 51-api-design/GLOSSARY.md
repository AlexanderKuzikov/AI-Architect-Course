# Глоссарий — API Design для систем-интеграций

## A

**API key** — длинная случайная строка (≥ 32 байта) для аутентификации сервис-потребителей (1С, cron, скрипты). Передаётся в `Authorization: Bearer <key>`. Для сервис-интеграций предпочтительнее JWT: нет refresh-цикла, хранится в конфиге потребителя, ротируется парой активных ключей.

## C

**Consumer-driven contract** — подход, при котором ожидания потребителя (1С-стороны) фиксируются как тесты против контракта и гоняются в CI провайдера. Потребитель не участвует в CI команды API — его ожидания проверяются автоматически.

**Contract-first** — проектирование API от спецификации (OpenAPI) к реализации, а не наоборот. Спецификация — единственный source of truth: из неё генерируются серверные хендлеры, клиенты, документация.

**Cursor (keyset) пагинация** — пагинация по позиции в строгом порядке сортировки, например `(updated_at, id)`. Курсор — непрозрачная для клиента строка, возвращается в `next_cursor`; клиент не строит и не разбирает курсоры. Применяется для выгрузок больших объёмов, где offset даёт пропуски/дубли.

## D

**Deprecation policy** — письменная политика вывода эндпоинтов из эксплуатации: заголовки `Deprecation: true` и `Sunset: <дата>`, минимальный период (≥ 12 месяцев) между объявлением и удалением, логирование клиентов на старой версии.

**DNS-pinning** — резолв DNS в IP один раз, валидация всех адресов и выполнение запроса по проверенному IP, чтобы повторный резолв внутри клиента не подменил адрес на внутренний (защита от SSRF).

## I

**Idempotency-Key** — заголовок, который клиент шлёт с POST-операцией; сервер хранит результат по ключу (TTL 24–48 ч) и при повторном запросе с тем же ключом возвращает сохранённый ответ, не выполняя операцию. Применяется для произвольных операций, где нет естественного бизнес-ключа.

**Идемпотентность по бизнес-ключу** — повторное выполнение операции не меняет результат благодаря уникальности естественного ключа, например `(court_id, case_number)` с `INSERT ... ON CONFLICT DO UPDATE`. Дефолтный механизм для импорта сущностей.

## O

**Offset-пагинация** — пагинация «страница N, размер M». Проста, но при изменении данных между страницами даёт пропуски и дубли; пригодна для UI со стабильными списками, не для выгрузок.

**OpenAPI 3.1** — спецификация REST API на JSON Schema 2020-12. Используется как контракт: линтеры (`@redocly/cli`), генерация кода, тесты контракта.

## R

**RPC-эндпоинт** — операция, не сводимая к CRUD ресурса: импорт пачки, синхронизация, выгрузка с нестандартными параметрами (`POST /import/cases`). Оправдана для неделимых batch-операций; обязана быть предсказуемой и идемпотентной.

**Rate limiting** — ограничение частоты запросов по ключу с заголовками `X-RateLimit-Limit/Remaining/Reset` и `429 + Retry-After`. Защищает справочники от полного выкачивания одним регламентным заданием; read/write лимиты разделяются.

**RFC 9457 (Problem Details)** — стандарт тела ошибок HTTP (заменил RFC 7807). В курсе используется упрощённая плоская схема `{code, message, details, request_id}`, дружелюбная к 1С-потребителю.

**request_id** — идентификатор запроса, возвращаемый в каждом ответе (включая успешные). Мост между логом сервера и обращением клиента: потребитель присылает `request_id` в тикет вместо пересказа симптомов.

## S

**SSRF** — Server-Side Request Forgery: сервер выполняет запрос по адресу, который контролирует (или подделывает) атакующий, и достигает внутренних ресурсов. Защита: allowlist доменов, блокировка private/loopback/link-local диапазонов, DNS-pinning.

**Sunset-заголовок** — `Sunset: <дата>` на deprecated-эндпоинте: объявляет дату удаления. Обязателен, иначе старые версии живут вечно.

## А

**API-контракт** — стабильный интерфейс между независимыми системами: ресурсы, коды ошибок, форматы, версия. Поля только добавляются; семантические изменения требуют новой версии. Единственный видимый потребителю артефакт системы.

**Антипаттерн «200 с ошибкой внутри»** — возврат HTTP 200 с `{"success": false}` вместо честного 4xx/5xx. Каждый потребитель обязан проверять `success`; тот, кто пропустил, молча обрабатывает ошибку как данные.

## В

**Версионирование в URL** — размещение версии контракта в пути (`/v1/cases`). Для внешних интеграций предпочтительно header-версиям: версия видна в логах прокси и конфиге потребителя, не зависит от возможностей HTTP-клиента.

## И

**Идемпотентность** — свойство операции: повторное выполнение даёт тот же результат, что первое. Обязательна для POST-операций интеграций: сеть не гарантирует доставки ответа, и клиент обязан безопасно повторить.

## К

**Курсор-позиция** — кортеж строгого порядка сортировки `(updated_at, id)` для выборки «после этой позиции». Стабилен при обновлении строк (id не меняется), в отличие от сортировки по одному `updated_at`.

## Н

**Нормализация номера дела** — приведение номера к канону (`1-123/2026`) до хранения и до поиска: неразрывные дефисы, пробелы, суффиксы. Номер дела — TEXT, уникален в паре `(court_id, case_number)`; в URL-пути не используется (слэши ломают маршрутизацию).

## П

**Плоский JSON** — ответ без глубокой вложенности (`court_id` + `court_name` вместо вложенного объекта суда). Снижает риск ошибок у потребителя, который пишет код без кодогенерации (1С).

**Partial failure пачки** — обработка импортируемой пачки поэлементно: `{processed: N, failed: [{index, code, message}]}`. Один битый элемент не блокирует остальные.
