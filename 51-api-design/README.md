## 1. Контракт — граница системы

### Механика

API-контракт — не документация, а **интерфейс между двумя независимыми системами**. Внутренний код меняется свободно; контракт — заморожен на годы, потому что потребитель живёт по своей версии контракта.

```
Команда A (CourtDesk)                    Команда B (1С, бухгалтерия)
   │                                             │
   │  контракт: OpenAPI 3.1 spec ───────────────►│
   │  (ресурсы, коды, форматы, версия)            │
   │                                             │
   │  релиз v1.2  ───────────────────────────────►│  интеграция на 1С-версии v1
   │  релиз v1.3                                  │  обновление клиента — через год
   │  релиз v1.4  (несовместим → v2)              │  → нельзя сломать v1
```

Свойства контракта, который выдерживает годы:

- **Поля только добавляются.** Удаление и изменение семантики — ломающее изменение.
- **Один source of truth.** OpenAPI-спецификация в репо — единственный источник; из неё генерируются серверные хендлеры и клиентская документация. Вторая копия контракта (README, wiki) обязательно расходится.
- **Тесты контракта.** Consumer-driven tests: ожидания потребителя проверяются на контракте при каждом CI-прогоне. 1С-разработчик не участвует в CI команды CourtDesk — его ожидания фиксируются в контрактных тестах за него.

### Реализация: контрактная проверка в CI

```yaml
# .github/workflows/contract.yml (фрагмент)
jobs:
  contract:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Validate OpenAPI spec
        run: npx @redocly/cli lint api/openapi.yaml
      - name: Contract tests (server agrees with spec)
        run: go test ./internal/api/... -run Contract
      - name: Example snapshots (spec agrees with reality)
        run: npx @redocly/cli preview-docs api/openapi.yaml --silent
```

### Граничные случаи — где ломается

**«Контракт — это README».** Второй источник правды расходится с реальностью через месяц. Если спецификации нет — потребитель дочитывает реальность по поведению API и зашивает её в свою логику. Любое последующее «исправление» для него — ломающее изменение.

**«Документация отстала» — это симптом.** Отставание документации означает, что контракт не управляется, а развивается стихийно. Чинить надо не документацию, а процесс: контрактные тесты в CI, review изменений спецификации.

**Контракт, который нельзя сгенерировать.** Если OpenAPI-файл пишется руками в отрыве от сервера, он врёт (описал эндпоинт, которого нет, или неверный формат поля). Лечится генерацией: типы Go/TS → OpenAPI → клиенты.

**Почему это важно архитектору:** контракт — единственная часть системы, которую потребитель видит. Всё остальное (качество кода, архитектура внутри) для него не существует. Инвестиции в контракт — инвестиции в интеграцию.

**Практический вывод для архитектора:** contract-first — не «модно», а минимально рискованно для интеграций с внешними системами. Если обе стороны разрабатываются в одном репо — можно schema-last; если потребитель живёт своей жизнью (1С) — контракт обязателен с первого дня.

## 2. Ресурсная модель и URL-дизайн

### Механика

Ресурсная модель строится от домена, а не от таблиц БД. Для CourtDesk домен (из модуля 49):

```text
courts        — справочник судов (ГАР)
cases         — карточки дел (case_number, status, court_id)
case_events   — события по делу (заседания, решения, изменения)
case_participants — участники дела (истцы, ответчики)
documents     — файлы по делу (судебные акты, сканы)
```

Правила URL-дизайна:

| Принцип | Пример |
|:--|:--|
| Коллекция — `GET /cases`, ресурс — `GET /cases/{id}` | `/cases/84921` |
| Вложенность отражает «принадлежит» | `GET /cases/{id}/events` |
| Действие — подресурс или RPC, не глагол в пути | `POST /cases/{id}/events` |
| Не копировать БД-идентификаторы в URL без необходимости | `/cases/{id}` — внутренний id |
| Бизнес-ключи — query, не путь | `GET /cases?number=1-123/2026` |

**Почему номер дела не в пути:** номер дела `1-123/2026` содержит символы, ломающие URL (`/`, пробелы, неразрывные дефисы), и не уникален глобально — только в паре `(court_id, case_number)`. В пути — стабильный числовой id, в query — нормализованный номер.

### RPC-эндпоинты для интеграций

Для batch-интеграций REST-канон (создавай по одному через POST) дороже:

```text
POST /cases/{id}/events            — единичное событие (нормально для UI)
POST /import/cases                 — пачка дел (для 1С-выгрузки)
POST /import/cases/{id}/documents  — документы по делу (PDF)
```

RPC-эндпоинты оправданы, когда операция неделима для потребителя: импорт пачки, синхронизация, поиск с нестандартными параметрами. Они не обязаны быть «чистым REST» — они обязаны быть **предсказуемыми и идемпотентными** (см. §6).

### Реализация: пример коллекции с фильтрами

```yaml
# api/openapi.yaml (фрагмент)
paths:
  /cases:
    get:
      summary: Поиск дел
      parameters:
        - name: number
          in: query
          schema: { type: string }
          description: Нормализованный номер дела (1-123/2026)
        - name: court_id
          in: query
          schema: { type: integer }
        - name: status
          in: query
          schema: { type: string, enum: [pending, active, closed] }
        - name: updated_after
          in: query
          schema: { type: string, format: date-time }
          description: Инкрементальная выгрузка изменений
      responses:
        "200":
          $ref: "#/components/responses/CaseList"
```

### Граничные случаи — где ломается

**Slash в бизнес-ключе.** Номер дела `1-123/2026` в пути `/cases/1-123/2026` ломает маршрутизацию (два сегмента). Экранирование `%2F` поддерживается не всеми прокси. Решение — нормализованный ключ в query (модуль 49: канон `1-123/2026`), id — в пути.

**Кириллица в URL.** Наименования судов, ФИО участников в пути — кодирование `%D0%...`, нечитаемые логи, кэши-прокси спотыкаются. Идентификаторы — латиница/цифры, кириллица — только в query-параметрах поиска.

**«Папки в URL» из БД-структуры.** `/courts/{court_id}/cases/{case_id}/events/{event_id}` — глубокая вложенность, копирующая схему БД. Глубина ≤ 2, связи через query-параметры (`?court_id=`), иначе клиент держит цепочку id.

**Идемпотентность названия коллекции.** `POST /cases` создаёт дело. Повторный POST тем же номером — дубль или ошибка? Решение — идемпотентный импорт по бизнес-ключу (§6), а не «потом разберёмся».

**Почему это важно архитектору:** URL-дизайн — это первое, что видит интегратор. Стабильные, предсказуемые URL уменьшают количество вопросов к команде и вероятность кривых решений у потребителя.

**Практический вывод для архитектора:** проектируй ресурсы от доменных сущностей и их отношений; RPC — только для неделимых batch-операций; бизнес-ключи — в query, стабильные id — в пути.

## 3. Версионирование API

### Механика

Внешний API обязан иметь версию в URL:

```text
https://api.courtdesk.ru/v1/cases
https://api.courtdesk.ru/v2/cases
```

Версия в URL — не «старомодно», а прагматично для внешних потребителей: видна в логах прокси, в конфиге клиента, не зависит от заголовков (старые HTTP-клиенты могут не отправить `Accept-version`). Header-версионирование уместно для внутренних API или когда URL должны быть стабильны (публичные SDK).

### Политика совместимости

| Тип изменения | Совместимость | Пример |
|:--|:--|:--|
| Добавление поля в ответ | ✅ | `participant_count` в `Case` |
| Добавление эндпоинта | ✅ | `GET /cases/{id}/documents` |
| Новое значение enum | ⚠️ может ломать | клиент с `switch` без default |
| Изменение семантики поля | ❌ v2 | `status` перестал включать `suspended` |
| Удаление поля | ❌ v2 | убрали `previous_number` |
| Изменение формата (дата-строка → ISO) | ❌ v2 | 1С парсил `DD.MM.YYYY` |

**Deprecation policy — письменная и измеряемая:** заголовок `Deprecation: true` + `Sunset: <дата>` на старых эндпоинтах, минимум 12 месяцев между объявлением и удалением, шлюз логирует клиентов, которые ещё ходят в старую версию.

### Реализация: заголовки deprecation

```go
// Заголовки deprecated-эндпоинта (net/http, Go 1.26)
w.Header().Set("Deprecation", "true")
w.Header().Set("Sunset", "2027-08-01T00:00:00Z")
w.Header().Set("Link", `</docs/v2/migration>; rel="migration"`)
```

Клиентская логика при получении `Deprecation` — логировать и запланировать миграцию; не молча продолжать.

### Граничные случаи — где ломается

**Молчаливое изменение семантики без смены версии.** Частый случай: «мы добавили поле, старые не трогали». Но если старое поле стало `null` вместо значения — потребитель молча получил другие данные. Семантика меняется — меняй версию.

**Enum-расширение ломает строгие клиенты.** 1С с `Если Статус = "closed" Тогда` молча пропускает новый статус `suspended` — данные «теряются» без ошибки. Расширение enum = минор только если потребители обрабатывают unknown-значения; иначе мажор.

**v2 существует, v1 никто не удаляет.** Без Sunset-политики держим обе версии вечно: двойная поддержка, двойное тестирование. Sunset — не опция, а обязательный заголовок на каждом deprecated-эндпоинте.

**Почему это важно архитектору:** версионирование — механизм обещания. «Мы не сломаем то, что ты используешь» — только если смены версии означают смену контракта, а не «вроде совместимо».

**Практический вывод для архитектора:** внешний API: `vN` в URL + Sunset-политика. Внутренний: header-версии или без версий (монорепо, разворачивается атомарно). Не смешивать: правила совместимости у них разные.

## 4. Пагинация

### Механика

Два механизма, разные задачи:

| Механизм | Применение | Риск |
|:--|:--|:--|
| offset/limit | UI, человеческие страницы, стабильные списки | пропуск/дубль при изменении данных между страницами |
| cursor (keyset) | выгрузки, инкрементальные синхронизации | требует стабильного ключа порядка |

Для 1С-интеграций (выгрузка тысяч дел, событий) — **cursor-based пагинация с инкрементальным фильтром**:

```text
GET /cases?updated_after=2026-08-01T00:00:00Z&limit=1000
  → { items: [...], next_cursor: "eyJ1cGRhdGVkX2F0Ijox..." }
GET /cases?cursor=eyJ1cGRhdGVkX2F0Ijox...&limit=1000
```

Курсор кодирует позицию `(updated_at, id)` — ключ, по которому стабильно сортируем:

```sql
-- Позиция курсора: (updated_at, id) — строгий порядок без дублей
SELECT * FROM cases
WHERE (updated_at, id) > ($1, $2)
ORDER BY updated_at, id
LIMIT $3;
```

Правила:

- **Cursor — непрозрачная строка.** Клиент не парсит и не строит курсоры, только возвращает `next_cursor`. Структура курсора зашифрована/подписана или просто закодирована — не контракт.
- **`limit` — с потолком.** Запросил 100000 — получи 1000 (или 5000). Потолок в контракте.
- **`next_cursor: null`** — конец выгрузки. Не `[]` последней страницы, а явный признак конца.
- **`total_count` — не бесплатно.** Для больших таблиц `COUNT(*)` дорогой; в выгрузках не нужен вовсе.

### Реализация: курсор-кодирование

```go
// Курсор = base64(JSON{updated_at, id}) — не секрет, но и не контракт
type cursorPayload struct {
    UpdatedAt time.Time `json:"u"`
    ID        int64     `json:"i"`
}

func encodeCursor(u time.Time, id int64) string {
    raw, _ := json.Marshal(cursorPayload{u.UTC(), id})
    return base64.RawURLEncoding.EncodeToString(raw)
}
```

### Граничные случаи — где ломается

**offset + изменяемые данные.** Список дел, статус меняется между страницами: страница 3 отдаёт элемент со страницы 2 (дубль) или теряет его (пропуск). Для UI терпимо, для выгрузки в 1С — рассинхрон справочника. Выгрузка — всегда cursor.

**Курсор по полю, которое меняется.** Если сортировка по `updated_at`, а строка обновилась после выдачи — курсорная позиция съезжает: строка может быть выдана дважды. Строгий порядок `(updated_at, id)` минимизирует, полное решение — сортировка по неизменяемому ключу (`created_at, id`) + отдельный фильтр изменений.

**Курсор устарел.** Пагинация на час-два, не на месяц: «продолжи вчерашнюю выгрузку» — это не про курсор, а про `updated_after` с нуля.

**Почему это важно архитектору:** пагинация — не «как разбить список», а механика передачи больших объёмов между системами. Ошибка пагинации = тихая потеря данных у потребителя (пропустил дело — не сделал иск).

**Практический вывод для архитектора:** UI — offset, выгрузки — cursor, инкрементальность — `updated_after` + порядок `(updated_at, id)`. Потолок limit, явный конец выгрузки, непрозрачные курсоры.

## 5. Ошибки и семантика статусов

### Механика

Контракт ошибки — плоский и стабильный (RFC 9457, но упрощённый для 1С):

```json
{
  "error": {
    "code": "CASE_NOT_FOUND",
    "message": "Дело 1-123/2026 не найдено в суде 77",
    "details": { "court_id": 77, "case_number": "1-123/2026" },
    "request_id": "8f4c-9a2b-4e1d-7c03"
  }
}
```

| Код | Семантика | Когда |
|:--|:--|:--|
| 400 | невалидный запрос | битый JSON, неизвестный параметр |
| 401 | нет/плохой ключ | заголовок отсутствует/невалиден |
| 403 | ключ валиден, прав нет | ресурс недоступен для роли |
| 404 | ресурс не существует | опечатка в id, удалён |
| 409 | конфликт состояния | дело уже существует с другим содержимым |
| 422 | валидация бизнес-правил | номер дела не прошёл нормализацию |
| 429 | rate limit | Retry-After обязателен |
| 5xx | ошибка сервера | 500/502/503 — retryable клиентом |

Ключевое:

- **`code` — машинный, стабильный.** `CASE_NOT_FOUND` не меняется никогда. `message` — человеческий, меняется свободно.
- **`request_id` в каждом ответе** (включая успешные) — мост между логом сервера и обращением клиента. 1С-разработчик присылает `request_id` в тикет — минус 30 минут разбора.
- **429 с `Retry-After`** — клиент ждёт указанное время, не экспоненту и не свои догадки.

### Реализация: единый хендлер ошибок

```go
type apiError struct {
    Code      string         `json:"code"`
    Message   string         `json:"message"`
    Details   map[string]any `json:"details,omitempty"`
    RequestID string         `json:"request_id"`
}

func writeError(w http.ResponseWriter, status int, code, msg string, details map[string]any) {
    w.Header().Set("Content-Type", "application/json; charset=utf-8")
    if status == http.StatusTooManyRequests {
        w.Header().Set("Retry-After", "60")
    }
    w.WriteHeader(status)
    json.NewEncoder(w).Encode(apiError{code, msg, details, requestID(r.Context())})
}
```

### Граничные случаи — где ломается

**200 с ошибкой внутри.** «Чтобы не смущать клиента» — антипаттерн: `{"success": false, "data": null}`. Потребитель обязан проверять `success` у каждого ответа; пропустил проверку — обработал ошибку как успех. Статусы HTTP для этого и существуют.

**Ошибка без деталей.** 400 без указания, какое поле невалидно: 1С-разработчик угадывает. `details` с машинным указанием поля (`{"field": "case_number", "reason": "unparseable"}`) превращает баг-репорты в фиксы.

**409 vs 422.** 422 — «запрос не может быть выполнен по данным» (повторный импорт с другим содержимым — конфликт), 409 — «состояние ресурса мешает» (дело закрыто, событие нельзя добавить). Путаница кодов = кривая обработка у клиента: он перестаёт различать retryable и не-retryable.

**Слишком разговорчивые 5xx.** Тело с трассировкой стека в ответе — утечка и мусор. 5xx — код + request_id, трассировка — в лог сервера.

**Почему это важно архитектору:** контракт ошибок — первое, что пишет потребитель, когда интеграция ломается. Хороший контракт ошибок сокращает среднее время починки интеграции с часов до минут.

**Практический вывод для архитектора:** стабильный машинный `code`, `request_id` везде, честные статусы, `Retry-After` на 429, детали валидации в `details`. Никогда — 200 с ошибкой внутри.

## 6. Идемпотентность

### Механика

Идемпотентность — свойство операции: повторное выполнение даёт тот же результат, что первое. Она обязательна для интеграций, потому что сеть не гарантирует доставки ответа: клиент отправил POST, ответ потерялся, клиент **обязан** повторить — иначе данные разъедутся.

```text
1С:  POST /import/cases  →  сервер создал 50 дел → ответ потерялся
1С:  повторный POST (тот же ключ) → сервер НЕ создаёт дубли → 200 + статус «уже обработано»
```

Три уровня идемпотентности:

| Уровень | Механизм | Применение |
|:--|:--|:--|
| Идемпотентный метод | GET, PUT, DELETE по природе | чтение, полная замена, удаление |
| Бизнес-ключ | уникальность `(court_id, case_number)` | импорт сущностей по естественному ключу |
| Idempotency-Key | заголовок с ключом операции | произвольные POST (импорт пачки, генерация документов) |

### Бизнес-ключ — дефолт для импорта

Из модуля 49: уникальность `(court_id, case_number)` — констрейнт в БД. Импорт дел использует его как идемпотентный ключ:

```sql
-- INSERT ... ON CONFLICT — идемпотентный импорт на уровне БД
INSERT INTO cases (court_id, case_number, status)
VALUES ($1, $2, $3)
ON CONFLICT (court_id, case_number)
DO UPDATE SET status = EXCLUDED.status, updated_at = now()
RETURNING id;
```

Повторная выгрузка из 1С не плодит дубли: та же строка обновляется. Это «импотентность по содержимому»: повторный импорт идентичных данных — no-op.

### Idempotency-Key для произвольных операций

```text
POST /import/cases
Idempotency-Key: 7f3c-2026-08-06-001
```

Сервер хранит результат по ключу (TTL 24–48 ч): повторный запрос с тем же ключом возвращает сохранённый результат, не выполняя операцию. Ключ генерирует клиент (1С: «выгрузка-дата-номер»), гарантируя уникальность в рамках отправителя.

### Граничные случаи — где ломается

**Retry после таймаута.** Самый частый сценарий: ответ потерялся, клиент ретраит. Без идемпотентности — дубли на сервере, которые потребитель не видит до сверки. Идемпотентность — не «плюшка», а требование к любой POST-операции интеграции.

**Частичный импорт пачки.** Пачка из 1000 дел, 400-е падает: что с остальными? Два подхода: (а) пачка атомарна — всё или ничего, (б) пачка поэлементна — отчёт об ошибках per-item. Для 1С-выгрузок (б) практичнее: один битый номер не блокирует остальные 999. Контракт: `{"processed": 999, "failed": [{"index": 400, "code": "CASE_NUMBER_INVALID"}]}`.

**ON CONFLICT не про «не трогать».** Если повторный импорт обновляет `status`, клиент может перезаписать более свежие данные своим старым статусом. Решение — только insert-if-not-exists для неизменяемых сущностей, update только для управляемых клиентом полей.

**Почему это важно архитектору:** без идемпотентности любая повторная выгрузка — рулетка: дубли дел, двойные документы, задвоенные события. В судебном контексте дубль — не «шум», а риск неправильного действия по делу.

**Практический вывод для архитектора:** каждый POST интеграции отвечает на вопрос «что будет при повторном вызове?». Ответ: констрейнт бизнес-ключа, Idempotency-Key или явная ошибка 409. Тишина в этом вопросе = дубли в production.

## 7. Интеграция с 1С: специфика потребителя

### Механика

1С:Предприятие — не «ещё один HTTP-клиент». Его особенности определяют контракт:

**Форматы данных.** 1С исторически работает с датами как `DD.MM.YYYY` и числами с запятой и пробелами-разделителями. REST/JSON должен принимать и отдавать нормализованные форматы, а нормализацию «человеческих» форм делать в сервисном слое (из практики модуля 17 — 1С-строки «1 234,56», даты-строки):

```go
// Сервисный слой нормализует вход, а не контракт
func parseRusDecimal(s string) (float64, error) {
    s = strings.ReplaceAll(s, " ", "")
    s = strings.ReplaceAll(s, "\u00A0", "") // неразрывный пробел
    s = strings.ReplaceAll(s, ",", ".")
    return strconv.ParseFloat(s, 64)
}
```

**Кодировки при файловом обмене.** При передаче файлов (XLSX-выгрузки, CSV) — Windows-1251 по умолчанию у 1С-сторон (практика: ГАС/1С-источники в CP1251, модуль knowledge cp1251-gas). Контракт: файлы отдаём в UTF-8 и явно помечаем (`charset=utf-8`), а принимаем с детектом кодировки.

**Батчевый характер.** 1С-интеграции — регламентные задания: раз в час/сутки выгрузить изменения. Отсюда требования: курсорная выгрузка (§4), идемпотентный импорт (§6), лимиты на размер ответа.

**Простота контракта.** 1С-разработчик пишет код без кодогенерации OpenAPI-клиентов. Чем площе JSON, тем меньше ошибок на его стороне: плоские объекты, без вложенных на 5 уровней, enum-строки, а не числа, даты в ISO 8601 (`2026-08-06T10:00:00Z`) — единый формат, который 1С умеет разбирать в `Дата` через конвертацию.

### Реализация: плоский ответ для 1С

```json
{
  "id": 84921,
  "court_id": 77,
  "case_number": "1-123/2026",
  "status": "active",
  "created_at": "2026-08-06T10:00:00Z",
  "updated_at": "2026-08-06T10:00:00Z",
  "participants_count": 3
}
```

Вместо `{"court": {"id": 77, "name": "..."}}` — плоский `court_id` + `court_name` (денормализация для чтения, из модуля 49: «денормализуй по измеренной проблеме» — потребитель не делает JOIN).

### Граничные случаи — где ломается

**Дата-строка в ответе.** Отдавать `created_at` строкой `"2026-08-06"` — клиент не знает, в какой timezone. ISO 8601 с `Z` — однозначно. 1С-сторона конвертирует в свою `Дата` с учётом зоны.

**Числа деньгами.** Цены, суммы штрафов — `FLOAT` в JSON теряет точность. Контракт: суммы — строки в рублях с двумя знаками или целые копейки, никогда не float.

**Русские имена полей.** `номер_дела` вместо `case_number` — выглядит «удобно для 1С», но ломает генерацию клиентов, язык контракта, и не помогает: 1С всё равно мапит поля на свои реквизиты. Язык контракта — английский, маппинг — на стороне потребителя.

**Большой ответ.** 1000 дел × 2 КБ = 2 МБ — 1С-клиент с таймаутом 30 сек может не успеть. Пагинация с потолком лимита (§4) + `limit` по умолчанию — не «чтобы все влезло», а «чтобы успело».

**Почему это важно архитектору:** контракт пишется для конкретного класса потребителей. 1С-потребитель прощает меньше: его код — не дженерики, его среда — не гибкая. Простота контракта — это надёжность интеграции.

**Практический вывод для архитектора:** плоские объекты, ISO-даты, строковые суммы, англоязычные поля, батчевые паттерны (курсор, идемпотентность), нормализация «человеческих» форматов на сервере. Форматы и кодировки — часть контракта, а не «мелочь для 1С».

## 8. Безопасность: ключи, rate limits, исходящие URL

### Механика

**API-ключи, не JWT.** Для сервис-интеграций (1С, скрипты, cron) — простые ключи в заголовке:

```text
Authorization: Bearer cdsk_9f2e4a7c8b1d3f6e5a0c2b4d8f1e3a5c
```

JWT оправдан для интерактивных пользователей (SSO, short-lived), для регламентных заданий — лишний механизм: нет refresh-цикла у 1С, ключ хранится в конфиге. Ключи: длинные, случайные (≥ 32 байт), с префиксом ресурса (`cdsk_`), ротация без разрыва (два активных ключа, см. модуль 11 — Key Rotation).

**Rate limiting по ключу** — обязателен: справочник дел не должен быть выкачан одним регламентным заданием за минуту. Заголовки:

```text
X-RateLimit-Limit: 600
X-RateLimit-Remaining: 342
X-RateLimit-Reset: 60
```

429 с `Retry-After` (§5) — 1С-задание спит и продолжает с курсора.

**Исходящие URL — SSRF-урок.** API принимает URL? (например, импорт документов по ссылке, callback-уведомления) — это инструмент типа `fetch_page` из модуля 47. Прод-инцидент CourtDesk: fetch-инструмент с непроверенным URL дёргал внутренние адреса. Правила:

- URL-allowlist доменов (суды, официальные порталы);
- запрет private/loopback/link-local диапазонов IP (10/8, 172.16/12, 192.168/16, 127/8, 169.254/16, ::1, fe80::/10);
- DNS-pinning: резолвить, валидировать IP, ходить по IP.

```go
// Проверка входящего URL перед fetch (фрагмент, net/netip)
func validateFetchURL(raw string) error {
    u, err := url.Parse(raw)
    if err != nil || (u.Scheme != "https" && u.Scheme != "http") {
        return errors.New("bad URL")
    }
    if !allowedHost(u.Hostname()) { // allowlist доменов судов
        return errors.New("host not allowed")
    }
    for _, ip := range resolveAll(u.Hostname()) {
        if ip.IsPrivate() || ip.IsLoopback() || ip.IsLinkLocalUnicast() {
            return errors.New("private IP blocked")
        }
    }
    return nil
}
```

### Граничные случаи — где ломается

**Ключ в логах.** 1С-клиент отправил ключ, шлюз залогировал заголовки — ключ в логе навсегда. Политика: никогда не логировать `Authorization`, маскировка в access-логах.

**Ключ в конфиге 1С у клиента.** Компрометация конфига = ключ ушёл. Ротация ключей — процесс, а не инцидент: регламентная ротация раз в N месяцев, два активных ключа для бесшовного перехода.

**Rate limit на запись, не только чтение.** Импорт с багом 1С (зациклилось регламентное задание) долбит POST-эндпоинты. Отдельные лимиты на read и write; write-лимиты жёстче.

**Внутренние эндпоинты без авторизации.** `/health`, `/metrics`, `/admin/*` в том же порту, что и публичный API — первый шаг к перебору. Внутреннее — отдельный порт/сеть, никогда не в публичном контракте.

**Почему это важно архитектору:** API-безопасность — это про границы: ключи ограничивают потребителей, allowlist ограничивает исходящие вызовы, rate limits ограничивают вред от ошибок. SSRF-инцидент в 47 — живое подтверждение, что URL-валидация — не теоретическая забота.

**Практический вывод для архитектора:** API-ключи с префиксом и ротацией, rate limits по ключу с честными заголовками, allowlist + private-range-блокировка для исходящих URL, внутренние эндпоинты — вне публичного порта, ключи — никогда в логи.

## 9. Реальный кейс: CourtDesk API для 1С

### Контекст

CourtDesk — система мониторинга судебных дел: сбор карточек дел с сайтов судов, события, документы (PDF), хранение в PostgreSQL (схема из модуля 49: `courts`, `cases`, `case_events`, `case_participants`). Потребитель — 1С:Предприятие клиента: регламентное задание выгружает изменения по делам, загружает документы в справочники, передаёт события для юридического учёта.

### Задача

Спроектировать внешний REST API для 1С: ~26 эндпоинтов — справочники, дела, события, документы, выгрузки изменений, импорт. Требования: регламентная синхронизация без потерь, повторяемость (ретраи после сетевых сбоев), работа с объёмами (тысячи дел, документы в PDF).

### Гипотеза

Классический REST: ресурсы по домену, cursor-пагинация для выгрузок, идемпотентность через бизнес-ключ, версия в URL. 1С-потребитель — регламентный, значит, основная нагрузка — `updated_after`-выгрузки, а не поиск.

### Карта API (обобщённая, для сверки)

```text
/v1
├── /courts                          — справочник судов (ГАР)
│   └── /{id}
├── /cases                           — дела: поиск, список, выгрузка изменений
│   ├── /{id}
│   ├── /{id}/events                 — события по делу
│   ├── /{id}/participants           — участники
│   └── /{id}/documents              — документы дела
├── /events                          — глобальная выгрузка событий
├── /documents                       — документы: список, содержимое
│   └── /{id}/content                — PDF-файл
├── /import/cases                    — идемпотентный импорт дел
├── /import/cases/{id}/documents     — импорт документов (PDF)
└── /import/cases/{id}/events        — импорт событий
```

> ⚠️ Требует сверки: реальный состав 26 эндпоинтов (имена, подресурсы, RPC-операции) может отличаться. Список выше — рабочий прототип по домену из модулей 49/16/47.

### Что получилось

**Работало как ожидалось:**

- `updated_after`-выгрузка с курсором `(updated_at, id)` — регламентное задание 1С забирает изменения за интервал без пропусков и дублей;
- импорт дел по бизнес-ключу `(court_id, case_number)` — повторные выгрузки после сетевых сбоев не плодят дубли (ON CONFLICT);
- документы по `GET /documents/{id}/content` с `Content-Type: application/pdf` — 1С кладёт файл в хранилище через штатное `ДвоичныеДанные`;
- плоский JSON: `court_id` + `court_name` — 1С-разработчик не делает JOIN-ов, а пишет прямой маппинг на реквизиты.

**Грабли (реальные, из практики):**

1. **SSRF-эндпоинт импорта по URL** (из инцидента в модуле 47): эндпоинт приёма документов по внешней ссылке без allowlist и проверки private-диапазонов. Закрыто: allowlist доменов + блокировка private IP + DNS-pinning. Урок: эндпоинты, принимающие URL, — это инструменты fetch, и валидация у них та же, что у агентских tools.

2. **Номера дел в пути ломали маршрутизацию.** Попытка `GET /cases/1-123/2026` — два сегмента пути, `%2F` не проходит через прокси. Решение: числовой id в пути, номер — нормализованный в query (`?number=1-123/2026`).

3. **Форматы из 1С:** выгрузка приносила даты `06.08.2026`, суммы «1 234,56 ₽». Нормализация на сервисном слое, контракт отдаёт ISO 8601 и строки-суммы. Без нормализации — мусорные даты в базе и «сумма не сошлась» у клиента.

4. **Даты-строки в 1С-сторону:** первый релиз отдавал `created_at` в местном времени без зоны — 1С-клиент трактовал по своей. Переход на ISO 8601 UTC (`Z`) закрыл расхождение.

5. **Потерянный ответ регламентного задания.** 1С отправила импорт, ответ потерялся, задание повторило — пока не пришёл ON CONFLICT и обработка 409, дубли плодились. Идемпотентность — не «дополнительно», а первое требование к POST.

### Вывод, противоречащий интуиции

Самые дорогие проблемы интеграции оказались не в архитектуре API (ресурсы, версии), а в **форматах данных и поведении при повторах** — том, что выглядит «мелочью» в прототипе. API с идеальной ресурсной моделью, но датой без зоны и неидемпотентным импортом, — интеграция, которая не работает в production.

Второй вывод: версия в URL и курсорная пагинация окупились в первый же месяц — 1С-клиент не обновлялся, а выгрузки работали без участия разработчика. Контрактные решения на годы важнее скорости первой интеграции.

**Практический вывод для архитектора:** проектируй контракт от реального сценария потребителя (регламент, ретраи, форматы), а не от красивой ресурсной модели. Идемпотентность и нормализация входных данных — часть контракта.

## 10. Антипаттерны

### «200 OK с ошибкой внутри»

**Выглядит правильно:** «мягкая» обработка, клиент не падает.

**Почему ошибка:** каждый потребитель обязан проверять `success`; тот, кто пропустил, молча обрабатывает ошибку как данные. В судебной интеграции это означает «дело не создано, а 1С считает, что создано». HTTP-статусы — контракт, не украшение.

---

### «Пагинация offset для всего»

**Выглядит правильно:** проще для UI и понимания.

**Почему ошибка:** при изменении данных между страницами — пропуски и дубли. Для регламентной выгрузки в 1С это тихая потеря дел. Выгрузка — курсор, UI — offset, не наоборот.

---

### «Эндпоинт принимает URL — пусть клиент сам передаст валидный»

**Выглядит правильно:** гибко, клиент знает свои источники.

**Почему ошибка:** SSRF. Эндпоинт с URL — это fetch-инструмент: без allowlist и блокировки private-диапазонов он ходит по внутренней сети (реальный инцидент — модуль 47).

---

### «Версия только в заголовке»

**Выглядит правильно:** URL чистые.

**Почему ошибка:** заголовки не видны в логах прокси, старые HTTP-клиенты их не шлют, в конфиге 1С версия незаметна. Внешняя интеграция — версия в URL.

---

### «Строгий enum, который расширяем»

**Выглядит правильно:** «мы добавили значение, ничего не сломали».

**Почему ошибка:** 1С-клиент с `Если Статус = "closed" Тогда` молча игнорирует новые значения. Расширение enum — это ломающее изменение для строгих потребителей, пока контракт не обязывает обрабатывать unknown.

---

### «Документация вместо контракта»

**Выглядит правильно:** «вот README с описанием API».

**Почему ошибка:** README — не контракт: расходится с реальностью, не проверяется тестами, не читается машинами. Контракт — спецификация + контрактные тесты в CI.

## Anti-checklist ☠️

- [ ] 200 OK с ошибкой внутри — потребитель молча обработает ошибку как данные
- [ ] offset-пагинация для выгрузок — пропуски/дубли при изменении данных
- [ ] POST без идемпотентности — ретрай после потерянного ответа плодит дубли
- [ ] Дата без зоны в контракте — 1С-клиент трактует по своему часовому поясу
- [ ] Эндпоинт с URL без allowlist и private-range-проверки — SSRF
- [ ] Версия в заголовке для внешнего API — не видна в логах и конфиге потребителя
- [ ] Enum-расширение без контракта на unknown-значения — строгие клиенты теряют данные
- [ ] Суммы как FLOAT в JSON — потеря копеек на больших числах

## Задачи AI-кодеру

**Задача 1 — Контракт и версионирование**

Плохая формулировка:
> «Сделай API для дел суда»

Хорошая формулировка:
> «Спроектируй OpenAPI 3.1 контракт для модуля CourtDesk: ресурсы `courts`, `cases`, `case_events`, `case_participants`, `documents`. Все пути под префиксом `/v1`. Версия в URL, не в заголовке. Для каждого ресурса — GET списка (пагинация cursor, query-параметры `limit` ≤ 1000, `cursor`, `updated_after`), GET по id, POST создания с идемпотентностью по бизнес-ключу `(court_id, case_number)`. Опиши схему ошибки: `{code, message, details, request_id}`. Проверь линтером (@redocly/cli lint).»

Формула: конкретные ресурсы + версия в URL + пагинация + идемпотентность + контракт ошибок + линтер.

---

**Задача 2 — Идемпотентный импорт**

Плохая формулировка:
> «Добавь импорт дел из 1С»

Хорошая формулировка:
> «Реализуй POST /v1/import/cases на Go: принимает пачку из N дел (N ≤ 500), каждое: `court_id`, `case_number`, `status`. Идемпотентность: `INSERT ... ON CONFLICT (court_id, case_number) DO UPDATE SET status = EXCLUDED.status` (модуль 49, констрейнт). Ответ: `{processed: int, failed: [{index, code, message}]}` — ошибка одного дела не роняет пачку. Поддержка заголовка `Idempotency-Key` с TTL-кэшем результата 24 часа. Тесты: повторный POST той же пачкой не создаёт дублей.»

Формула: эндпоинт + бизнес-ключ + partial failure + Idempotency-Key + тест на дубли.

---

**Задача 3 — Контракт ошибок**

Плохая формулировка:
> «Сделай нормальные ошибки в API»

Хорошая формулировка:
> «Реализуй единый обработчик ошибок: структура `{code, message, details, request_id}`, статусы по семантике (400 — валидация, 404 — нет ресурса, 409 — конфликт состояния, 422 — бизнес-валидация, 429 — rate limit с `Retry-After`), `request_id` из контекста запроса в каждом ответе (включая успешные), трассировка стека только в лог. Покрой тестами: 404 для несуществующего дела, 429 с заголовком Retry-After.»

Формула: структура + семантика статусов + request_id + тесты.

---

**Задача 4 — Безопасность URL-импорта**

Плохая формулировка:
> «Добавь импорт документов по ссылке»

Хорошая формулировка:
> «Реализуй POST /v1/import/cases/{id}/documents с полем `source_url`. Валидация: только https, allowlist доменов судов из конфига, резолв DNS с проверкой — все IP не private/loopback/link-local (169.254/16, 10/8, 172.16/12, 192.168/16, ::1, fe80::/10), fetch по IP с DNS-pinning, лимит размера 20 МБ. Ошибки — коды `URL_BLOCKED`, `URL_DOWNLOAD_FAILED`. Напиши тесты на private-IP-домен и redirect на внутренний адрес (SSRF).»

Формула: валидация URL + private-range + DNS-pinning + лимиты + SSRF-тесты.

## Чеклист архитектора

### Контракт
- [ ] OpenAPI 3.1 — единственный source of truth, контрактные тесты в CI
- [ ] Поля только добавляются; семантические изменения — новая версия
- [ ] Плоские объекты, ISO 8601 UTC, суммы — строки/копейки, поля на английском
- [ ] Enum-расширение согласовано с обработкой unknown-значений

### Версионирование
- [ ] Версия в URL (`/v1`), политика deprecation (Sunset ≥ 12 мес)
- [ ] Заголовки `Deprecation`/`Sunset` на старых эндпоинтах
- [ ] Шлюз логирует клиентов на старых версиях

### Пагинация
- [ ] UI — offset, выгрузки — cursor
- [ ] Порядок строгий: `(updated_at, id)`, курсор непрозрачен для клиента
- [ ] Потолок limit, `next_cursor: null` — явный конец

### Ошибки
- [ ] Стабильный машинный `code`, человеческий `message`
- [ ] `request_id` в каждом ответе
- [ ] 429 всегда с `Retry-After`, никогда 200 с ошибкой внутри

### Идемпотентность
- [ ] Каждый POST отвечает на «что при повторе?»
- [ ] Импорт — по бизнес-ключу (ON CONFLICT), произвольные операции — Idempotency-Key
- [ ] Partial failure пачки: per-item отчёт, не «всё или ничего»

### Безопасность
- [ ] API-ключи (≥ 32 байта, префикс, ротация с двумя активными)
- [ ] Rate limits по ключу, read/write раздельно
- [ ] URL-эндпоинты: allowlist + private-range + DNS-pinning
- [ ] Authorization не логируется; внутренние эндпоинты — отдельный порт
