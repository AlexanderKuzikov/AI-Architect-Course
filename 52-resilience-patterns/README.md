> **Для AI-архитектора:** надёжность — не «пережить отказ», а пережить отказ незаметно для остальной системы. ## 1. Карта resilience-паттернов

### Механика

Resilience-паттерны отвечают на разные вопросы отказа:

| Паттерн | Вопрос | Ответ |
|:--|:--|:--|
| Timeout | «Как долго ждать?» | жёсткий лимит на каждый вызов и весь запрос |
| Retry | «Что делать при сбое?» | повторить с backoff + jitter, в рамках бюджета |
| Circuit Breaker | «Стоит ли вообще пытаться?» | отключить вызовы к падающему сервису |
| Bulkhead | «Как не дать одному сбою убить всех?» | изолированные пулы ресурсов |
| Rate Limiting | «Как не убить downstream?» | ограничить частоту исходящих |
| Saga | «Как откатить распределённую операцию?» | компенсации вместо транзакции |
| Fallback | «Что отдать при отказе?» | деградированный, но работающий ответ |

Порядок применения на пути запроса:

```text
Request → Timeout → Rate Limit → Bulkhead → Retry (снаружи CB)
     → Circuit Breaker → Call downstream → Fallback
```

Ключевое правило связки: **паттерны должны быть упорядочены, а не наложены хаотично**. Retry внутри circuit breaker скрывает ошибки от счётчика (модуль 19 §6); rate limit без backoff на downstream создаёт шторм; bulkhead без таймаутов копит занятые слоты.

### Где в курсе лежит основа

| Модуль | Что даёт |
|:--|:--|
| 19 | HTTP-клиенты: retry-стратегии, circuit breaker, connection pooling |
| 23 | Rate limiting: token bucket, лимиты на клиенте и шлюзе |
| 18 | Очереди, DLQ, graceful shutdown |
| 11 | Key rotation и fallback pools для AI API |
| 51 | Идемпотентность — фундамент для Saga-компенсаций |

Этот модуль собирает паттерны в целостную систему и добавляет недостающее: bulkhead, saga, retry storm.

### Граничные случаи — где ломается

**«Навесить все паттерны на каждый вызов».** Куча middleware замедляет и запутывает: ретрай во внутреннем вызове + ретрай на шлюзе = экспонента повторов (retry-бабочка). Паттерны назначаются по слою: транспортный — retry/backoff, сервисный — CB/bulkhead, оркестрация — saga.

**«Отказ одного сервиса маскируется ретраями».** Если downstream лежит 10 минут, retry-пакет 5 попыток превращает 10 минут простоя в 10 минут бесполезных запросов, усиливающих нагрузку. Retry лечит кратковременные сбои (секунды), не лечит длительные.

**Почему это важно архитектору:** resilience — системное свойство, а не коллекция библиотек. Каждый паттерн имеет зону ответственности; пересечение зон — источник каскадных отказов.

**Практический вывод для архитектора:** сначала определи сценарии отказа (отказ сервиса, перегрузка, медленный ответ, сетевой сбой) — потом назначай паттерны. Начинай с таймаутов: без них остальные паттерны бессмысленны.

## 2. Timeout и cancellation — фундамент

### Механика

Без таймаута любой другой паттерн бессмысленен: retry повисает на мёртвом соединении, bulkhead-слот занят вечно, saga ждёт ответа компенсации.

Три уровня таймаута:

| Уровень | Где | Зачем |
|:--|:--|:--|
| Соединение | транспорт (dial) | не ждать TCP-handshake вечно |
| Вызов | один запрос | не ждать ответ вечно |
| Общий | весь pipeline | не держать ресурсы сверх лимита |

```go
// Go 1.26: context распространяется на все вызовы
ctx, cancel := context.WithTimeout(r.Context(), 5*time.Second)
defer cancel()

req, _ := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
resp, err := http.DefaultClient.Do(req)
if errors.Is(ctx.Err(), context.DeadlineExceeded) {
    // ✅ таймаут — отделяемый сбой: ретраить можно
}
```

```typescript
// Node.js 24: AbortSignal.timeout
const resp = await fetch(url, { signal: AbortSignal.timeout(5_000) });
```

### Граничные случаи — где ломается

**Таймаут на каждый уровень, а не только на внешний вызов.** Внутренний вызов БД без таймаута при падении БД держит воркер вечно; внешний таймаут запроса не спасает — ресурс уже занят. Deadline распространяется по context сверху вниз, лимиты — на каждом уровне.

**Таймаут больше, чем у клиента.** 1С-клиент ждёт 30 секунд, серверный вызов — 60: клиент уходит по таймауту, а сервер продолжает работу (запрос-призрак). Общий таймаут сервера ≤ таймаута потребителя.

**Таймаут — не отмена работы.** Обработка тяжёлой задачи в фоне: клиент отключился, но работа должна продолжаться. Отдельно: таймаут ожидания ответа, отдельно — жизненный цикл задачи (очередь, модуль 18).

**Почему это важно архитектору:** таймауты — единственная защита от «медленного отказа» (slow degradation), который не виден в мониторинге ошибок: запросы не падают, они копятся. Без таймаутов система умирает от накопления висящих запросов.

**Практический вывод для архитектора:** `context`/`AbortSignal` пронизывают весь стек. Общий бюджет запроса меньше суммы компонентов (клиентский таймаут — верхняя граница). Начинай проектирование resilience с таблицы таймаутов, а не с retry.

## 3. Retry: политики и Retry Storm

### Механика

Retry лечит сбои, которые проходят сами: 429 (перегрузка), 502/503/504 (шлюз/перегрузка), сетевые обрывы. 4xx (кроме 408/429) — не ретраить: повтор не изменит ответ.

```typescript
// Политика: exponential backoff + full jitter (Node.js 24)
function retryDelay(attempt: number): number {
  const base = Math.min(1000 * 2 ** attempt, 10_000); // 1s → 2s → 4s → 8s → 10s cap
  return Math.floor(Math.random() * base);           // full jitter [0..base)
}

const retryable = (status: number) =>
  status === 408 || status === 429 || status >= 500;

async function callWithRetry(fn: () => Promise<Response>, maxAttempts = 4) {
  for (let attempt = 0; ; attempt++) {
    const resp = await fn();
    if (resp.status < 500 && resp.status !== 408 && resp.status !== 429) return resp;
    if (attempt >= maxAttempts - 1) return resp;
    if (resp.status === 429) {
      const after = Number(resp.headers.get('retry-after'));
      await sleep(Number.isFinite(after) ? after * 1000 : retryDelay(attempt));
    } else {
      await sleep(retryDelay(attempt));
    }
  }
}
```

**Retry-бюджет:** не «сколько попыток», а «сколько суммарного времени и запросов мы готовы потратить». `maxAttempts × maxDelay` — бюджет; для AI-пайплайнов с лимитами (модуль 11) бюджет критичен: 5 попыток × 10 секунд — полминуты на одну задачу.

### Retry Storm — почему каскад ретраев убивает систему

Сценарий: сервис B лёг. Десять клиентов A1..A10 ретраят с одинаковым интервалом → пики запросов в одни и те же моменты → B не восстанавливается → больше клиентов видят ошибки → шторм.

```
t=0   B упал
t=1s  A1..A10 ретраят одновременно (10 запросов)
t=2s  A1..A10 ретраят одновременно (пик)
t=4s  пик снова — B не успевает ответить ни на один запрос
```

Три обязательных компонента против шторма:

1. **Jitter** — рандомизация интервала. Без jitter ретраи синхронизируются, с jitter — размазываются.
2. **Один ретрай-слой.** Ретрай на клиенте + ретрай на шлюзе + ретрай в очереди = произведение попыток. Разрешить ретрай только на одном уровне, остальные — нет (или трейс `Retry-Count`).
3. **Уважение `Retry-After`.** Сервер явно сказал «подожди 60 секунд» — клиент ждёт 60 секунд, а не свой backoff.

### Граничные случаи — где ломается

**429 без Retry-After.** Интервал — собственный backoff с джиттером, но НЕ быстрый retry: 429 означает «тебя лимитят», быстрые повторы усугубляют.

**Retry неидемпотентного запроса.** POST без идемпотентности (модуль 51) при ретрае плодит дубли. Ретрай POST — только с Idempotency-Key или бизнес-ключом.

**Слишком большой retry-бюджет.** «Пять попыток на каждый запрос, 50 запросов» = 250 исходящих при падении downstream. Потолок бюджета в единицах «сколько трафика готов отдать» — параметр архитектуры, не библиотеки.

**Почему это важно архитектору:** retry — самый «успешный» по применению и самый опасный паттерн: в одиночку он лечит, в связке без джиттера — убивает. Retry storm — классический каскадный отказ, который начинается с «мы добавили повтор при ошибке».

**Практический вывод для архитектора:** retry с exponential backoff + full jitter, Retry-After первичен, один ретрай-слой на пути, бюджет в попытках и времени, ретрай только идемпотентных операций, ретрай снаружи circuit breaker.

## 4. Circuit Breaker: защита от каскадов

### Механика

Circuit breaker отвечает на вопрос «стоит ли пытаться?» — и после серии отказов отвечает «нет», быстро (fail fast), не тратя ресурсы на обречённые попытки.

```
CLOSED ──(ошибки > порога)──► OPEN ──(таймаут)──► HALF_OPEN
   ▲                                                  │
   └────────────(успех)───────────────────────────────┘
   ┌────────────(ошибка)──────────────────────────────┘
```

| Состояние | Поведение |
|:--|:--|
| CLOSED | запросы идут, ошибки считаются |
| OPEN | мгновенный отказ (fail fast), запросы не идут |
| HALF_OPEN | пробный запрос: успех → CLOSED, ошибка → OPEN |

Параметры: порог ошибок (например, 50% за 30 секунд, минимум 10 запросов — чтобы не сработал на одном сбое), таймаут открытого состояния (5–30 сек), пробные запросы (1–3).

```typescript
// opossum 8.x: обёртка вокруг вызова
import CircuitBreaker from 'opossum';

const cb = new CircuitBreaker(fetchCase, {
  timeout: 5_000,
  errorThresholdPercentage: 50, // 50% ошибок за окно
  rollingCountTimeout: 30_000,
  rollingCountMinimums: 10,     // минимум запросов для срабатывания
  resetTimeout: 15_000,         // HALF_OPEN через 15 сек
});

// ✅ Fallback при OPEN — задеградированный ответ вместо ошибки
cb.fallback(() => ({ degraded: true, source: 'cache' }));
```

### Связка с retry — порядок критичен (модуль 19 §6)

```text
❌ retry ВНУТРИ circuit breaker:
   CB не видит реальных ошибок (клиент их скрывает) → порог не сработает

✅ retry СНАРУЖИ CB:
   CB видит каждую попытку → OPEN отключает даже ретраи → fail fast
```

### Граничные случаи — где ломается

**CB на нестабильном, но не «мёртвом» сервисе.** 429 от rate limit тоже считаются ошибками — CB откроется из-за перегрузки, хотя сервис жив (модуль 19: реальный случай). Разделяй: 429 — не ошибка CB, а сигнал сбросить backoff; 5xx — ошибка CB.

**HALF_OPEN с одним пробным запросом.** Один пробный запрос — шум: на удаче — открытие шлюза для потока. Несколько пробных (1–3%) с ограничением числа параллельных.

**CB на клиенте, а не на каждом слое.** CB защищает одного клиента. Шлюз с собственным CB защищает downstream от всех клиентов сразу. Для «не убить внешний сервис» (судебные сайты) CB — на шлюзе/оркестраторе, а не в каждом воркере.

**Почему это важно архитектору:** CB превращает «сервис лежит, все ждут таймауты» в «сервис лежит, вызовы мгновенно отклоняются» — downstream получает передышку, а клиент — быстрый fallback. Это разница между минутой и часами простоя.

**Практический вывод для архитектора:** CB — на границе к нестабильному downstream, с минимальным порогом запросов, раздельной семантикой 429/5xx, fallback-ответом при OPEN. Retry — снаружи, никогда внутри.

## 5. Bulkhead: изоляция потребителей

### Механика

Bulkhead (переборка) — изоляция ресурсов между потребителями: отказ или перегрузка одного сегмента не истощает ресурсы других. В корабле отсеки герметичны; в системе — пулы.

```
❌ Общий пул:
   [UI клиент]──┐
   [1С задание]─┼─► Общий пул (50 слотов) ─► DB + CourtAPI
   [Парсер]─────┘
   1С-выгрузка 10k дел заняла все 50 слотов → UI отвечает секундами

✅ Bulkhead:
   [UI клиент]──► пул UI (10 слотов)
   [1С задание]─► пул 1С (30 слотов)
   [Парсер]─────► пул парсера (10 слотов)
   Изоляция: перегрузка парсера не влияет на UI и 1С
```

Реализация — семифор/канал на сегмент:

```go
// Go: bulkhead через каналы-семафоры
type Bulkhead struct {
    slots chan struct{}
}

func NewBulkhead(size int) *Bulkhead {
    return &Bulkhead{slots: make(chan struct{}, size)}
}

func (b *Bulkhead) Run(ctx context.Context, fn func() error) error {
    select {
    case b.slots <- struct{}{}:
        defer func() { <-b.slots }()
        return fn()
    case <-ctx.Done():
        return ErrBulkheadFull // или ожидание с таймаутом — по контракту
    }
}
```

Ключевое: **слот занят только во время выполнения, а не ожидания**. Без таймаутов (§2) bulkhead-слоты заполняются висящими запросами — изоляция превращается в общий отказ.

### Где переборки: размеры пулов

| Потребитель | Размер | Обоснование |
|:--|:--|:--|
| UI-запросы | малый (10) | интерактив, SLA важен |
| Регламентные задания (1С) | большой (30) | батчи, терпим к latency |
| Фоновый парсер (суды) | малый (3–5) | downstream судов лимитит (429) |

### Граничные случаи — где ломается

**Слот без таймаута.** Bulkhead-очередь без таймаута ожидания: запросы копятся в очереди, сегмент «забит» при живых слотах. Ожидание слота — с таймаутом: `ErrBulkheadFull` → fail fast или очередь с лимитом.

**Bulkhead вместо rate limit.** Bulkhead ограничивает параллельность, не частоту. Парсер с bulkhead 5 и быстрыми запросами всё равно шлёт 5 req/s — суд банит. Нужен и bulkhead, и rate limit (§6).

**Переборки по числу клиентов, а не по нагрузке.** Два клиента не означают два сегмента: «1С выгрузка» и «парсер судов» конкурируют за БД и внешние API. Переборки — по конкурирующим ресурсам, не по источнику запроса.

**Почему это важно архитектору:** bulkhead — защита качества сервиса для всех, когда кто-то один плохо себя ведёт. В судебном сборе парсер с десятками воркеров без переборки съедает пул целиком — и юридический UI клиента падает вместе с ним.

**Практический вывод для архитектора:** переборки по конкурирующим ресурсам (БД, внешний API, GPU), слот = время выполнения, ожидание слота — с таймаутом, совместно с rate limit, а не вместо.

## 6. Rate Limiting как защита downstream

### Механика

Rate limit защищает **другое** звено: downstream от перегрузки нашим трафиком, а не нас от злоупотреблений (модуль 23 — токен-баскет на клиенте и шлюзе).

```go
// Токен-баскет для исходящих запросов (пример, на Redis — общий для воркеров)
type TokenBucket struct {
    capacity float64
    tokens   float64
    rate     float64 // токенов/сек
    last     time.Time
    mu       sync.Mutex
}

func (b *TokenBucket) Take() bool {
    b.mu.Lock()
    defer b.mu.Unlock()
    now := time.Now()
    b.tokens = math.Min(b.capacity, b.tokens+now.Sub(b.last).Seconds()*b.rate)
    b.last = now
    if b.tokens >= 1 {
        b.tokens--
        return true
    }
    return false
}
```

Для судебных сайтов реальные лимиты неизвестны до бана: стартовый консервативный rate (например, 1 req/2 сек на домен), мониторинг 429, плавный рост до «почти-бан»-порога (см. §9).

### Граничные случаи — где ломается

**Rate limit в каждом воркере, а не общий.** 10 воркеров × 1 req/сек = 10 req/сек на домен — бан. Общий счётчик на downstream (Redis/локальный для одного процесса) — иначе лимиты суммируются.

**Rate limit без учёта ответов.** Downstream сам вернул 429 — наш rate limit не учитывает это как сигнал: продолжаем в том же темпе. Уважение `Retry-After` + снижение темпа на 429 — часть политики (§3).

**Лимит на «запрос», а не на ресурс.** Суд считает не запросы, а «сессии»: открытая сессия + капча (RuCaptcha) на каждую N-ю страницу. Лимит должен учитывать реальный счётчик downstream (сессии/капчи), а не абстрактные запросы.

**Почему это важно архитектору:** без ограничения исходящих мы сами себе создаём отказ: суд блокирует IP на сутки (реальная практика судебного сбора), и сбор встаёт не из-за падения сервиса, а из-за своей же скорости.

**Практический вывод для архитектора:** общий rate limit на downstream (не на воркер), консервативный старт, уважение Retry-After, мониторинг 429 как метрики «близко к банам».

## 7. Saga: распределённые операции с компенсацией

### Механика

Saga — распределённая операция, состоящая из локальных шагов с **компенсациями**: если шаг N не удался, откатываются шаги 1..N−1 компенсирующими действиями. ACID-транзакции между сервисами не бывает; сага — её замена.

```text
Кейс: «Зарегистрировать судебное дело + загрузить документы + уведомить 1С»

Оркестратор:
  1. create_case(Deal)                 → success (id=84921)
  2. upload_documents(id, pdfs)        → fail (PDF битый)
  3. → compensate: delete_case(84921)  → учётная запись удалена
  Итог: система не знает о деле — 1С не уведомлялась
```

Два стиля саги:

| Стиль | Плюсы | Минусы |
|:--|:--|:--|
| **Orchestration** (один оркестратор) | явный порядок, проще отладка | централизация, оркестратор — точка отказа |
| **Choreography** (события между сервисами) | децентрализация, масштабирование | порядок неявный, сложно отлаживать |

Для интеграции CourtDesk→1С — orchestration: последовательность явная, шагов немного, отладка важнее масштабирования.

### Правила саги

1. **Каждый шаг — идемпотентный** (модуль 51): компенсация и повтор не должны плодить дубли. `compensate` для `create_case` = `delete_case` — идемпотентно по id.
2. **Компенсация не может отказать «навсегда».** Компенсация падает → saga застряла. Повтор компенсации с backoff, DLQ для некомпенсируемых (модуль 18 §4), ручной контур.
3. **Состояние саги — в БД, не в памяти.** Оркестратор упал — сага возобновляется по сохранённому состоянию. Таблица `sagas(id, step, state)` + журнал шагов.

```sql
-- Состояние саги: шаг + результат (пример схемы)
CREATE TABLE sagas (
    id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    kind       TEXT NOT NULL,            -- 'case_register'
    state      JSONB NOT NULL,           -- идемпотентные ключи шагов
    step       TEXT NOT NULL DEFAULT 'create_case',
    status     TEXT NOT NULL DEFAULT 'running',  -- running|done|compensating|failed
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

### Граничные случаи — где ломается

**Компенсация после успешного шага без сохранения идемпотентного ключа.** Повторный `delete_case` по несуществующему id — ошибка, сага не может продолжить. Идемпотентность каждого шага — предусловие, а не опция.

**Компенсация затронула чужие данные.** `delete_case` удаляет дело, которое уже «увидела» 1С в промежутке. Сага не заменяет согласованность — она ограничивает окно несогласованности. Фиксировать видимость шагов (шаг «published» — компенсация переходит в «уведомить об удалении»).

**Choreography без идемпотентных событий.** Два потребителя события «case.created» обработали его дважды (replay) — задвоенные уведомления. События с idempotent key и dedupe у потребителей.

**Почему это важно архитектору:** сага — единственный способ поддерживать согласованность за пределами одной БД. Без неё распределённые операции «почти работают» — и оставляют сиротские данные при сбоях.

**Практический вывод для архитектора:** orchestration для явных последовательностей, идемпотентность каждого шага, состояние в БД, компенсации с ретраями и DLQ. Сага — про «согласованность в итоге», не про атомарность.

## 8. Fallback и degraded mode

### Механика

Fallback — заранее определённый ответ, когда основной путь недоступен. Degraded mode — состояние системы, в котором части функциональности заменены на дешёвые/кэшированные.

Пирамида fallback (по убыванию качества):

```text
1. Основной путь (свежие данные)
2. Кэш (данные последнего успеха — модуль 20)
3. Кэш с возрастом (данные вчерашние, с пометкой)
4. Деградированный ответ (пустой список + метаданные «данные устарели»)
5. Ошибка (если контракт не позволяет деградацию)
```

Контракт деградации — **явный**:

```json
{
  "cases": [],
  "stale": true,
  "generated_at": "2026-08-05T23:00:00Z",
  "note": "Суд недоступен, данные кэша за 2026-08-05"
}
```

Потребитель (1С) видит `stale: true` и решает: принять данные с пометкой или повторить позже. Молчаливый пустой список — «дело закрылось, хотя суд просто лежал» — худший вариант.

### Граничные случаи — где ломается

**Fallback скрывает проблему.** CB открылся, fallback отдал кэш — пользователь не видит ошибок, но данные стареют. Degraded mode обязан быть видимым: метрика `stale_serves`, алерты на возраст кэша.

**Деградация не определена в контракте.** Клиент ожидал `cases: [...]` и получил пустой список — это валидный ответ «дел нет»? Fallback-поля (`stale`, `generated_at`) в контракте (модуль 51) — иначе потребитель не отличает «пусто» от «недоступно».

**Fallback цепочка бесконечная.** «Кэш → резервный сервис → другой провайдер → ...» — каждый уровень добавляет latency и скрывает деградацию. Конечная цепочка из 2–3 уровней с явным терминалом (ошибка).

**Почему это важно архитектору:** fallback — мост между «сервис лежит» и «продукт жив». Без деградации отказ downstream = отказ продукта; с деградацией — продукт работает на устаревших данных с явной пометкой.

**Практический вывод для архитектора:** конечная цепочка fallback, кэш последнего успеха, `stale`-флаг в контракте, видимость деградации в метриках и алертах.

## 9. Реальный кейс: судебный сбор против 429-шторма

### Контекст

Сбор карточек судебных дел с сайтов судов (sudrf, мировые участки): сотни тысяч карточек, парсинг страниц, капча на N-ю сессию (RuCaptcha), блокировки по IP за частоту запросов. Сбор — фоновые задания из очереди (модуль 18, инкрементальный cron-сбор), потребители выгрузки — 1С-интеграция (модуль 51).

### Гипотеза

«Просто добавим retry при ошибке»: сайт упал/вернул 429/капчу — повтор через секунду, и всё поедет.

### Что получилось — 429-шторм

Первый продакшен-прогон: 10 воркеров × ретрай без джиттера. Сайт одного суда начал отвечать 502 (перегрузка) → все воркеры ретраили **синхронно** через 1 сек → пик запросов на домен → суд отдал 429 и через минуту — **блокировка IP на сутки**.

```text
10 воркеров, retry через 1s без jitter:
t=0   502 ×10 → retry через 1s (все одновременно)
t=1s  10 запросов пиком → 429 ×10 → retry через 1s
t=2s  10 запросов пиком → блокировка (403) на 24 часа
Итог: сбор встал на сутки, а «ретраи» сделали хуже
```

Ошибка была не в том, что ретраили, а в том, что **10 воркеров ретраили без координации** — и это был не retry storm, а retry-залп.

### Архитектурные решения

```text
Очередь (pg-boss)                    Судебный сайт
   │  задание «собрать суд X»              ▲
   ▼                                      │
Оркестратор сбора (Go 1.26)
   ├─ Bulkhead: пул 3 воркера на домен     │ 1 req / 2 сек на домен
   ├─ Rate limit: токен-баскет 0.5 req/s   │ (общий на домен, Redis)
   ├─ CB на домен: OPEN при 40% 5xx за 30с │
   ├─ Retry: +full jitter, 3 попытки,      │
   │         Retry-After > backoff         │
   └─ Капча: RuCaptcha при 403/captcha →   │
      пауза сессии, не ретрай потока       │
```

1. **Bulkhead 3 воркера на домен** — перегрузка одного суда не съедает сбор остальных.
2. **Общий rate limit на домен** (Redis): 1 запрос/2 сек — суд не видит «залпа».
3. **CB на домен**: 40% 5xx за 30 сек → OPEN → очередь не тратит попытки на лежащий суд; HALF_OPEN через 10 минут.
4. **Retry с full jitter** и уважением `Retry-After`; лимит 3 попытки.
5. **Капча — отдельный путь**: при капче не ретрай, а сессионная пауза (капча дорогая, RuCaptcha решает), иначе ретраи жгут баланс капчи.

### Результат

- Блокировки IP прекратились (главная метрика: 0 банов за месяц против 2 за первый день);
- сбор лежащего суда: CB отключает вызовы мгновенно, очередь ждёт HALF_OPEN — остальные суды собираются без деградации;
- 429 стали ожидаемым сигналом (Retry-After + снижение темпа), а не ошибкой сбора.

### Вывод, противоречащий интуиции

Retry без координации — не resilience, а **мультипликатор нагрузки**. Синхронные ретраи 10 воркеров превратили перегрузку сайта в блокировку IP — отказ стал длиннее в 24 раза. Resilience паттерны работают только связкой: retry-бюджет, jitter, bulkhead-изоляция, общий rate limit и CB на домен.

Второй вывод: **самый важный паттерн — тот, который выглядит лишним.** Rate limit на «наш» трафик к судам казался замедлением работы; именно он (а не retry и не CB) снял блокировки.

**Практический вывод для архитектора:** при сбое внешнего сервиса считай свой трафик к нему, а не только ошибки. Каскад начинается с того, что «мы просто повторили запрос» — синхронно, всем пулом.

## 10. Антипаттерны

### «Retry на каждом слое»

**Выглядит правильно:** надёжность по всем уровням.

**Почему ошибка:** клиент ретраит + шлюз ретраит + очередь ретраит = произведение попыток и экспонента нагрузки. Один ретрай-слой на пути, остальные — fail fast (или трейс `Retry-Count` для координации).

---

### «Retry без джиттера»

**Выглядит правильно:** равные интервалы, предсказуемо.

**Почему ошибка:** все клиенты ретраят в одни и те же моменты — пики на падающий сервис, который от этого не восстанавливается. Полный джиттер обязателен.

---

### «Circuit breaker и retry в одном middleware»

**Выглядит правильно:** «и то и то» для надёжности.

**Почему ошибка:** retry скрывает ошибки от счётчика CB — порог не срабатывает, fail fast не наступает. Retry снаружи CB (модуль 19 §6).

---

### «Bulkhead без таймаутов»

**Выглядит правильно:** пулы изолированы.

**Почему ошибка:** слоты занимаются висящими запросами — изоляция превращается в общий отказ. Слот = время выполнения, ожидание слота с таймаутом.

---

### «429 считаем как ошибку CB»

**Выглядит правильно:** сервис нас лимитит — значит, он нездоров.

**Почему ошибка:** 429 — сигнал «сбавь темп», не «сервис упал». CB откроется от перегрузки, хотя сервис жив; правильная реакция на 429 — Retry-After и снижение темпа.

---

### «Сага без идемпотентности шагов»

**Выглядит правильно:** компенсация откатит.

**Почему ошибка:** компенсация сама падает на повторных вызовах (шаг уже откачен, delete несуществующего) — сага застревает навсегда. Идемпотентность шагов — предусловие саги.

---

### «Молчаливый fallback»

**Выглядит правильно:** пользователь не видит ошибок.

**Почему ошибка:** деградация невидима: пустой список вместо данных суда = «дел нет» у 1С. Fallback обязан быть помеченным (`stale`, возраст данных) и видимым в метриках.

---

## Anti-checklist ☠️

- [ ] Retry на каждом слое — произведение попыток, экспонента нагрузки
- [ ] Retry без джиттера — синхронные пики на падающий сервис (реальный шторм)
- [ ] Retry внутри circuit breaker — CB не видит ошибок, порог не срабатывает
- [ ] POST без идемпотентности с ретраем — дубли на каждом повторе
- [ ] Rate limit на воркер вместо общего — 10 воркеров × лимит = бан downstream
- [ ] 429 как ошибка CB — CB открывается от перегрузки, а не от отказа
- [ ] Bulkhead без таймаутов — слоты занимаются висящими запросами
- [ ] Сага без идемпотентных шагов — компенсация не может повториться
- [ ] Молчаливый fallback — деградация данных невидима потребителю

## Задачи AI-кодеру

**Задача 1 — Retry с бюджетом и джиттером**

Плохая формулировка:
> «Добавь ретрай к HTTP-запросу»

Хорошая формулировка:
> «Реализуй на TypeScript функцию `callWithRetry(fn: () => Promise<Response>, opts: {maxAttempts: 4, baseDelayMs: 1000, maxDelayMs: 10000})`: retry при статусах 408/429/5xx, exponential backoff с full jitter (`random() * base`), при 429 — приоритет заголовку `Retry-After`, бюджет: не более `maxAttempts` попыток и не более `maxDelayMs` между попытками. Покрой тестами: не-retryable 4xx, 429 с Retry-After, синхронность ретраев двух экземпляров (недетерминизм jitter).»

Формула: конфигурация бюджета + семантика статусов + Retry-After + тесты.

---

**Задача 2 — Circuit breaker с 429-семантикой**

Плохая формулировка:
> «Оберни вызовы в circuit breaker»

Хорошая формулировка:
> «Реализуй CircuitBreaker (или opossum 8.x): порог 50% ошибок за 30 сек при минимуме 10 запросов, resetTimeout 15 сек, HALF_OPEN с 1 пробным запросом. Ошибки: 5xx и таймауты — считаются, 429 — не считается, но возвращается как есть (не ретрай). fallback — кэшированный ответ с флагом `stale: true`. Тесты: открытие при 50% 5xx, НЕ-открытие при 100% 429, переход CLOSED→OPEN→HALF_OPEN→CLOSED.»

Формула: параметры порога + разделение 429/5xx + fallback + state-машина в тестах.

---

**Задача 3 — Bulkhead с таймаутом ожидания**

Плохая формулировка:
> «Сделай лимит параллельных запросов»

Хорошая формулировка:
> «Реализуй на Go bulkhead-пулы: `UI` (10 слотов), `Replica` (30 слотов), `Parser` (5 слотов на домен). Слот — на время выполнения, ожидание слота с таймаутом 500 мс → `ErrBulkheadFull`. Контекст отмены пробрасывается из запроса. Тесты: перегрузка пула Parser не влияет на UI; таймаут ожидания слота возвращает ошибку, а не блокирует.»

Формула: пулы по потребителям + таймаут ожидания + изоляция в тестах.

---

**Задача 4 — Сага с компенсацией**

Плохая формулировка:
> «Добавь откат при ошибке интеграции»

Хорошая формулировка:
> «Реализуй сагу “case_register”: шаги 1) create_case, 2) upload_documents, 3) notify_1c. Каждый шаг идемпотентен по бизнес-ключу. При отказе шага — компенсация пройденных в обратном порядке (delete_case, delete_documents), повтор компенсации с backoff до 3 раз, DLQ при исчерпании. Состояние саги — в PostgreSQL (таблица `sagas`), возобновление после рестарта. Тесты: отказ на шаге 2 → компенсация 1, повторный запуск с тем же ключом не создаёт дублей.»

Формула: шаги + компенсации + идемпотентность + состояние в БД + тесты на откат.

## Чеклист архитектора

### Таймауты
- [ ] Таймаут на соединение, вызов, общий бюджет (клиентский ≤ серверного)
- [ ] Deadline распространяется через context/AbortSignal на все вызовы
- [ ] Фоновые задачи отделены от таймаутов ожидания (очередь)

### Retry
- [ ] Ретраят только 408/429/5xx и сетевые сбои; 4xx — нет
- [ ] Exponential backoff + full jitter; Retry-After первичен
- [ ] Ретранслируется только на одном слое пути
- [ ] Ретрай только идемпотентных операций (модуль 51)
- [ ] Бюджет: maxAttempts и maxDelay заданы явно

### Circuit Breaker
- [ ] Порог: % ошибок + минимум запросов (не срабатывает на одном сбое)
- [ ] 429 не считается ошибкой CB
- [ ] Retry снаружи CB, fallback при OPEN
- [ ] CB на границе к нестабильному downstream, не на каждом слое

### Bulkhead
- [ ] Пулы по конкурирующим ресурсам (БД, внешний API)
- [ ] Слот = время выполнения; ожидание слота с таймаутом
- [ ] Вместе с rate limit, не вместо

### Rate limiting
- [ ] Общий лимит на downstream (не на воркер)
- [ ] Уважение Retry-After, снижение темпа на 429
- [ ] Метрика «близость к бану» (429/403 доля)

### Saga
- [ ] Каждый шаг идемпотентен (бизнес-ключ)
- [ ] Состояние саги в БД, возобновление после рестарта
- [ ] Компенсации с backoff + DLQ; видимость шагов учтена

### Fallback
- [ ] Цепочка конечна (2–3 уровня + явный терминал)
- [ ] Деградация помечена в контракте (`stale`, `generated_at`)
- [ ] Деградация видима в метриках и алертах
