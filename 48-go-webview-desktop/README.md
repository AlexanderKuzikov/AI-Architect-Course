## 1. Введение и актуальность

### 1.1. Когда десктоп, а не web

| Сценарий | Web | Desktop (Go+WebView) |
|:--|:--|:--|
| Многопользовательский сервис | ✅ | ❌ |
| Локальная обработка приватных данных | ❌ (данные на сервере) | ✅ |
| Офлайн-инструмент для клиента | ❌ | ✅ |
| Работа с локальными файлами/папками | ❌ | ✅ |
| Интеграция с ОС (WebView, shell, yt-dlp) | ❌ | ✅ |

Для российского рынка ключевой кейс: **локальный VLM + десктоп без облака** — данные не покидают машину клиента, оплата в рублях, бинарник распространяется файлом.

### 1.2. Go+WebView vs Electron vs Tauri vs Fyne

| Метрика | Electron | Tauri | Go+WebView | Fyne |
|:--|:--|:--|:--|:--|
| Размер | 150+ MB | 10–15 MB | **~6 MB** | 40 MB |
| Runtime | Node+Chromium | Rust+system WebView | Go+system WebView | Go+OpenGL |
| UI | HTML/CSS/JS | HTML/CSS/JS | HTML/CSS/JS | виджеты |
| Toolchain | Node | Rust | Go | Go |

**Практический вывод для архитектора:** Go+WebView выигрывает, когда нужен маленький бинарник, HTML-интерфейс и Go-бэкенд (встроенный HTTP, VLM-клиент, обработка файлов). Electron — если мало критичен размер и нужен зрелый экосистемный инструментарий. Tauri — если Rust-стек оправдан. Fyne — если интерфейс простой и нативный виджетный.

### Граничные случаи — где ломается

**«Desktop для всего»**: если приложению нужен сервер, мультитенантность и веб-доступ — десктоп не та архитектура. Go+WebView — для локального инструмента, а не распределённой системы.

**WebView как браузер**: WebView2 — это не полноценный браузер. Ограничения: нет расширений, разный уровень поддержки между платформами, кэш и куки ведут себя иначе. UI должен быть простым, без экзотических веб-фич.

**Почему это важно архитектору:** десктоп-слой — это UI-обёртка над локальным движком. Вся бизнес-логика должна жить в Go-модулях (HTTP-клиент, обработка файлов, VLM), а WebView — только рендерить. Иначе UI становится монолитом и его нельзя тестировать.

## 2. Архитектурная механика

### 2.1. Движки WebView

| Платформа | Движок | Зависимость |
|:--|:--|:--|
| Windows | WebView2 (Edge Chromium) | встроен в Win10/11 |
| Linux | WebKitGTK | `libwebkit2gtk-4.0` |
| macOS | WKWebView | встроен |

Утилита не тянет Chromium — бинарник ~6 MB. Но движок системный: поведение зависит от ОС пользователя.

### 2.2. Минимальный скелет

```go
package main

import "github.com/webview/webview_go"

func main() {
    w := webview.New(true) // true = debug mode
    defer w.Destroy()

    w.SetTitle("PDFtoText")
    w.SetSize(1440, 900, webview.HintNone)
    w.Navigate("http://127.0.0.1:8767") // встроенный loopback-сервер
    w.Run()
}
```

### 2.3. Два варианта UI-контента

```text
Вариант A: встроенный loopback HTTP-сервер (127.0.0.1:0) → Navigate
    ✅ рендерится как http-документ, надёжно
    ✅ удобно дебажить (браузер + те же эндпоинты)
    ✅ можно отдавать и статику, и API одним процессом

Вариант B: SetHtml (NavigateToString)
    ❌ до готовности контрола WebView2 — тёмный фон без контента
    ⚠️ только для простых страниц, не для стартовых
```

**Практический вывод:** для приложения с настройками, статусами и обработкой файлов — всегда встроенный HTTP-сервер. Это даёт тестируемость (UI — обычные HTTP-эндпоинты) и надёжный рендер.

### 2.4. Мост Go ↔ JavaScript

**Go → JS: `Eval`**

```go
w.Eval("document.title = 'New Title';")
```

**JS → Go: `Bind` — только функции**

⚠️ **Критично:** `webview_go` биндит ТОЛЬКО функции, не структуры. `w.Bind("app", &API{})` молча не работает — все `app.*` в JS будут undefined, интерфейс «мёртвый», но без ошибок.

```go
// ✅ Правильно — отдельные функции-обёртки
w.Bind("getVersion", func() string { return api.GetVersion() })
w.Bind("saveSettings", func(raw string) string { return api.SaveSettings(raw) })
w.Bind("process", func(names []string) { api.Process(names) })
```

В JS имя становится **глобальной функцией**:

```javascript
const v = await getVersion();
```

⚠️ Не объявляй в JS функции/переменные с теми же именами, что биндинги:
`async function process()` затеняет биндинг `process` — рекурсия; `const hasKey = await hasKey()` — TDZ. Префиксуй локальные имена.

### 2.5. Профиль пользователя

```go
func profilePath() string {
    home, _ := os.UserHomeDir()
    return filepath.Join(home, ".config", "myapp", "profile.json")
}
```

Стандартное расположение: `~/.config/<app>/profile.json`. Профиль вне репо, вне бинарника — данные пользователя.

### 2.6. Страница настроек

Генерировать HTML настроек в Go, рисовать через `Eval`:

```go
func (a *API) OpenSettings() {
    html := buildSettingsPage()
    w.Eval(`document.body.innerHTML = '` + escapeJS(html) + `';`)
}
```

### Граничные случаи — где ломается

**Температура 0 не сохраняется**: `parseFloat(v) || 1.0` трактует 0 как falsy → дефолт. Для значений, где 0 валидна, нужна явная проверка `v === ''`.

**Nil-слайс → null в JS**: Go-функция, возвращающая `nil` слайс, через JSON даёт `null`, а не `[]`. UI ломается на `list.map`. Для списков: `make([]T, 0)`.

**Пройденный API-URL**: пользователь вводит `http://server:8767`, `.../`, или `.../api` — все нормализуются `TrimSuffix` до единого вида.

**Почему это важно архитектору:** мост Go↔JS — самое хрупкое место паттерна. Ошибки там «тихие»: интерфейс запускается, но ничего не работает. Правило: биндить только функции, валидировать контракты на границе (типы, нули), нормализовать вход.

## 3. Security и грабли

### 3.1. XSS через profile.json

Поля профиля интерполируются в HTML/JS на странице настроек. Экранировать: `html.EscapeString` для HTML-контекста, `escapeJS` (`\\`, `\'`, `\n`, `\r`) для JS-строк.

### 3.2. Arbitrary scheme navigation

Валидировать URL: только `http://` / `https://`. `file://`, `javascript:` работают в WebView2 и опасны — произвольная навигация = произвольный код.

### 3.3. Дочерние процессы из GUI

**CREATE_NO_WINDOW обязателен** для console-процессов (yt-dlp, ffmpeg, taskkill) из GUI-приложения: без него Windows создаёт новую консоль — чёрное окно мигает при каждом запуске.

```go
cmd.SysProcAttr = &syscall.SysProcAttr{CreationFlags: 0x08000000}
// константы CREATE_NO_WINDOW в syscall нет — только литерал
```

**`exec.CommandContext` может НЕ убить процесс** (Go 1.26, блокировка сети): не полагаться на context-отмену, использовать `taskkill /PID <pid> /T /F` по таймеру.

### 3.4. Чёрный экран при старте

Три причины, в порядке частоты:

```text
1. Блокирующий <link> на внешний CDN (Google Fonts) в <head>
   → first paint ждёт stylesheet, пока он висит — тёмный фон
   Лечение: шрифты в embed (woff2, @font-face + font-display: swap),
   html { background: <светлый>; } инлайн

2. SetHtml до готовности контрола WebView2
   → NavigateToString даёт тёмный фон без контента
   Лечение: служебные страницы через loopback http-сервер + Navigate

3. Отсутствие -H windowsgui
   → консольное окно рядом с WebView (выглядит как чёрный экран)
```

### Граничные случаи — где ломается

**Статусы через document.title не работают**: на Windows-реализации `document.title` не обновляет заголовок окна. Диагностика через title — ложная. Используй fetch на локальный сервер или лог в Go.

**Прогресс дочернего процесса**: yt-dlp пишет прогресс в **stdout** (не stderr) с шаблоном `download:...` — префикс `download:` это тип шаблона, в выводе его нет. Строки `0.0%|390KiB/s|00:51|...` парсить по `|`, 5 полей, первое содержит `%`.

**stdout лимитом не резать**: полный JSON (yt-dlp `-J`) больше 4 КБ — обрезка даёт `unexpected end of JSON input`. `bytes.Buffer` без лимита; лимит — только для stderr.

**Почему это важно архитектору:** грабли десктопа — это не «можно потом починить», а блокеры поставки. XSS, чёрный экран, мигающее консольное окно — то, что клиент видит первым. Их надо проектировать заранее.

## 4. Production: сборка и поставка

### 4.1. Сборка

```bash
# Windows (без консольного окна)
go build -ldflags="-H windowsgui" -o myapp.exe .

# Release для клиента — ключ вшивается при сборке, не в коде
go build -ldflags="-H windowsgui -X main.bundledKey=API_KEY" -o dist\myapp.exe .
```

`-X main.bundledKey=...` — встраивание секрета в бинарник при сборке. В git/исходники не попадает. `HasKey=true`, настройка ключа в UI скрыта (`keyLocked`).

### 4.2. Антивирусные ложные срабатывания

**Инцидент из практики:** release-бинарник (16 МБ, `-s -w`) на второй машине удалялся Defender'ом мгновенно при копировании из любого источника. Диагностика: локальный `MpCmdRun` со свежими подписями — бинарь чист → детект в **облачной репутации Defender по SHA256**, не в подписях.

Фикс: пересборка **без `-s -w`** (бинарник больше, символы на месте — меньше ML-триггеров), новый хеш, локальный скан чист.

```text
- `-s -w` (strip) → больше ML-триггеров у Defender
- код-подпись (code signing) — долгосрочное решение для поставки
- при ложном срабатывании — WDSI false-positive submission по хешу
```

### 4.3. Поставка клиенту

```text
Один exe со вшитым ключом → клиенту по файлу
Профиль на машине клиента (~/.config/<app>/profile.json)
Обновление: замена exe (или автозагрузчик версий)
```

### Граничные случаи — где ломается

**Приложение без блокирующей проверки API**: если сервер недоступен, приложение должно загружаться и показать ошибку в UI, а не висеть. Проверка — в UI, не в Go.

**Полноэкранный режим**: `webview.HintMax` максимизирует. Отдельный `-fullscreen` флаг удобнее hardcoded.

**Почему это важно архитектору:** поставка десктопа — отдельная дисциплина: сборка для клиента, вшивание секретов, антивирусные риски, обновление. Она не похожа на деплой сервера.

## Реальный кейс

### Входные данные

PDFtoText: desktop-утилита конвертации PDF в текст через VLM. Пользователь выбирает папку деревом, отмечает PDF, получает `<имя>.txt` рядом. Распознавание — облачная модель `qwen/qwen3.7-flash` через RouterAI (рубли, ключ локально). 15 страниц ≈ 3.5 мин (параллель 10).

### Гипотеза

Go + WebView + встроенный loopback HTTP-сервер; UI — vanilla JS; VLM-клиент и обработка — Go-модули. Один exe ~6–28 MB без Node и Chromium.

### Что получилось

- **Архитектура**: `main.go` (WebView, Bind по функциям), `profile.go`, `converter.go` (режим API), `raster.go` (pdfium WASM + VLM), `processor.go` (очередь, статусы), `ui.go` (HTML UI). Бизнес-логика в Go-модулях, WebView только рендерит.
- **Инцидент 1 — «ничего не работает»**: `w.Bind` со структурой не работает — интерфейс запустился, но все `app.*` undefined. Фикс: биндинг отдельных функций + устранение TDZ-коллизий имён + `make([]T, 0)` вместо nil-слайсов.
- **Инцидент 2 — отказ модели как результат**: API-парсер не разобрал скан, модель вернула отказ, приложение записало его как результат. Фикс: `looksLikeRefusal`-детектор, дефолт `mode=raster`, подсказка сменить режим.
- **Инцидент 3 — Defender**: release `-s -w` удалялся облачной репутацией по SHA256. Фикс: пересборка без strip, новый хеш, WDSI submission.
- **Инцидент 4 — чёрный экран**: блокирующий CDN-шрифт в `<head>` — first paint ждал stylesheet. Фикс: шрифты embed, светлый бэкграунд инлайн.

### Вывод, противоречащий интуиции

Самые дорогие инциденты десктопа — не логика, а **поставка и доверие**: «ничего не работает» из-за тихого провала bind, антивирус по репутации, чёрный экран из-за CDN-шрифта. Архитектура Go+WebView выигрывает не в производительности, а в **контроле поставки**: один бинарник, локальные данные, никаких runtime-зависимостей. Но цена — ручная возня с граблями bridge и поставкой.

## 6. Антипаттерны

### «Вся логика в JS»

**Выглядит правильно:** UI и бизнес-логика вместе.

**Почему ошибка:** JS-слой не тестируется, мост Go↔JS хрупкий, данные и секреты утекают в WebView. Бизнес-логика — в Go-модулях, WebView рендерит.

---

### «Биндить структуру вместо функций»

**Выглядит правильно:** `w.Bind("app", &API{})` — удобно.

**Почему ошибка:** webview_go биндит только функции. Интерфейс запускается, но молча не работает. Диагностика — часы.

---

### «Strip-флаги для красоты размера»

**Выглядит правильно:** `-s -w` уменьшает бинарник.

**Почему ошибка:** в 2026 это триггер ML-детекторов антивирусов. Бинарник 28 МБ без strip безопаснее 16 МБ со strip.

---

### «SetHtml для всех страниц»

**Выглядит правильно:** просто показать HTML.

**Почему ошибка:** до готовности контрола WebView2 — тёмный фон без контента. Для служебных страниц — loopback сервер + Navigate.

---

## Anti-checklist ☠️

- [ ] Вся логика в JS — JS-слой не тестируется, мост хрупкий
- [ ] Биндить структуру — webview_go биндит только функции, интерфейс «мёртвый»
- [ ] Локальные JS-имена совпадают с биндингами — TDZ и рекурсия
- [ ] `-s -w` в release — ML-триггер антивирусов, пересобирать на чистом хеше
- [ ] Без `-H windowsgui` — чёрное консольное окно рядом с приложением
- [ ] Блокирующий CDN-шрифт в `<head>` — чёрный экран при старте
- [ ] Дочерние процессы без CREATE_NO_WINDOW — мигающее консольное окно
- [ ] Поля профиля в HTML без экранирования — XSS через profile.json
- [ ] `document.title` для статусов — не работает на Windows-реализации

## Задачи AI-кодеру

Плохая формулировка: > «Сделай десктоп-приложение на Go»

Хорошая формулировка: > «Реализуй на Go функцию `bindAPI(w webview.WebView, api *API)`, которая регистрирует через `w.Bind` отдельные функции: `getVersion`, `saveSettings(raw)`, `process(names []string)`. Не биндить структуру целиком. В JS глобальные функции без конфликтов имён. Добавь тест, что `process` в JS не перекрывает Go-биндинг.»

Формула: конкретные биндинги + ограничение (только функции) + контракт JS + тест.

---

**Задача 1 — Profile manager**

> Реализуй на Go `LoadProfile(path) (*Profile, error)` и `SaveProfile`. `Profile` содержит `APIURL`, `Model`, `Temperature` (0 валидна — не терять), `Thinking`, `Concurrency` (1–32), `Theme`. Валидация через единый `Normalize()`. Профиль хранится в `~/.config/<app>/profile.json`. Тест: температура 0 сохраняется и загружается.

---

**Задача 2 — XSS-safe settings page**

> Реализуй на Go `buildSettingsPage(profile Profile) string`, которая генерирует HTML настроек. Все строковые поля (`APIURL`, `Model`) экранируются `html.EscapeString` + `escapeJS`. Тест: профиль с полем `<script>alert(1)</script>` не содержит инъекцию в HTML.

---

**Задача 3 — URL normalization**

> Реализуй `normalizeAPIURL(raw string) string`: `TrimSuffix("/api")`, `TrimSuffix("/")`, дефолт только если пусто. Тест: `http://server:8767/api` → `http://server:8767`, `http://server:8767/` → `http://server:8767`.

---

**Задача 4 — Child process guard**

> Реализуй на Go `runHidden(cmd string, args ...string) (string, error)`: запуск console-процесса из GUI-приложения с `CREATE_NO_WINDOW` (0x08000000), полный stdout без лимита, kill через `taskkill /PID /T /F` по таймеру (не полагаясь на context-отмену). Тест: длинный stdout > 4 КБ не обрезается.

## Чеклист архитектора

### Архитектура
- [ ] Бизнес-логика в Go-модулях, WebView только рендерит
- [ ] UI отдаётся через loopback HTTP-сервер, не SetHtml
- [ ] Мост Go↔JS — только функции, контракты валидируются
- [ ] Нет TDZ-коллизий имён в JS

### Security
- [ ] Поля профиля экранируются (html + JS)
- [ ] Навигация только http/https
- [ ] Секреты не в коде — вшиваются при сборке (`-X`)
- [ ] Профиль вне репо и бинарника

### Production
- [ ] `-H windowsgui` при сборке
- [ ] Release без `-s -w` (антивирусные триггеры)
- [ ] Дочерние процессы с CREATE_NO_WINDOW
- [ ] Kill процесс через taskkill, не context
- [ ] Приложение загружается без сервера (ошибка в UI)
- [ ] code signing для поставки

### Gradники
- [ ] Чёрный экран проверен (нет блокирующих CDN-шрифтов)
