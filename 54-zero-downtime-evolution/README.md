## 1. Правило: откат — критерий готовности

Одна проверка отделяет готовую фичу от почти готовой: **что произойдёт, если её откатить через час после включения?**

Если ответ требует думать — фича не готова. Думать некогда в 2 часа ночи, когда включение привело к росту ошибок.

Отсюда три следствия:

1. **Изменение обратимо до включения.** Деплой и миграция — два независимых шага, каждый откатывается сам.
2. **Старый код работает с новой схемой.** Иначе откат схемы ломает откаченный код.
3. **Новый код работает со старой схемой.** Иначе деплой кода ломается о ещё не мигрированную базу.

Пункт 3 — самый недооценённый. Между деплоем кода и миграцией есть окно, в котором новый код уже в бою, а схема ещё старая. Если новый код читает поле, которого нет, — он падает на каждом запросе.

```text
❌ Неправильный порядок:            ✅ Безопасный порядок:
  1. миграция (ADD NOT NULL)           1. миграция: ADD nullable (старый код не видит)
  2. деплой кода                       2. деплой кода: пишет в новое, читает старое
  3. бэкфилл                           3. бэклфилл старых строк
  4. NOT NULL                          4. деплой: только новое
                                       5. миграция: NOT NULL
                                       6. деплой: удаление старой ветки
```

Шесть шагов вместо одного — и это нормальная цена изменения схемы в продакшене. Схема в проде меняется на два порядка дороже, чем в прототипе (модуль 49).

**Практический вывод для архитектора:** планируй изменение как два независимых деплоя с окном совместимости между ними, а не как «миграция плюс релиз».

## 2. Expand-contract: миграция без простоя

Расширение схемы добавлением, затем сужение удалением. Между шагами существуют две версии, и обе работают.

### Шаг 1 — Expand

Добавить новое, не убирая старое. Старый код не должен сломаться.

```sql
-- ❌ Ломает старый код: NOT NULL без дефолта
ALTER TABLE contracts ADD COLUMN region text NOT NULL;

-- ✅ Старый код не видит колонку и продолжает работать
ALTER TABLE contracts ADD COLUMN region text NULL;

-- ✅ Если нужен дефолт для старых строк — только на этапе backfill
UPDATE contracts SET region = 'unknown' WHERE region IS NULL;
```

Правило: **на шаге expand колонка nullable, старый код её не читает, новый код читает со значением по умолчанию в приложении, а не в базе.**

```typescript
// Новый код: старое значение допустимо, отсутствие — нет
function normalizeRegion(row: ContractRow): string {
  return row.region ?? DEFAULT_REGION;
}
```

### Шаг 2 — Переход

Код учится писать в новое поле и читать оба:

```typescript
type ContractReader = {
  readonly region: string;
};

// Слой совместимости живёт один деплой
function readRegion(row: ContractRow): string {
  return row.region ?? row.legacy_region ?? DEFAULT_REGION;
}
```

На этом шаге старые инстансы ещё работают и пишут только в старое поле. Чтобы «старое» перестало расходиться, его надо дозаполнять — триггер или запись в оба поля.

```sql
-- Двойная запись на время перехода
CREATE FUNCTION contracts_sync_region() RETURNS trigger AS $$
BEGIN
  IF NEW.region IS NULL THEN NEW.region := COALESCE(NEW.legacy_region, 'unknown'); END IF;
  RETURN NEW;
END $$ LANGUAGE plpgsql;

CREATE TRIGGER contracts_region_sync BEFORE INSERT OR UPDATE ON contracts
  FOR EACH ROW EXECUTE FUNCTION contracts_sync_region();
```

### Шаг 3 — Backfill

Существующие строки получают значение. Бэкфилл больших таблиц обязан быть батчами, иначе он блокирует запись.

```sql
-- ❌ Одна транзакция на миллион строк: блокировка, рост WAL, отмена запроса
UPDATE contracts SET region = 'unknown' WHERE region IS NULL;

-- ✅ Батчами с паузой — production-безопасный вариант
DO $$
DECLARE
  batch_size int := 1000;
  updated int;
BEGIN
  LOOP
    UPDATE contracts SET region = 'unknown'
    WHERE id IN (
      SELECT id FROM contracts
      WHERE region IS NULL
      ORDER BY id
      LIMIT batch_size
    )
    AND region IS NULL;
    GET DIAGNOSTICS updated = ROW_COUNT;
    EXIT WHEN updated = 0;
    PERFORM pg_sleep(0.05);
  END LOOP;
END $$;
```

### Шаг 4 — Contract

Перевод поля в `NOT NULL`, потом удаление старого. Только когда старый код выведен из строя и откат к нему уже не планируется.

```sql
ALTER TABLE contracts ALTER COLUMN region SET NOT NULL;
-- пауза: убедиться, что ни один инстанс не пишет NULL
ALTER TABLE contracts DROP COLUMN legacy_region;
DROP FUNCTION contracts_sync_region();
DROP TRIGGER contracts_region_sync ON contracts;
```

### Инструмент, который делает шаги 1–4 за один раз

`pgroll` версионирует схему: держит старую и новую версии одновременно через view'ы над физическими таблицами, бэкфиллит скрытыми колонками батчами и откатывается откатом версии, а не обратной миграцией.

```bash
pgroll init
pgroll start add_region.json      # обе версии схемы доступны одновременно
# приложение переключается на новую версию через search_path
psql -c "SET search_path TO 'public_000002';"
pgroll back add_region            # мгновенный откат
pgroll complete                   # старая схема удаляется, когда миграция закрыта
```

Требует PostgreSQL 14+. На 14 не работает с RLS: версионные view'ы создаются без `security_invoker`, а эта опция появилась в 15.

**Граничные случаи — где ломается:**

**`ALTER TABLE ... SET NOT NULL` переписывает таблицу.** В старых версиях Postgres для добавления `NOT NULL` требовалась полная перезапись, то есть блокировка на время всей таблицы. Современный Postgres использует проверку по constraint'у, но на больших таблицах всё равно нужен `lock_timeout` и проверка, что null'ов действительно нет, до попытки.

**`ADD COLUMN` с дефолтом тоже может блокировать.** На PostgreSQL 11+ дефолт без `VOLATILE` не переписывает таблицу — но только если дефолт константа. Дефолт как вызов функции (`now()`, `uuid_generate_v4()`) переписывает таблицу и блокирует запись на всё время добавления колонки.

**`CREATE INDEX` блокирует запись, `CONCURRENTLY` — нет.** Но `CONCURRENTLY` нельзя выполнять в транзакции, и индекс может остаться в состоянии `INVALID` при сбое. Индекс с `INVALID` не используется планировщиком — то есть внешне всё работает, а запросы идут по старому пути. Проверять: `SELECT indexrelid::regclass, indisvalid FROM pg_index WHERE NOT indisvalid;`

**Переименование через «добавить новое, скопировать, переключить, удалить старое» — четыре деплоя.** Соблазн переименовать столбец напрямую силён, потому что код меняется в одном коммите. Но между коммитом с миграцией и коммитом с кодом в системе есть окно, где старое имя ещё нужно, а новое — нет. Если в это окно придётся откатываться, откатывается только код, а миграция уже применена.

**Почему это важно архитектору:** `NOT NULL` без дефолта, `DROP COLUMN`, переименование, изменение типа — четыре операции, которые в проде означают аварию. Не «требуют аккуратности», а означают: без expand-contract их не выполняют в рабочей среде.

**Практический вывод для архитектора:** любое изменение схемы разбивай на «можно откатить в любой момент» и «необратимо». Первых в жизненном цикле фичи — четыре, второе — одно и в самом конце.

## 3. Миграции, которые ломают прод

Регулярное выражение, не требующее синтаксиса: **`ALTER TABLE` без таймаута блокировки** означает, что одна миграция может повесить всю запись в таблицу на время ожидания.

```sql
-- Перед каждой миграцией, меняющей схему
SET lock_timeout = '3s';
SET statement_timeout = '60s';
```

Если миграция не успела за `lock_timeout` — она падает и ждёт следующего запуска, вместо того чтобы встать в очередь за блокировкой и заблокировать всех, кто пишет.

| Операция | Блокирует запись | Обходной путь |
|:--|:--|:--|
| `ADD COLUMN` без дефолта | нет | — |
| `ADD COLUMN` с константой (PG 11+) | нет | — |
| `ADD COLUMN` с неконстантным дефолтом | да | добавить nullable, дефолт ставить отдельно |
| `SET NOT NULL` | нет на PG 12+ (проверка по constraint'у) | сначала `CHECK ... NOT VALID`, затем `VALIDATE CONSTRAINT` |
| `ALTER COLUMN TYPE` | да | новая колонка + бэкфилл + переключение |
| `DROP COLUMN` | нет | переименовать в `_deprecated` и ждать |
| `CREATE INDEX` | да | `CONCURRENTLY` вне транзакции |
| `ADD FOREIGN KEY` | да | `NOT VALID`, затем `VALIDATE CONSTRAINT` |

**Проверка ограничения без блокировки** — приём, который экономит самую неприятную миграцию:

```sql
-- 1. добавить ограничение как NOT VALID: проверяет только новые строки, мгновенно
ALTER TABLE contracts ADD CONSTRAINT contracts_region_check
  CHECK (region <> '') NOT VALID;

-- 2. проверить существующие строки, удерживая только SHARE UPDATE EXCLUSIVE
ALTER TABLE contracts VALIDATE CONSTRAINT contracts_region_check;
```

**Граничные случаи — где ломается:**

**Длинная транзакция в приложении держит блокировку, миграция ждёт.** `lock_timeout` превращает это в отказ миграции, а не в очередь. Но если миграция падает каждую попытку, нужен анализ: найти транзакцию, которая держит блокировку (`pg_stat_activity` + `pg_locks`), а не увеличивать таймаут.

**`VALIDATE CONSTRAINT` тоже берёт блокировку, но слабую.** Она не мешает записи и чтению, только DDL. Проверка 50 миллионов строк занимает минуты — в это время DDL в этой таблице стоит. Для таблиц, где DDL нужен часто, проверку выносят в отдельное окно.

**Бэкфилл больших таблиц раздувает WAL и сбивает репликацию.** Батчи с паузой решают и это, но добавляют время: миллион строк по тысяче с паузой 50 мс — минимум минута только на паузы.

**Почему это важно архитектору:** миграция, которая берёт `ACCESS EXCLUSIVE`, — это не «медленная миграция», а остановка приёмки заявок на 10 минут. И это происходит в пятницу вечером, потому что CI зелёный.

## 4. Обратная совместимость API

Пока в системе работают две версии кода, контракт обязан читаться обеими. Матрица решений:

| Изменение | Ломает? | Что делать |
|:--|:--|:--|
| Добавить **необязательное** поле ответа | нет | - |
| Добавить **обязательное** поле запроса | да, старый клиент не пришлёт | сделать nullable, валидировать на сервере |
| Удалить поле ответа | да, клиент может его читать | удалять после deprecation-окна |
| Удалить поле запроса | нет | но проверить, что клиент не присылает мусор |
| Переименовать поле | да | новое + старое одновременно, потом deprecation |
| Сменить тип (`string` → `int`) | да | старый тип в старом поле, новый в новом |
| Ужесточить `enum` (добавить значение) | да, старый клиент упадёт на новом значении | клиент обязан иметь fallback на неизвестное |
| Ужесточить валидацию запроса | да | принимать старое, отдавать ошибку только на явно мусорных |

```typescript
// Клиент, который пережил расширение enum на сервере
function parseStage(raw: unknown): CaseStage {
  if (raw === 'review' || raw === 'ready') return raw;
  if (raw === 'new') return 'new';
  return 'new';  // ⚠️ неизвестное значение деградирует, а не падает
}
```

**Deprecation как процесс, а не заголовок:**

```http
HTTP/1.1 200 OK
Deprecation: true
Sunset: Sat, 30 Nov 2026 23:59:59 GMT
Link: <https://docs/api/v2/migration>; rel="deprecation"
```

Депрекация работает, только если по ней есть метрика: кто из потребителей ещё шлёт старое. У 1С нет активной авторизации — придётся идентифицировать по `User-Agent`, по формату запроса или по имени базы в параметрах.

**Граничные случаи — где ломается:**

**Клиент с кэшем ответа старой формы.** Ответ закешировали на сутки, сервер убрал поле — клиент падает через сутки, когда обновление уже прошло и все уверены, что всё в порядке.

**Enum, расширенный без предупреждения, ломает не только старых клиентов.** Новый сервер может вернуть значение, которое старый десктопный клиент 1С покажет как пустое поле, и бухгалтер не заметит — а расчёт пойдёт неверно. Расширение enum для интегратора хуже, чем для веб-клиента: у веба есть JS с `default`, у 1С — типизированная форма.

**Смена смысла поля при том же имени.** Самая дорогая ошибка совместимости: поле называется `status`, но теперь значит другое. Формально совместимо, фактически — порча данных у всех потребителей.

**Почему это важно архитектору:** для интеграций совместимость измеряется не «мы ничего не сломали в своём коде», а «ни один потребитель не получил неожиданный ответ». У внешних потребителей нет твоего CI.

## 5. Feature flags: временная конструкция

Флаг — это `if` в production, который можно снять, не передеплоивая. Полезен, но у него есть срок жизни, и забытый флаг дороже, чем его отсутствие.

```typescript
// Флаг читается из конфигурации, а не из кода: значение меняется без релиза
type Flags = {
  readonly newCourtClient: boolean;
  readonly batchParsing: boolean;
};

const parseCase = (raw: RawCase, flags: Flags) =>
  flags.batchParsing ? parseBatch(raw) : parseOne(raw);
```

### Что флаг делает хорошо

- Разделение деплоя и включения: можно задеплоить в пятницу, включить в понедельник
- Персиентный rollout: 1% → 10% → 50% → 100%
- Kill switch: выключить дорогое или сломанное без релиза
- Разделение двух несовместимых схем БД на время миграции

### Что флаг делает плохо

**Комбинаторный взрыв.** Восемь флагов дают 256 комбинаций, из которых тестированы две. Каждая новая ветка удваивает пространство состояний.

**Код, который живёт вечно.** `if (flags.oldPath)` не удаляется, потому что «кто его знает». Через год это мёртвая ветка, которую никто не может удалить без риска.

**Флаг как неявный параметр функции.** Произвольное поведение, зависящее от флага, перестаёт быть тестируемым: нужно проверять каждую комбинацию.

### Три правила, которые превращают флаг в инструмент

1. **Владелец и дата удаления пишутся рядом с флагом.** Не в задаче, не в переписке — в коде:

```typescript
// @flag newCourtClient
// owner: @alex · removeAfter: 2026-11-30 · issue: COURT-412
// Удаление флага — обязательный шаг рефакторинга, не отдельная задача.
```

2. **Заведён дедлайн удаления, а не «когда понадобится».** Без даты флаг живёт вечно: он работает, он никому не мешает, его забывают.

3. **Флаг удаляется в том же цикле работы, где появился.** Не «после стабилизации», а после перевода всех на новый путь.

```bash
# Проверка: флаги, которые пережили дедлайн
rg -n "removeAfter:\s*(\d{4}-\d{2}-\d{2})" src/ \
  | awk -F'removeAfter: ' '{print $2}' \
  | awk -v today="$(date +%F)" '$1 < today {print}'
```

**Граничные случаи — где ломается:**

**Флаг включили, но код с флагом задеплоили не везде.** Включение флага раньше, чем код с ним попал во все инстансы, даёт `undefined` на старых инстансах. Порядок: сначала деплой кода с флагом, выключенным по умолчанию, потом включение.

**Флаг как разделитель двух схем, а не как kill switch.** Такие флаги живут дольше всех, потому что «нужно поддерживать оба формата». Это не флаг, а версия API: у неё должно быть имя и дата окончания поддержки, а не булево значение.

**Два флага на одну настройку.** Появились `useNewParser` и `newParserEnabled`, потому что настройку вынесли в конфиг, потом в панель, потом в БД. Дублирование флагов означает, что часть трафика идёт по старому пути «случайно», и это не диагностируется.

**Почему это важно архитектору:** флаг без владельца и даты — это отложенный рефакторинг, который переживёт того, кто его включил. Срок жизни флага должен быть виден в том же месте, где флаг включается.

## 6. Деплой без простоя

Классическая схема: поднимается новая версия рядом со старой, переключение — мгновенное, откат — переключение обратно.

```text
        nginx / балансировщик
              │
     ┌────────┴────────┐
     ▼                 ▼
  app v1            app v2          ← обе живы одновременно
  (порт 3001)       (порт 3002)
```

| Стратегия | Как переключается | Откат | Когда брать |
|:--|:--|:--|:--|
| **Blue-green** | переключение целиком | обратное переключение | простой деплой, нет схем |
| **Rolling** | по инстансам, балансировщик выводит по очереди | сложнее: надо понять, где смесь | обычный случай |
| **Recreate** | стоп, потом старт | стоп, потом старт | только dev и однопользовательские витрины |
| **Canary** | 1% трафика на новую версию | перевести обратно трафик | рискованный релиз |

Canary на новой схеме БД не работает, если схема изменилась необратимо: старый инстанс на новой схеме, а новый — на обеих. Отсюда правило: **если в релизе есть необратимая миграция, canary невозможен**, сначала expand-contract, потом canary.

**Миграция — отдельный шаг, не часть деплоя:**

```yaml
# .github/workflows/deploy.yml
jobs:
  migrate:
    # Отдельная job: миграция применяется и коммитится ДО деплоя кода
    - run: npm run migrate:up
    - run: git add migrations/ && git commit -m "chore: миграция N применена"
  deploy:
    needs: migrate
    # Код деплоится на expand-совместимую схему: старое поле ещё есть
    - run: ./deploy.sh
```

Коммит миграции важен: он делает применённое состояние видимым в истории. Без него следующий деплой попытается применить ту же миграцию повторно.

**Граничные случаи — где ломается:**

**Rolling-деплой со сменой схемы = смесь версий на одной базе.** Во время раскатки часть инстансов со старым кодом, часть с новым, все на одной схеме. Если новый код удалил поле, которое старый пишет, — потеря данных при откате на старый код. Отсюда правило: раскатка возможна, только пока схема покрывает обе версии.

**Инерция соединений.** База данных не отдаёт соединение мгновенно: пул, keep-alive, долгие транзакции. Деплой «мгновенный», а старый процесс живёт ещё минуту. Отсюда два требования: graceful shutdown с завершением текущих запросов (модуль 18) и `lock_timeout` для миграций, идущих параллельно.

**Health-check, который проверяет «процесс жив», а не «работает».** Новый инстанс поднялся, отвечает на `/`, но падает на реальном запросе к БД. Нужен readiness-чек, который делает настоящую работу: соединение с БД, чтение схемы. Иначе балансировщик заливает трафик в нерабочий инстанс.

**Почему это важно архитектору:** canary и blue-green дают деплой, который почти невозможно превратить в аварию. Отсутствие такой схемы — это не «не успели», а сознательно выбранный риск, и его надо записать.

## 7. Strangler fig: вытеснение чужой системы

Когда чужую систему нельзя выключить целиком: 1С в бухгалтерии, старая CRM, кабинет на веб-фреймворке. Вытеснение идёт по вертикали — перехватывается одна операция, а не всё приложение.

```text
Шаг 1: всё в старой системе, новая принимает чтение
Шаг 2: новая система — прокси перед старой, логика постепенно переезжает
Шаг 3: новая пишет и читает сама, старая — только чтение (для сверки)
Шаг 4: старая отключена, остаётся для отчётов и аудита
```

```typescript
// Шаг 2: маршрутизация по одной операции, не по пользователю
export async function createCase(input: CaseInput): Promise<CaseRef> {
  if (await flag('new_case_write')) {
    const created = await newSystem.create(input);
    await mirrorToLegacy(created);   // двусторонняя сверка на переходном этапе
    return created;
  }
  return legacySystem.create(input);
}
```

Сверка обязательна: пока обе системы пишут, они разъедутся. Расхождения собираются в таблицу и разбираются — иначе через месяц выясняется, что данные уже не восстановить.

**Граничные случаи — где ломается:**

**Перехват по одной операции даёт две модели данных в одном интерфейсе.** Пользователь создаёт дело в новой системе, а видит старые — и не понимает, где истина. Нужен явный признак «это запись новой системы» в интерфейсе и единая точка чтения.

**Двусторонняя синхронизация — источник расхождений.** Односторонняя миграция расходится предсказуемо (всё новое в одной системе), двусторонняя — непредсказуемо. Если расхождение уже есть, автоматический выбор «победителя» по времени опасен: поздняя запись не значит правильная.

**Старая система не умеет отдавать, что ей добавили.** Расширение чужой схемы возможно не всегда, и тогда часть данных приходится держать у себя — это уже две системы хранения для одного домена.

**Почему это важно архитектору:** вытеснение занимает месяцы, и всё это время в проде две реализации. План «переписываем и переключаем» почти всегда дешевле для маленькой системы и почти всегда дороже для большой — цена ошибки растёт нелинейно с размером.

## 8. Реальный кейс

### Контекст

Сервис CourtDesk (модули 51, 49) отдаёт 26 эндпоинтов в формате, который читает 1С. Потребление живёт: одна и та же версия 1С стоит у нескольких клиентов, обновление не под контролем, запросы идут постоянно. То есть схему и контракт менять можно только так, чтобы старый клиент продолжил работать.

### Симптом

Требование: добавить в карточку дела признак «требует сверки с судом». Первая реализация добавила поле в таблицу `cases`, сразу `NOT NULL` с дефолтом, и задеплоила вместе с кодом, который его читает.

Что произошло: `ALTER TABLE ... ADD COLUMN ... NOT NULL DEFAULT 'false'` отработал за секунду на пустой по меркам нагрузки таблице, но в момент деплоя шел бэкфилл. Клиентская 1С в этот момент делала выгрузку: запросы к `cases` встали на время блокировки. Деплой занял 40 секунд, из них 25 — ожидание блокировки. Ошибок не было — просто выгрузка встала и повторилась.

### Гипотеза

Разделить изменение на expand и contract, добавить `lock_timeout` перед каждой миграцией, перевести опасные операции на `NOT VALID` + `VALIDATE CONSTRAINT`, индексы строить `CONCURRENTLY`.

### Что получилось

- **Смена признака сверки** теперь идёт как: `ADD COLUMN nullable` → деплой кода, читающего `?? false` → бэкфилл батчами → `SET NOT NULL` через `CHECK NOT VALID` + `VALIDATE` → удаление слоя совместимости через два деплоя. Окно неработоспособности — ноль.
- **`lock_timeout = 3s` и `statement_timeout = 60s`** в начале каждой миграции. Одна из них до сих пор падает на миграции и переносится на следующее окно — раньше она бы встала в очередь и заблокировала выгрузку.
- **Индексы строятся `CONCURRENTLY` вне транзакции.** Отдельно добавлена проверка `NOT indisvalid` в ночной джоб: индекс, оставшийся `INVALID` после сбоя, выглядит как рабочий, но планировщиком не используется.
- **Формат ответа 1С не меняется.** Новое поле появилось как необязательное, старое продолжает заполняться. Клиенты, не обновлявшиеся полгода, работают.
- **Контракт ответа версионируется в докстринге** с указанием, какие поля можно не возвращать. Новые поля — всегда необязательные, пока не подтверждена готовность всех потребителей читать их как обязательные.

### Вывод, противоречащий интуиции

Интуиция говорит: «деплой на пустой по меркам нагрузки столе не может быть проблемой». Проблема не в размере таблицы, а в том, что **1С в момент деплоя делала выгрузку**. Размер таблицы и наличие длинных транзакций потребителя — независимые величины, и вторая не видна ни в личном кабинете БД, ни в метриках приложения.

Второй вывод: `lock_timeout` выглядит как уступка — миграция иногда падает вместо того, чтобы дождаться. На деле это размен 40 секунут недоступности на одну перенесённую миграцию.

### Дополнение из практики: флаг без даты удаления (сентябрь 2026)

В CourseDesk-подобной системе флаг `newCourtClient` пережил две версии. Он был нужен для миграции на новый HTTP-клиент: старый код и новый должны были работать одновременно. Переключение прошло успешно, а ветка `if (flags.newCourtClient) { ...старый путь... }` осталась, потому что «она работает, её не трогать». Через два месяца она мешала: при разборе инцидента в неё зашли, потому что она выглядела как единственное место, где «может быть по-старому». Удаление — одна правка, но найти её без даты удаления в коде стоило отдельного захода.

## 9. Антипаттерны

### «`NOT NULL DEFAULT` в одной миграции с релизом кода»

Работает на dev, где нет чужих длинных транзакций. В проде — блокировка на время перезаписи (если дефолт неконстантный) или, что хуже, падение старого кода, если он пишет в таблицу без нового поля.

---

### Переименование столбца одним коммитом

Миграция и код в одном коммите: между ними окно, в котором старое имя ещё нужно, а новое — нет. Откатывается только код, миграция остаётся. Дальше — расхождение имён между схемой и ветками.

---

### `CREATE INDEX` в транзакции миграций

Блокирует запись на всё время построения. Для растущей таблицы — минуты. Правильно: `CONCURRENTLY` вне транзакции, плюс проверка на `INVALID`-остатки после сбоя.

---

### Feature flag без владельца и даты

Работает, никому не мешает, живёт вечно. Через год — мёртвая ветка, которую никто не удаляет из страха, и место в коде, куда при разборе инцидента заходят по ошибке.

---

### Миграция внутри шага деплоя

Необратимый шаг смешан с обратимым. Упал деплой — откатывается код, миграция осталась; или наоборот. Два независимых шага с отдельными кнопками «назад».

---

### Canary поверх необратимой миграции

Старый инстанс на новой схеме, новый на обеих. Если миграция удалила то, что пишет старый код, — 1% трафика теряет данные. Сначала expand-contract, потом canary.

---

### Recreate-деплой на однопользовательской витрине, объявленный как «у нас нет простоя»

У витрины с одним пользователем минута простоя — не авария, а неудобство. Объявлять это отсутствием простоя в ADR вредно: оно показывает, что обсуждение шло не о требованиях.

---

### Откат через обратную миграцию

`down`-миграция для обратимости работает только для простых операций. `DROP COLUMN` откатывается добавлением пустой колонки — данные потеряны навсегда. Откат в проде — это не обратная миграция, а развёртывание предыдущей версии кода на схеме, которая его поддерживает.

---

## Anti-checklist ☠️

- [ ] `ADD COLUMN NOT NULL` без дефолта в миграции — старый код падает на записи
- [ ] `NOT NULL DEFAULT now()` — неконстантный дефолт переписывает таблицу и блокирует запись
- [ ] `CREATE INDEX` без `CONCURRENTLY` — блокировка записи на время построения
- [ ] `CONCURRENTLY` внутри транзакции — ошибка; индекс остаётся `INVALID` и не используется, а выглядит рабочим
- [ ] `DROP COLUMN` в релизе, где возможен откат кода — откатнувшийся код пишет в несуществующее поле
- [ ] Переименование столбца одним коммитом с кодом — окно несовместимости при откате
- [ ] Флаг включён раньше, чем код с флагом задеплоен во все инстансы — на старых инстансах `undefined`
- [ ] Флаг без владельца и даты удаления — мёртвая ветка живёт вечно
- [ ] Миграция в одном шаге с деплоем — необратимое смешано с обратимым, откатывается только половина
- [ ] `ALTER TABLE` без `lock_timeout` — миграция встаёт в очередь за блокировкой и вешает запись
- [ ] Canary на необратимой миграции — старый инстанс теряет данные
- [ ] Обязательное поле в ответе или добавление значения в `enum` — внешний клиент падает без твоего CI
- [ ] Обратная миграция как единственный способ отката — `DROP COLUMN` откатывается пустой колонкой, данные потеряны

## Задачи AI-кодеру

Плохая формулировка:
> «Добавь поле `region` в таблицу contracts и обнови код, чтобы он его использовал.»

Разбор: не сказано, что старый код не должен сломаться, не задан порядок шагов, не сказано, что таблицу читает внешний потребитель. AI выдаст `ADD COLUMN ... NOT NULL` плюс правку кода в том же коммите — классическая авария, которую не ловит ни typecheck, ни тесты на dev.

Хорошая формулировка:
> «В таблице `contracts` (PostgreSQL 18) добавить nullable-колонку `region text`. Требования:
> 1. Миграция отдельным шагом от деплоя кода; коммит применённой миграции обязателен.
> 2. `SET lock_timeout = '3s'` и `statement_timeout = '60s'` в начале каждой миграции.
> 3. Новый код читает `row.region ?? DEFAULT_REGION`, старый код колонку не видит и не ломается.
> 4. Backfill существующих строк батчами по 1000 с паузой, вне одной длинной транзакции.
> 5. Переход в `NOT NULL` — через `ADD CONSTRAINT ... CHECK ... NOT VALID`, затем `VALIDATE CONSTRAINT` отдельным шагом.
> 6. `region` в ответе API — необязательное поле: внешний потребитель (1С) читает старый формат.
> Проверяемый критерий: на копии боевой базы миграция проходит при активной выгрузке потребителя, `lock_timeout` не срабатывает, время выполнения меньше 60 секунд.»

Формула: что делает + ограничения + конкретные API + версия платформы + проверяемый критерий.

Вторая задача — на порядок шагов:
> «Требуется переименовать `court_id` в `court_ref` и изменить тип с `bigint` на `text`. Опиши порядок операций, который переживает откат кода в любой момент, и укажи в каждом шаге, что именно делает система, если её в этот момент перезапустить.»

Ожидаемый ответ: `ADD COLUMN court_ref text NULL` → деплой кода с двойной записью → бэкфилл батчами → деплой только на `court_ref` → `DROP COLUMN court_id`. Переименование «в один шаг» в ответе быть не должно.

## Чеклист архитектора

### Порядок изменений
- [ ] Каждое изменение схемы разбито на обратимые шаги и одно необратимое — необратимое в конце
- [ ] Миграция — отдельный шаг с отдельной кнопкой «назад», коммит применённой миграции в репозитории
- [ ] Новый код работает со старой схемой; старый код работает с новой
- [ ] Определён порядок: expand → релиз → бэкфилл → contract

### Миграции
- [ ] `lock_timeout` и `statement_timeout` заданы в начале каждой миграции
- [ ] Неконстантные дефолты не используются в `ADD COLUMN` — дефолт ставится отдельно
- [ ] Индексы строятся `CONCURRENTLY` вне транзакции; наличие `INVALID` проверяется отдельным джобом
- [ ] `NOT NULL` через `CHECK NOT VALID` + `VALIDATE CONSTRAINT`, а не перезаписью
- [ ] Бэкфилл больших таблиц батчами с паузой, не одной транзакцией

### Контракт
- [ ] Новые поля ответа необязательные; расширение `enum` согласовано с потребителями, клиенты деградируют на неизвестное значение
- [ ] `Deprecation` и `Sunset` отправляются, по ним есть метрика использования старого пути
- [ ] Время кэша ответа у потребителей меньше окна deprecation
- [ ] Смысл существующего поля не меняется — при смене смысла это новое поле

### Флаги
- [ ] У каждого флага есть владелец и дата удаления в коде, рядом с местом чтения
- [ ] Код с флагом задеплоен во все инстансы до включения
- [ ] Флаг читается из конфигурации, а не зашит в код
- [ ] Проверка просроченных флагов в CI или в ночном джобе

### Деплой и откат
- [ ] Стратегия деплоя (rolling, blue-green, canary) зафиксирована в ADR вместе с kill criteria
- [ ] Graceful shutdown: текущие запросы завершаются, пул БД закрывается (модуль 18)
- [ ] Readiness-чек делает настоящую работу (соединение с БД, чтение схемы), а не проверяет, что процесс жив
- [ ] Откат проверен на практике: не «должен работать», а откатывали и зафиксировали время
- [ ] Миграция не мешает раскатке: схема покрывает обе версии кода на всё время раскатки

### Вытеснение чужой системы
- [ ] Перехват идёт по операциям, а не «переписываем и переключаем»
- [ ] На переходном этапе есть сверка расхождений и владелец, который их разбирает
- [ ] У пользователя виден признак, в какой системе создана запись
- [ ] Направление синхронизации одностороннее, либо правило выбора победителя при расхождении определено явно
