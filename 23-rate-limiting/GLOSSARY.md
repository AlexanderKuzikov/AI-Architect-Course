# GLOSSARY — Rate Limiting паттерны

Термины из модуля по алфавиту. Латиница — первой, затем кириллица.

---

## B

**blockDuration**  
Параметр rate-limiter-flexible: время блокировки ключа (в секундах) после превышения лимита. При `blockDuration: 3600` — ключ заблокирован на 1 час после 5 неудачных попыток. Без этого параметра — каждый запрос просто отклоняется без накопительного эффекта.

**burst capacity**  
Максимальный токен/запрос накопленный в Token Bucket. Определяет разрешённый мгновенный burst: при полном bucket клиент может сделать B запросов за любое время. После исчерпания — только со скоростью пополнения R/sec.

---

## F

**fail closed**  
Стратегия поведения при недоступности Redis: блокировать все запросы. Максимальная безопасность, минимальная доступность. Применимо для аутентификации и финансовых операций — не для публичного API.

**fail open**  
Стратегия поведения при недоступности Redis: пропускать все запросы. Сервис работает, но без защиты. Компромисс — insurance limiter: in-memory fallback с теми же ограничениями.

**Fixed Window**  
Алгоритм rate limiting: счётчик сбрасывается по фиксированному таймеру. O(1) память. Уязвим к window boundary attack: злоумышленник делает burst в конце одного окна и начале следующего — реальный burst = 2× лимита.

---

## H

**hash tag (Redis Cluster)**  
Конструкция `{userId}` в Redis-ключе, гарантирующая что ключ попадёт в определённый hash slot. В Redis Cluster ключи Lua-скрипта должны быть на одном узле. Без hash tags Lua-скрипты падают при cross-slot операциях.

---

## I

**idempotency key**  
Заголовок (`Idempotency-Key`) позволяющий клиенту безопасно повторить запрос. Сервер хранит результат по ключу: повторный запрос возвращает сохранённый результат, не выполняет операцию заново. Связан с rate limiting: ретрай не должен тратить дополнительные токены.

**insurance limiter**  
Паттерн rate-limiter-flexible: RateLimiterMemory как fallback при недоступности Redis. Активируется при `instanceof Error` в `catch` блоке. Разные инстанции приложения не синхронизируются между собой — лимит применяется per-process, не globally.

---

## K

**keyPrefix**  
Namespace для Redis-ключей в rate-limiter-flexible. Формат: `rl:{service}:{limiterName}`. Обязателен при shared Redis между сервисами — предотвращает коллизии счётчиков.

---

## L

**Leaky Bucket**  
Алгоритм rate limiting: входящие запросы накапливаются в очереди, обрабатываются с фиксированной скоростью. Гарантирует равномерный выходной поток. Burst легитимных запросов отклоняется при заполненной очереди. Применим для защиты downstream сервисов.

---

## P

**points**  
Единица измерения в rate-limiter-flexible. Один запрос потребляет 1 point по умолчанию. Дорогие операции могут потреблять больше: `limiter.consume(key, 5)` — списать 5 points за один вызов AI inference.

---

## R

**RateLimiterRes**  
Объект, который rate-limiter-flexible бросает при превышении лимита. Поля: `remainingPoints` (0 при блокировке), `msBeforeNext` (миллисекунды до сброса), `consumedPoints` (текущее потребление). Используется для заголовков `Retry-After` и `RateLimit-Remaining`.

**RateLimiterUnion**  
Класс rate-limiter-flexible для одновременного применения нескольких лимитеров. `consume()` атомарно проверяет все — отклоняет если хотя бы один превышен. Используется для многоуровневых лимитов: per-minute + per-hour + per-day.

**Retry-After**  
HTTP заголовок (RFC 7231): число секунд или дата до которой клиент должен подождать перед повтором. Обязателен в 429 ответе. Клиенты, соблюдающие его, автоматически снижают нагрузку — retry storm предотвращается.

---

## S

**Sliding Window Counter**  
Алгоритм rate limiting: взвешенная комбинация двух соседних fixed window. `count = prev × (1 - elapsed/window) + curr`. Аппроксимация скользящего окна. O(1) память. Погрешность ≤ 10% — достаточно для production.

**Sliding Window Log**  
Точный алгоритм rate limiting: sorted set с timestamp каждого запроса. O(N) память. Нет window boundary attack. Не масштабируется при высоком трафике (> 1000 req/min/user) из-за роста sorted set.

---

## T

**throttling**  
Замедление запросов, а не отказ. Вместо 429 — добавление задержки ответа. Менее агрессивная альтернатива rate limiting для легитимных клиентов при перегрузке. Реализуется через Leaky Bucket с очередью.

**tiered limits**  
Разные rate limits для разных тарифных планов. Free / Premium / Enterprise — каждый получает свой экземпляр лимитера. Синглтоны лимитеров на уровне модуля, не создавать при каждом запросе.

**Token Bucket**  
Алгоритм rate limiting: bucket наполняется токенами со скоростью R/sec до максимума B. Каждый запрос потребляет токен. Разрешает burst до B запросов. Сложнее реализовать атомарно в Redis, чем Fixed Window.

**trust proxy (Express)**  
Настройка `app.set('trust proxy', N)` определяет сколько hop-ов от клиента доверять в X-Forwarded-For. Без этой настройки `req.ip` возвращает IP прокси. С `trust proxy: 1` — извлекает реальный IP клиента для per-IP rate limiting.

---

## W

**window boundary attack**  
Атака на Fixed Window: burst запросов в конце текущего окна + burst в начале следующего = 2× лимита за короткий период. Sliding Window Counter снижает уязвимость до ~10% благодаря взвешиванию предыдущего окна.
